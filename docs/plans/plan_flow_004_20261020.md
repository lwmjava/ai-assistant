## 1. 契约

交付：

- 打开开关且 croniter 齐全时，定时路径可用。
- 未安装 croniter 时，页面写明只剩手动执行。

验收：

- 关闭时不自动跑定时。
- 打开且依赖齐全时，到点可触发。
- 缺 croniter 时，页面有只剩手动的说明。

非目标：不做重试；不重做 FLOW-003 的到点判定。默认开关保持关闭。不新增配置项、依赖、迁移或模型表。

## 2. 现状

`WORKFLOW_ENABLED` 默认 false。关闭时 `start_scheduler` 不创建循环，工作流 API 返回 503，页面标题为「工作流引擎未启用」。打开且已安装 croniter 时，调度器会启动，到点执行已由现有最近到期判定完成。

croniter 缺失时，调度器只记警告并不启动，API 仍可手动执行，但列表响应和页面都没有「只剩手动执行」。页面无法自行得知服务器是否装了 croniter。

`README.md` 不在本卡允许路径。因此不新增路由，避免端点表必须改到仓库根文档。调度可用性挂在现有 `GET /api/v1/workflows` 的响应头 `X-Workflow-Schedule` 上，JSON 列表保持不变。

## 3. 方案

在 `app/workflow/scheduler.py` 增加 `schedule_mode()`：

- 开关关闭：`disabled`。调度器不启动。API 仍返回 503，页面保持现有未启用说明，不把「只剩手动」写到整组接口被拒绝的状态上。
- 开关打开且 croniter 可导入：`scheduled`。`start_scheduler` 创建原循环。
- 开关打开但 croniter 不可用：`manual-only`。不创建循环，不把导入失败变成进程崩溃。列表响应头为 `manual-only`。手动执行仍走原引擎。

`_is_scheduler_runnable` 复用同一判定，保留现有缺失依赖警告。第二次启动仍幂等。

列表路由在返回前写入响应头。值只表示本进程当前配置，不读取其他租户的数据。未登录或无读权限仍按原依赖拒绝，不额外暴露模式。

现有 `api.get` 只解析 JSON，会丢掉响应头。列表查询要在 `frontend/src` 内改成能同时拿到 JSON 和 `X-Workflow-Schedule`，再把模式放进页面状态。只改渲染、继续用现在的 `useWorkflows`，页面说明不会出现。

值为 `manual-only` 时，空列表和已有任务列表都显示：「未安装 croniter，定时不会自动运行，目前只剩手动执行。」空列表不得再写「引擎会按周期自动执行」。`scheduled`、缺少响应头，以及 503 未启用页，保持现有文案。

## 4. 失败边界

| 类别 | 反例与可观察结果 |
|---|---|
| 数值/枚举边界 | 模式只允许 `disabled`、`scheduled`、`manual-only`。导入抛出既有 `CroniterNotAvailableError` 时得到 `manual-only`，不得到空字符串或未捕获崩溃。 |
| 失败路径 | croniter 缺失时调度任务为空；同一进程第二次 `start_scheduler` 不创建第二个循环；手动执行仍能写入一条 manual 记录。 |
| 权限与租户 | 无读权限或未登录不能靠列表响应头看到模式；模式不包含其他租户的工作流内容。开关关闭时 503 行为保持。 |
| 身份与绑定 | 响应头来自当前进程配置和当前解释器的导入结果，不读取另一套数据库里的开关。 |
| 回滚与幂等 | 缺失依赖时没有残留后台任务；恢复导入后下一次启动可以创建循环。已有执行记录不删除、不重放。 |

到点触发复用现有 `_loop`/`_tick`，不改最近到期算法。打开且依赖齐全的验收必须经过 `start_scheduler`，不能只调用手动接口。
