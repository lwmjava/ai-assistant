## 1. 目标

创建者（owner）被禁用、移出租户或删除时，工作流被自动停用（`suspended_owner=True, enabled=False`，此既有行为已存在），同时**新增落库一条本租户可查询告警**，包含：工作流（名称/ID）、原创建者（ID/用户名快照）、原因。本租户 `tenant_admin`（及同租户具备 `workflows:read` 者）可在工作流页/API 查到；跨租户不可见。

## 2. 现状（读代码后核对，含行号）

- 既有停用逻辑：
  - 引擎手动/每次重试前复核：`app/workflow/engine.py:288-296`。条件合并了「工作流行变化 / tenant 不匹配 / owner_id 不匹配 / 传入 owner 与记录 owner 不一致 / actor 为 None / actor 非 active / actor.tenant_id != workflow.tenant_id」；命中后置 `current.enabled=False; current.suspended_owner=True` 并 commit，返回 failed。
  - 调度器 cron 触发前：`app/workflow/scheduler.py:127-132`，`owner is None` 时停用。
- 路由：`app/api/routes/workflow.py`。`WorkflowOut` 已含 `suspended_owner`（第 97 行）；列表 `GET /workflows`（180）、详情 `GET /workflows/{workflow_id}`（193）、执行历史 `GET /workflows/{workflow_id}/executions`（264）。权限依赖 `require_permission("workflows", "read"|"write"|"delete")`。
- 权限矩阵：`app/core/security.py:216-229`，`workflows:read` 允许 system_admin / system_viewer / tenant_admin / member。
- 多租户可见性惯例：`_list_stmt`（routes/workflow.py:126-131）与 `_get_owned`（134-142）：system_admin 跨租户，其余按 `tenant_id` 过滤。
- 建表机制：`app/core/database.py:46-57`，`init_db` 已 side-effect import `app.audit.models`，随后 `SQLModel.metadata.create_all(engine)` 幂等建表。**新告警表放入 `app/audit/models.py` 即自动纳入导入链，无需改 `app/core/database.py`**。
- 审计体系：`app/audit/models.py` 现有 `AuditLog`（`audit_logs`）与 `AuditAction` 枚举；`app/audit/logger.py` 为旁路异步写入，失败降级。审计事件无面向 tenant_admin 的结构化查询端点，且语义是「谁做了什么」，不承载「工作流被停用的原因快照」。本卡不复用 AuditLog，新建独立告警表（与 PWFL-004 的执行失败告警互不混用）。
- 全库当前无任何 Alert/告警模型（grep 核对），本卡为首建。
- 前端：`frontend/src/pages/Workflows.tsx` 已对 `suspended_owner` 渲染「创建者失效」Badge（354-358）；`frontend/src/api/workflows.ts` 提供 react-query hooks；`frontend/src/types/api.ts:316` 定义 `WorkflowOut`。

## 3. 方案

### 3.1 告警模型（落点：`app/audit/models.py`）

新增 SQLModel 表 `workflow_owner_alerts`：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | str PK | uuid hex |
| tenant_id | str, index | 告警归属租户（隔离键） |
| workflow_id | str, index | 被停用工作流 |
| workflow_name | str | 名称快照（工作流可能被删） |
| owner_id | str, index | 原创建者 |
| owner_username | str \| None | 用户名快照（owner 已删时为 None） |
| reason | str, index | `owner_disabled` / `owner_moved_out` / `owner_deleted` / `owner_invalid` |
| detail | str \| None | 人读原因 |
| created_at / updated_at | TimestampMixin | |

理由：放 `app/audit/models.py`，该模块已被 `database.py:46` import，create_all 自动建表；不触碰 `app/models/`（不在 allowed_paths）、不改 `app/core/database.py`。

### 3.2 写入点（两处，幂等）

- **`app/workflow/engine.py` `_attempts`**：在现有置位块内，先按 actor 状态判定 reason：
  - `actor is None` → `owner_deleted`
  - `not actor.is_active` → `owner_disabled`
  - `actor.tenant_id != tenant_id` → `owner_moved_out`
  - 其余（并发行变化/身份不一致）→ `owner_invalid`
  - 仅当 `current.suspended_owner` 当前为 False（即首次转入停用态）时写入告警，避免重试/重复触发产生重复记录；随后照旧置 `enabled=False, suspended_owner=True` 并同一事务 commit。
- **`app/workflow/scheduler.py` `_trigger`**：`owner is None` 分支内，置位前写 reason=`owner_deleted` 的告警（同一 session，commit 一并落库）。

幂等：已 `suspended_owner=True` 的工作流不会被调度器选中（scheduler.py:67 过滤）；手动 `run_workflow` 在 engine 前对 `owner is None` 返回 409；引擎路径用「仅首次转入」守卫避免重复告警。

### 3.3 查询 API（`app/api/routes/workflow.py`）

- 新增响应模型 `WorkflowAlertOut`（id/tenant_id/workflow_id/workflow_name/owner_id/owner_username/reason/detail/created_at）。
- 新增 `GET /workflows/alerts`（**必须声明在 `/{workflow_id}` 之前**，避免被路径参数吞掉）：
  - 依赖 `require_permission("workflows", "read")`（与既有工作流读一致，不新增资源/动作，避免改 `app/core/security.py`）。
  - system_admin 跨租户；其余按 `tenant_id == user.tenant_id` 过滤 → 跨租户 tenant_admin 查不到他租户告警。
  - 按 created_at 倒序。

### 3.4 前端展示（`frontend/src/`）

- `types/api.ts` 增 `WorkflowAlertOut`。
- `api/workflows.ts` 增 `useWorkflowAlerts()`。
- `pages/Workflows.tsx`：拉取告警，存在时在列表顶部渲染一条告警条，展示「工作流名 / 原创建者 / 原因文案」。原因文案映射四种 reason。

- 路由顺序：`/alerts` 必须先于 `/{workflow_id}` 声明，否则被当 workflow_id。→ 代码审查核对。

- 幂等：重复触发不得产生重复告警 → 用 `not current.suspended_owner` 守卫 + 测试断言行数。
