## 3. 实现方案

### 3.1 十要素契约模型（新增 `app/agents/tools/contract.py`，allowed 内）

对齐 AGENTS.md §7 十项，定义：

- `RiskLevel(str, Enum)`：`L0/L1/L2/L3`。
- `ToolPermission` dataclass：`authenticated: bool`（是否要求非空 user_id）、`allowed_roles: frozenset[str] | None`（None＝任意已认证角色；限定角色集如 {system_admin, tenant_admin}）、`tenant_scoped: bool`（是否必须绑定上下文 tenant_id，且工具参数不得接受 tenant_id）、`resource: str`、`action: str`（供与既有 RBAC 语义对齐的标签，不强行改 ROLE_PERMISSIONS）。
- `ToolContract` dataclass：`version: str`、`permission: ToolPermission`、`risk: RiskLevel`、`side_effect: str`、`timeout_seconds: float`、`max_retries: int`（当前全部 0，不盲目重试）、`idempotent: bool`、`conflict_policy: str`（如 "create_only_no_overwrite" / "none"）、`error_model: str`（"observation_string_no_raise"）、`audit: bool`。
- `Tool` 增加可选字段 `contract: ToolContract | None = None`（向后兼容；但 §3.3 强制要求 default_tools() 全部显式声明）。
- 既有工具契约初值（不改变业务行为，只声明）：

|---|---|---|---|---|---|---|---|

| get_current_datetime | L0 | 否 | None | 5 | 是 | none | 1.0.0 |

| code_sandbox | L1 | 否 | None | =timeout 参数上限 | 否 | sandboxed_code_execution | 1.0.0 |

### 3.2 执行咽喉改造（`app/agents/tools/base.py` run()）

按顺序：

1. **身份解析**：`user_id = log_context.get_user_id()`、`tenant_id = log_context.get_tenant_id()`；user_id 非空时 `Session(engine)` 查 User 得 role（失败/用户不存在 → role=None，按未授权处理）。
2. **权限门**：契约 `permission.authenticated` 且 user_id 为空 → 拒绝；`allowed_roles` 非 None 且 role 不在集合 → 拒绝；`tenant_scoped` 且 tenant_id 为空 → 拒绝；工具参数含 `tenant_id`/`user_id` 键 → 拒绝（防伪造身份）。
3. **L2 保守门**：risk >= L2 且（写开关未显式开启 或 角色未授权）→ 拒绝。拒绝返回脱敏观测文本（不含堆栈/密钥/参数）。
4. **L3 注册拦截**：`register()` 时契约 risk==L3 → 抛 `ValueError`/拒绝注册（审批闭环不存在，保证 L3 永不进注册表）。
5. **超时包裹**：`asyncio.timeout(contract.timeout_seconds)` 包裹 execute；超时 → 分类观测 "timeout"。既有工具内部超时仍保留（双重保护，不改变成功路径行为）。max_retries=0：不自动重试。
6. **审计写入**：执行前/后统一 `get_audit_logger().log(action=AuditAction.TOOL_CALL, user_id=..., tenant_id=..., resource_type="tool", resource_id=tool_name, details={risk, allowed, reason_code, latency_ms, idempotent})`——**每次 run() 恰好一条**（拒绝也写，allowed=false）；details 不含 arguments/密钥；AUDIT_ENABLED=False 或 DB 故障时降级不阻断业务。
7. **审计枚举**：`app/audit/models.py` `AuditAction` 增加 `TOOL_CALL = "tool_call"`（allowed 内）。
8. **注册表输出**：`ToolRegistry.describe_contracts() -> list[dict]`，逐工具输出十要素全字段（acceptance①）。

### 3.4 file_ops 写路径（`app/agents/tools/file_ops.py`，L2 参考实现）

- **显式开启开关**：因 config.py 不在 allowed_paths，写开关采用模块内显式 opt-in：`file_ops_write_availability()` 要求 `os.environ.get("FILE_OPS_WRITE_ENABLED") == "true"` 且 `settings.FILE_OPS_ENABLED is True` 且 `_approved_roots()` 有效；否则写动作不注册、执行即拒。默认（无环境变量）＝关闭。计划在此标注偏差：正式应移入 Settings（属后续配置治理卡），本卡不扩 config.py。
- **写动作边界**：仅在已授权共享根下**新建** UTF-8 文本文件；目标路径已存在 → conflict 拒绝（create_only_no_overwrite，重试不产生重复副作用）；复用读路径全部防护（相对路径、无 `..`/绝对/盘符、私有组件后缀/名字、符号链接/junction 链、扩展名白名单、字节上限＝FILE_OPS_MAX_BYTES、内容控制字符/秘密模式拒绝）；不接受 tenant_id/user_id 参数；写后回读绑定校验（同读路径的 handle/TOCTOU 思路）。
- **注册形态**：写不拆成第二个工具名，而是 file_ops 工具内 `action: "write"` 参数；写开关关闭时 `action="write"` 直接拒绝且工具 Schema 不暴露 write（保持默认关闭不可见）。
- **角色门**：运行时仅 {system_admin, tenant_admin} 可写；匿名/开发无认证模式（ContextVar 空）一律拒绝。

### 3.5 决策点（实现前需审查确认，均不擅自扩范围）

1. config.py 排除 → 写开关走 os.environ 直读（§3.4），接受与 Settings 惯例的偏差并在实现说明登记。
2. `GET /api/chat/tools` 不扩展十要素输出（chat.py 越界）；acceptance① 由进程内 `describe_contracts()` 满足。
3. 角色解析走 DB 单查（不缓存跨请求）；测试内用 `log_context.set_user` 合成身份。
4. **P2-2 分层偏差登记（审查 2026-10-12 要求）**：run() 入口以 `Session(engine).get(User, user_id)` 直查角色，属 AGENTS.md §5「agents 不得直接操作数据库」的 Brownfield 偏差。在此处直查的原因：①角色上下文注入（deps.py/log_context.py）不在本卡 allowed_paths，无法改认证链路把 role 带进 ContextVar；②为只读主键查询，与既有 `AuditLogger._write_db`（logger.py:186）同模式，不嵌套请求 session、无写操作。最小化措施：仅在契约 `permission.allowed_roles` 非 None（即 L2 写）时才查询，L0/L1 工具不触发 DB 访问；查询 try/except 失败按 role=None（未授权、fail-closed）。后续治理方向：由身份依赖把 role 写入 ContextVar，run() 只读上下文，消除 agents 层直查（后续卡，本卡不做）。实现说明须原样登记本偏差。
5. **P3 约束登记（审查注明，接受为约束，不改方案）**：
   - P3-1：写开关 os.environ 直读，.env 文件无法配置——方向保守（更难开启），符合「未单独批准不开放」。
   - P3-2：契约 allowed_roles 硬编码与 ROLE_PERMISSIONS 矩阵双轨——因 security.py 越界；resource/action 标签字段预留对齐，不新增矩阵行。
   - P3-3：合同级 asyncio.timeout 对同步阻塞工具（code_sandbox）只能取消 await 点、不能中断线程内执行——timeout 字段语义为「墙钟目标」，依赖 code_sandbox 既有内部超时兜底。
   - P3-4：dev 无认证模式 `_DISABLED_AUTH_PRINCIPAL` 合成 SYSTEM_ADMIN（deps.py:23-31）与 ContextVar 空（deps.py:48）并存——本卡按 ContextVar 判定，dev 模式「合成 admin 也不能用 L2 写」是刻意保守行为，实现说明须写明以免误判为 bug。

### 3.6 contract=None 工具的 fail-closed 语义（审查 P2-1 要求）

MCP 启用时 `chat_service.py:206` 的 MCP 工具经同一 ToolRegistry 进入 run()，其 Tool 无 contract。定义统一语义：

- **权限门**：contract is None 视同 `authenticated=True`：ContextVar user_id 为空 → 拒绝（观测脱敏，写审计 allowed=false）。不假定其角色。
- **风险门**：contract is None 视同 risk=L2 保守门：未经显式允许一律拒绝执行（返回脱敏观测）。MCP 默认关、本卡不扩展 MCP 治理，故该语义在本卡表现为「MCP 工具在契约补齐前不可被执行」，而不是静默放行。
- **审计**：与契约工具一致，run() 每次调用（含拒绝）写一条 tool_call，details.risk 记 `"unlisted"`、allowed 按实际判定。
- **describe**：`describe_contracts()` 对 contract=None 工具输出十要素字段显式标 `"missing"`（不静默跳过、不伪造默认值）。完整性断言 `test_every_registered_tool_has_complete_contract` 遍历的是 `default_tools()` 注册表（本卡装配口径）；MCP 工具以 `"missing"` 显式标注，实现说明写清「十要素完整性覆盖 default_tools 注册表，MCP 工具经 fail-closed 拒绝并标注 missing」的边界。

## 6. 验收映射、风险与回滚
