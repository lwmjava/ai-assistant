### 2.1 工具循环与退出条件（`app/agents/pipeline.py`）

- `AgentState`（pipeline.py:218-241）：每请求新建；已有 `tool_results`、`code_results`、`draft`、`executed_tool_fingerprints` 等请求态字段。

## 3. 实现方案

### 3.1 落地位置：管线循环层（`_iter_action_loop`），不动注册表层

理由：预算语义是「请求内行动轮次上限」；注册表层 run() 是单次工具咽喉，无循环上下文。管线层已有 `range` 硬边界，最小增量。Brownfield 约束：不重写循环结构。

### 3.2 计数口径

- 预算单位 = **进入工具行动的轮次**（每轮至多一次实际 `registry.run()`）。
- 被拒（invalid/denied）的尝试**也消耗一轮**——保守侧：失控 LLM 发畸形格式同样烧预算，防止靠畸形消息无限循环。
- 重复指纹 skip → break，不继续消耗（既有行为）。
- 实际执行次数 ≤ 预算值；PAGT-002 每 run() 一条审计不变。

### 3.3 停止行为与返回文案（acceptance② 落地；审查 P2-1 采用方案 B）

- 新模块常量（pipeline.py 顶部既有观察串旁）：
  `_BUDGET_EXHAUSTED_NOTICE = "\n\n（系统提示：本次对话已达到工具调用次数上限 {limit} 次，后续内容基于已有工具结果生成。）"`
- **循环内只置标志、不改 draft**：
  - `AgentState` 新增字段 `tool_budget_exhausted: bool = False`（请求态，与 executed_tool_fingerprints 同层）。
  - `_iter_action_loop` 循环改为 `for round_no in range(1, self.max_tool_rounds + 1): ... else: state.tool_budget_exhausted = True`（`return`/`break` 不触发 else；`continue` 照常触发）。既有尾块 `if wrap_up and inspect_tool_call(state.draft).status != "none": state.draft = await self._finalize_without_tools(state)`（:803-804）**原样保留**——finalize 只经此一处发生，天然幂等、不 double-finalize（审查 P3-1）。
- **注入点后移到 QualityGate 之后（方案 B）**：新增 `_apply_budget_notice(state)`（幂等：标志未置或 draft 已含后缀则不动），在以下四处调用——
  1. `run()` 短路路径：:603 `_run_action_loop(state, _SHORT_PATH_POLICY)` 之后、:607 应答之前；
  2. `run()` 完整路径：:642 `state.draft = await self._quality_gate_loop(state)` 之后、:646 反思之前；
  3. `run_stream()` 短路路径：:831 行动循环之后、:835 stream_chat 之前；
  4. `run_stream()` 完整路径：:884 质量门块之后、:887 反思之前。
- 效果：**被评分 draft 不含 notice**（质量门在注入前完成评分与重入）；最终应答草稿携带确定性说明。跑满上限且 LLM 仍要工具 → 既有 `_EXHAUSTED_DRAFT` 保留，其后再追加 notice；LLM 自愿提前停 → 标志不置，无后缀（未达上限=现状行为）；重复指纹 skip-break → else 不触发、标志不置、无后缀（对齐既有 `test_trace_records_tool_statuses_without_secrets` 与 `test_distinct_arguments_stop_at_round_limit` 的精确断言）。
- 短路径（fast_path.py 直调 `_iter_action_loop` 后 `state.answer = state.draft`，fast_path.py 不在 allowed_paths）：耗尽时 draft 可能是既有 `_EXHAUSTED_DRAFT`（LLM 坚持调用时逐字可见说明）；LLM 配合时该路径不追加后缀——登记为已知边界（实现说明写明）。

### 3.4 配置项设计（config.py + .env.example）

- `AGENT_MAX_TOOL_ROUNDS: int = Field(default=10, ge=1, le=100)`（对齐 PRD §5.1.3 的 10；上界 100 防失控成本）。
- 仿 config.py:432 加 `@field_validator("AGENT_MAX_TOOL_ROUNDS", mode="before")`：`bool` 或非 `int|str` → `ValueError("单次对话工具调用上限必须是 1..100 的整数")`；环境变量整数字符串放行（pydantic ge/le 兜底）。
- `.env.example:225`：`AGENT_MAX_TOOL_ROUNDS=5` → `AGENT_MAX_TOOL_ROUNDS=10`，注释补「范围 1~100；达到上限后停止并在回复中说明」。
- `pipeline.py:323` 默认 `5` → `10`（直接构造对齐 PRD；chat_service 两处显式从 settings 赋值不变——那是「可按配置调整」的接线证据）。
- **命名保留** `AGENT_MAX_TOOL_ROUNDS`（PRD 名 `max_tool_calls`）：单轮≤1 次调用，语义等价；改环境变量名属破坏性配置变更，Brownfield 不做；实现说明登记别名关系。

### 3.5 流式兼容

后缀由 `_apply_budget_notice` 落在 `state.draft`（质量门之后）：run_stream 经 `_build_respond` 的「回答草稿」转述输出（既有 LLM 阶段）；fast_path 逐字 chunk（其耗尽文案依赖既有 `_EXHAUSTED_DRAFT`，见 §3.3 边界）。测试断言 draft 层与（脚本化应答者回显的）answer 层。
