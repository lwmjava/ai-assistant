# 工作流失败重试实施计划

日期：2026-10-20。状态：独立计划审查的四项阻断已纳入，按修订后的计划实施。原始任务：tasks.yaml 的 PWFL-001。前置是 FLOW-001。用户要求用单卡交付技能实现本卡。本计划不授权生产启用、收费模型、合并或部署。审查见 `docs/reviews/2026-10-20-pwfl-001-plan-review.md`。

技能要求落盘计划与审查，因此会写入 `docs/plans/` 与 `docs/reviews/`。配置只改 `app/core/config.py` 和 `.env.example`，不改 `README.md`。三项参数都要写上：重试上限、退避基数、单次等待上限。

## 1. 契约

交付：失败按指数退避重试并设上限；重试次数与退避参数可配置。

验收：注入一次临时失败后可自动重试成功；持续失败达到上限后停止并记录原因。

非目标：不做分布式重试协调；不改 cron 触发机制。不实现超时、取消、并发池或告警。不新增表、迁移或前端。

产品 §5.6.2 写明 `retry_count` 默认 0、最大 3。misfire 仍是只补跑最近一次，本卡不改调度比较。

## 2. 现状

`WorkflowEngine.execute` 调用 bridge 一次。失败就把同一条执行记录标为 failed 并写入异常文本。调度器在进入执行前消费到期槽；失败记录的创建时间会挡住同槽再次触发。因此重试必须发生在同一次 `execute` 内，不能靠下一轮 tick 补跑。

手动执行和定时执行都走 `execute`。创建者失效是确定性拒绝，不是临时故障。

## 3. 方案

在 `app/workflow/engine.py` 内对 bridge 失败做有限重试。同一条 `WorkflowExecution` 从 pending 到 running，成功或最终失败后结束。不新增多条执行记录，不改 `scheduler.py` 的到期判定。

配置：

- `WORKFLOW_RETRY_MAX`：额外重试次数，默认 0，小于 0 按 0，大于 3 按 3。默认 0 时现有失败路径只尝试一次。
- `WORKFLOW_RETRY_BASE_SECONDS`：第一次重试前的等待基数，默认 1。非有限数或负数按 0，大于 30 按 30。
- `WORKFLOW_RETRY_MAX_DELAY_SECONDS`：单次等待上限，默认 8。非有限数或负数按 0，大于 30 按 30。

第 n 次重试前等待 `min(base * 2^(n-1), max_delay, 30)` 秒。基数和单次等待都不再超过 30 秒，避免串行调度被一次退避拖住。等待函数默认为 `asyncio.sleep`，测试注入记录等待值的替身，避免真实长睡。

每次调用 bridge 前重新读取创建者和任务。创建者禁用或离开原租户时立即失败并停用任务，不再调用 bridge，也不为后续尝试继续等待。`CancelledError` 不捕获。只有最终成功才发 webhook。最终失败时 `error` 保留最后一次异常文本，并写明已达到的重试上限。成功时 `status=success`，`error` 为空。

每次 bridge 尝试仍走原 `WorkflowBridge` 和 `ChatService`。失败尝试可能已经留下对话消息并计入配额。本卡不改 `ChatService`，也不做跨尝试的幂等抵消。

## 4. 失败边界

| 类别 | 反例与可观察结果 |
|---|---|
| 数值边界 | 重试次数 -1 与 99 分别变成 0 与 3。退避基数或上限为负数、NaN、Infinity 时等待为 0，不挂起。 |
| 失败路径 | 第一次 bridge 失败、第二次成功：只新增一条 success 记录，等待次数为 1。连续失败时调用次数等于 1 加上限，随后停止，记录含原因和上限。 |
| 权限与租户 | 创建者禁用或租户不匹配时不重试、不调用 bridge，原停用逻辑仍生效。重试不读取其他租户的执行记录。 |
| 身份与绑定 | 重试更新同一条执行记录，租户和 `triggered_by` 不变。等待使用测试注入的时钟，不依赖另一套数据库。 |
| 回滚与幂等 | 上限为 0 时失败只调用一次，与现有行为一致。同一次执行不产生第二条记录。调度水位仍按该记录的创建时间消费，不因重试再触发同一槽。 |
