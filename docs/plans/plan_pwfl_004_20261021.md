## 1. 目标

1. **执行失败产生告警事件**：一次执行最终失败时，落库一条可查询告警记录（含租户、工作流、执行 ID、失败原因）。
2. **执行日志可按 trace_id 检索**：每次执行生成一个执行级 trace_id，所有执行日志（开始、每次尝试、结束）关联该 trace_id，可按 trace_id 查询完整轨迹。

## 2. 现状（代码事实，2026-10-21 核对）

### 2.1 执行失败路径

`app/workflow/engine.py` 的 `_execute_admitted`（第 152–274 行）是唯一执行入口：

- **最终失败统一落点**：第 246–258 行——`outcome[0] != "success"` 时 rollback 未提交的尝试写入，再把 `WorkflowExecution` 行的 status/output/error/finished_at/duration_ms 落库 commit。
- **所有失败路径都汇聚到这里**：
  - 重试耗尽（`_attempts` 返回 `("failed", None, ...)`，第 327 行）
  - 桥接调用异常（第 321–325 行 catch 后 continue，最终耗尽重试）
  - 总时限超时（`entry.stop("WORKFLOW_TIMEOUT")` → 第 241–242 行覆盖 outcome）
  - 父任务取消（第 269–270 行抛 CancelledError 前，第 241–244 行已落库 failed）
  - 创建者失效（`_attempts` 第 316 行返回 failed；同时 FLOW-005 已写 `WorkflowOwnerAlert`）
  - 租户不可用（第 318 行返回 failed）
- **异常 setup 路径**：第 187–216 行——register/timer 创建失败时，单独把执行行置 failed 并 commit。这也是失败，应产生告警。

## 3. 方案

### 3.1 新增两个模型（均在 `app/audit/models.py`）

**`WorkflowExecutionAlert`（表 `workflow_execution_alerts`）**——执行失败告警：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | str (PK, uuid hex) | 主键 |
| tenant_id | str, index=True | 租户隔离键 |
| workflow_id | str, index=True | 工作流 ID |
| workflow_name | str | 名称快照（工作流可能被删） |
| execution_id | str, index=True | 关联的 WorkflowExecution.id |
| trace_id | str, index=True | 关联执行日志的 trace_id |
| reason | str, index=True | 失败原因码：`retry_exhausted` / `timeout` / `owner_invalid` / `tenant_unavailable` / `bridge_error` / `cancelled` / `setup_error` |
| error_message | str \| None | 原始错误信息（截断） |
| detail | str \| None | 补充说明 |
| TimestampMixin | | created_at / updated_at |

**`WorkflowExecutionLog`（表 `workflow_execution_logs`）**——执行日志条目：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | str (PK, uuid hex) | 主键 |
| tenant_id | str, index=True | 租户 |
| workflow_id | str, index=True | 工作流 |
| execution_id | str, index=True | 关联的执行 |
| trace_id | str, index=True | **核心检索键**：同一执行的所有日志共享 |
| level | str | `info` / `warning` / `error` |
| message | str | 日志消息 |
| TimestampMixin | | created_at |

### 3.2 执行级 trace_id 生成与贯穿

- 在 `_execute_admitted` 第 157 行附近（拿到 workflow_id/tenant_id 后）生成：`trace_id = uuid.uuid4().hex[:12]`（与 `app/debug/trace.py` 同风格）。
- 把 `trace_id` 作为参数传入 `_attempts`，使每次尝试的日志都带同一 trace_id。
- 所有日志条目（开始、每次 attempt、结束）和最终失败告警都使用该 trace_id。
- **重试/退避过程中的日志归并**：因为 trace_id 在执行开始时生成且不变，同一次执行的多次 attempt 日志自然归并到同一 trace。

### 3.3 日志写入点（`app/workflow/engine.py`）

| 位置 | level | message 示例 |
|---|---|---|
| `_execute_admitted` 第 168 行 commit 后 | info | `执行开始 triggered_by=manual` |
| `_attempts` 每次 bridge 调用前 | info | `第N次尝试开始` |
| `_attempts` bridge 异常 catch（第 321 行） | warning | `第N次尝试失败：<错误>` |
| `_attempts` 成功 return 前 | info | `第N次尝试成功` |
| `_attempts` 最终耗尽（第 327 行） | error | `重试耗尽` |
| `_attempts` owner 失效分支 | warning | `创建者失效` |
| `_attempts` 租户不可用 | warning | `租户不可用` |
| `_execute_admitted` 最终 commit 后（第 258 行） | info/error | `执行结束 status=failed reason=...` |
| setup 异常路径（第 207 行） | error | `执行初始化失败` |

### 3.4 失败告警写入点

**统一在最终落库成功后写**（避免每次 attempt 都写）：

1. **正常路径**：第 257 行 `session.commit()` 之后、第 258 行 `session.refresh(row)` 之后，若 `row.status == "failed"`：
   - 根据 `row.error` 判断 reason 分类：
     - 含 "WORKFLOW_TIMEOUT" → `timeout`
     - 含 "创建者已失效" → `owner_invalid`
     - 含 "WORKFLOW_TENANT_UNAVAILABLE" → `tenant_unavailable`
     - 含 "已达到重试上限" → `retry_exhausted`
     - 含 "WORKFLOW_CANCELLED" → `cancelled`
     - 其他 → `bridge_error`
   - 写一条 `WorkflowExecutionAlert`（含 trace_id），同 session commit。
   - **幂等**：因为一次 execute 调用只落一次最终状态，天然只写一条告警。重复触发 = 新的执行 = 新的 execution_id = 新的告警（语义正确，不是「同一次执行重复告警」）。

2. **setup 异常路径**：第 207 行 commit 之后，若执行行被置 failed，写一条 reason=`setup_error` 的告警。

## 7. 风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| 日志写入拖慢主执行 | L1 | 日志是同步 DB 写入，但只在关键节点（开始/尝试/结束）写，每次几条；不打 debug 日志；异常吞掉不影响主流程 |
| 告警写入失败导致主事务回滚 | L1 | 告警在最终 commit 成功后再写；若告警写入异常，单独 rollback + log，不回滚已成功的执行状态 |
| 与 FLOW-005 告警混淆 | L1 | 表名/字段/语义独立；测试中分别计数 |
| 全量 pytest 基线失败（WinError 5） | 环境 | 用全新 `--basetemp` 跑 |
