## 2. 分项方案

### 2.1 M1 BM25 全 0 时稀疏路不进 RRF，并记诊断

**原因。** 全 0 表示查询词项与当前候选没有重合。`hybrid_search` 把 `range(len(valid))` 当成稀疏排名送进 RRF，载入顺序会改写稠密排序。全 0 不全是分词器切分太粗：查询切不出词、候选正文切不出词、词面确实不重合，都会得到全 0。含词分块若已因租户、版本或向量维度被排除，也不会进入这次打分。

**行为。** `app/rag/vectorstore/local.py` 中，BM25 存在大于 0 的分数时保持现在的 `argsort`。全 0 时 `sparse_order = []`，`_rrf` 只保留稠密路。

**诊断。** 全 0 时打一条 `logger.info`，事件名固定为 `bm25_all_zero`，便于检索。级别用 info，不用 error 或 warning。字段只包括：

| 字段 | 含义 |
|---|---|
| `tenant_id` | 本次检索租户 |
| `candidate_count` | 进入 BM25 的候选数 |
| `query_token_count` | 查询词项个数 |
| `empty_doc_count` | 词项列表为空的候选数 |
| `reason` | 下表三者之一 |

原因码按这个顺序判定，只记一个：

| `reason` | 条件 |
|---|---|
| `empty_query_tokens` | 查询词项为空 |
| `empty_doc_tokens` | 查询有词项，且每个候选的词项都为空 |
| `no_overlap` | 查询和候选都有词项，但没有任何词项重合 |

日志不写查询原文、分块正文、词项列表、文档标识。`no_overlap` 同时覆盖真实词面未命中和入库/查询分词器不一致，本阶段不再拆开。这条日志用于事后统计全 0 的频率和原因，不进入 Reflect / Distill。

**测试。** 在 `tests/test_rag.py` 先写失败用例：构造 BM25 全 0 的候选，断言融合顺序等于稠密顺序；再覆盖三条原因码，断言日志字段不含正文。有正分时的排序保持现有断言。

**验收。** 全 0 不再扰动稠密排序。诊断可按 `reason` 统计。不宣称检索质量提升，不重跑官方基线。

### 2.2 M2 生效日期打开后的全量载入只作记录

**原因。** 版本是否可见由 `document_version_status` 在 Python 中计算。Flag 关闭时 SQL 用 `is_current` 收窄；打开后查询不再加该条件，租户分块全部载入，再按文档 `session.get`（有 `doc_cache`）。

**企业里版本不能只有当前/非当前。** 常见状态是草稿、待生效、已发布、已替换、已归档。成员只看已发布。待生效对应现在的预告版本，已替换对应被新版本顶掉的历史版。生效日期开关要表达的是这些状态里“此刻哪一版可被检索”，不是把 `is_current` 从 SQL 里拿掉之后在内存里再滤一遍。

**检索面和控制面不能共用一个 `is_current` 判断。** 对话检索是数据面，只命中本租户已发布的当前版本。管理列表是控制面，管理员要能按状态看到历史版本、预告版本和已替换版本，否则无权可清。M2 现在的实现把这两件事压在同一个 Flag 上：Flag 关闭时大家只能看见当前版；Flag 打开时检索为了识别待生效，把租户全部分块载入。控制面需要的“按状态查看”因此没有单独的查询，检索面也没有保持窄查询。

**做法。** 本项不改 `local.py` 查询，也不在本项实现上述状态机。在 `docs/adr/0002-official-vectorstore.md` 性能节写明三件事：`RAG_EFFECTIVE_DATE_FILTER=true` 时 Local 按租户全量载入再逐文档过滤；默认 `false`；在控制面能按状态查询、检索面仍只查已发布当前版之前，不得为了生效日期把检索改成全量载入。生产打开该 Flag 前须另立性能项。不把日期谓词下推到 SQL，也不改 Milvus。状态机本身放在第 3 节阶段 4。

**验收。** ADR 写清全量载入的限制、默认值、两条路径不能共用 `is_current`，以及“本阶段不改代码”。

### 2.3 L2 收紧成员，放宽两类管理员

原选项 A、B 均不采用。A 把管理员和非当前版本一起拒绝，管理员清不掉历史脏数据。B 保留成员对历史版本的写侧门。

**现状。** `Role.SYSTEM_ADMIN` 的定义是平台超级管理员、跨租户。知识库判定却先要求 `same_tenant`，管理员写路径再要求 `is_current`。租户是平的，没有上下级租户。因此“租户管理员管理下面的租户”在本系统中就是管理自己所属的那一个租户。ADR-0001 写的是全员禁止跨租户、管理员只能写同租户当前文档；本项按产品决定修订该 ADR，不扩大到用户、审计或其他资源。

**两条路径。** 企业里对话检索和管理列表是两条路。对话检索是数据面，只命中本租户已发布的当前版本。管理列表是控制面，管理员要能按状态看到历史版本、预告版本和已替换版本，否则无权可清。这两条不能共用一个 `is_current` 判断。成员在控制面只看已发布、且是自己上传的当前版本。版本状态的完整集合（草稿、待生效、已发布、已替换、已归档）与第 2.2 节相同，实现放在阶段 4；阶段 2 先用现有的当前版 / 历史版把两条路径拆开。

**成员。** 列表、详情、删除、重解析都只允许自己上传的当前版本。历史版本在这四条上都拒绝。

**租户管理员。** 管理本租户全部知识库文档，包括历史版本、预告版本和已替换版本的列表、详情、删除和重解析。不能跨租户。

**系统管理员。** 可对任意租户的知识库文档做上述控制面操作，包括历史版本，用于清理脏数据。跨租户是破玻璃操作：允许，但要留下操作者、租户、文档、动作和时间。没有审计的超级权限，脏数据清掉了，责任也跟着丢。复用现有 `audit_event`，不新建审计系统。本项不改用户、审计产品和其他资源的跨租户权限。

**重解析与发布分开。** 重解析是对某一版重新切块建索引，不自动把它变成新的当前版，也不修改同组其他版的 `is_current`。把某一历史版重新发布才是另一步：先在同一版本组里取消现有当前版，再把目标版标为当前，并且这两步要在同一事务里一起成功。现有重解析在内容变化时会新建一个 `is_current=true`，企业里这会被当成误发布。阶段 2 先堵住误发布。显式的发布接口放在阶段 4，本阶段不做。

**单一当前版是数据约束。** 同一版本组同时只能有一个当前版。权限放宽之后，只靠调用方记得“先把旧的标掉”，仍会留下双当前版。阶段 2 在写入路径上保证同一 `version_group_id` 最多一个 `is_current=true`，不只在接口里做判断。

**删除分两档。** 成员不能删历史版。租户管理员在本租户内可以归档或删除；系统管理员可以跨租户删除。商业系统对管理员删除多用软删除加保留期，而不是立刻物理抹掉，以便审计和恢复。阶段 2 先做权限和最小审计（谁在何时对哪个租户的哪份文档做了删除或重解析）。软删除和保留期放在阶段 3。工单或二次审批放在阶段 4，不挡这次收口。

**范围。** 停在知识库的列表、详情、删除、重解析，以及同一版本组只有一个当前版这条约束。对话检索维持只命中本租户当前版。

**测试。** 成员不能读、删、重解析非当前版本，也不能操作他人文档。租户管理员可管理本租户历史版本，且跨租户失败。系统管理员可跨租户删除和重解析历史版本，并产生审计记录。重解析历史版本后，原当前版仍是唯一当前版。对话检索不命中历史版本和他租户。

### 2.4 L3 单次评测恢复融合常数

**原因。** `apply_rrf_k` 改的是进程内 `settings.RAG_HYBRID_RRF_K`。`run_sweep` 在同一进程里切换多个 k，所以 `finally` 会恢复。单次路径把进程退出当成清理，`finally` 只关闭索引。脚本头“待完善”已记录这一点。同进程内后续代码仍会看到被改过的值。

**做法。** `scripts/run_rag_baseline.py` 的单次路径在进入前保存 k，在现有 `finally` 中写回。`run_sweep` 的恢复逻辑不动。删掉文件头“待完善”里“单次覆盖后不自动改回”这一条，其余待完善项保留。

**测试。** `tests/eval/test_rrf_k_experiment.py` 已有 `test_apply_rrf_k_can_be_restored`，它只证明调用方自己能改回。新增用例调用单次路径的恢复边界（或抽出的保存/恢复函数），断言函数返回后 `RAG_HYBRID_RRF_K` 等于进入前的值。不跑官方评测。

**验收。** 单次运行结束后进程内融合常数与进入前一致。

### 2.5 N1 写明工具名拒绝的真实边界

**原因。** `reject_untrusted_tool_call` 要拦的是检索正文点名、用户原文没提的工具。上下文是一整段拼接文本，实现用 `[UNTRUSTED_SOURCE]` 当开关，再对整段 `context` 做子串匹配。记忆和之后追加的 critique 也参与匹配。模型凭空造出、且整段 context 中不存在的工具名不会被拒绝。

**做法。** 不改拒绝条件。在 `docs/AI辅助开发迭代指导.md` 已有围栏条目旁写上上述边界，并写明这不是通用工具白名单，也不是只在围栏内部查找。`app/rag/context_merge.py` 的函数说明与该行为对齐。

**验收。** 文档与 `context_merge.py` 第 30–37 行一致。现有拒工具测试仍通过，不新增行为。

### 2.6 N2 写明 critique 不在 RAG 字符预算内

**原因。** `_trim` 只在 `merge_memory_and_rag` 截断记忆和检索正文。QualityGate 在合并之后把 `critique` 拼进 `state.context` 并重跑行动，没有第二次按 `RAG_CONTEXT_CHARS` 截断。检索正文仍在围栏内。轮数由 `AGENT_MAX_REVISIONS` 封顶。

**做法。** 不把 critique 纳入 `_trim`，不改 `app/agents/pipeline.py` 的拼接。在同一份迭代指导中写明：critique 追加发生在预算截断之后，长度随自纠错轮数增长，上限是配置的轮数。

**验收。** 文档记录预算边界。管线行为不变。

在阶段 2 的权限之上，把管理员删除从立刻物理删除改为软删除。成员的删除范围不变，仍只能删自己的当前版本；软删除后的文档对成员和对话检索都不可见。

| 顺序 | 内容 | 完成标准 |
|---|---|---|
| 1 | 文档增加删除标记与删除时间，列表默认不展示已软删文档；管理员可查看并确认 | 成员与检索都看不到已软删文档 |
| 2 | 保留期届满后的物理清理单独做，并再次审计 | 未到保留期不物理删除；清理记录可追溯 |

保留期的具体天数在实施该阶段前写入 ADR，不在本文件先定一个天数。

### 阶段 4：后续，不在本次分支实施

- 系统管理员跨租户操作的工单或二次审批。阶段 2 只要求审计，不要求审批流。
- 显式的“发布历史版为当前版”接口。
