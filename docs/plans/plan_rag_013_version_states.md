# RAG-013：版本状态机、跨租户二次确认与发布历史版

> 状态：已实现（RAG-013 `done`）
> 分支：`feat/rag-013-version-states`
> 来源：交付排期 A3；评审修复方案阶段 4
> 日期：2026-09-25
> 截止：2026-10-23

文档增加版本状态。把某一历史版重新定为当前版必须显式发布，并在同一事务里取消同组旧的当前版。系统管理员跨租户删除、重解析、发布前要有一条可查询的确认记录。检索仍只命中未删除的当前版。

## 目标

1. 状态：草稿、待生效、已发布、已替换、已归档。
2. 显式发布历史版，同一事务内只留一个当前版。
3. 跨租户删除、重解析、发布的二次确认，确认记录可查。
4. 前端可按状态筛选，并可发布。

## 非目标

不做生效日期全量载入的性能优化；不打开检索侧的生效日期开关；不做完整工单；不提供恢复已软删文档的接口；不改默认向量库。

## 验收

发布后同组仅一个当前版；无二次确认则拒绝跨租户敏感操作；前端可筛选与发布；相关 pytest 通过。

## 风险与回滚

L2。回滚状态字段、发布接口和确认表。检索继续只认未删除的当前版。

## 实现方案

先写会失败的发布与确认测试，再改状态、发布和列表筛选。角色矩阵不变：成员仍只能操作自己的未删当前版；租户管理员管本租户；系统管理员可跨租户。已软删文档不能发布、归档或重解析。

代码注释只描述当前行为，不写任务编号、文档编号、文档名称或修订日期。

### 1. 版本状态

`rag_documents` 增加 `version_state`。取值只有：

| 状态 | 含义 | `is_current` |
|---|---|---|
| `draft` | 草稿，未发布 | false |
| `scheduled` | 待生效，记着未来的 `effective_at`，还不是发布指针 | false |
| `published` | 已发布，该版本组的当前版 | true |
| `replaced` | 曾是当前版，被新的发布顶掉 | false |
| `archived` | 已归档，退出当前版 | false |

`is_current` 继续表示发布指针。检索条件不改成按状态全表扫描，仍是未删除且 `is_current=true`。生效日期开关保持关闭。

已有行：当前版标 `published`，其余标 `replaced`。不把历史行猜成草稿。Alembic 修订挂在 `e7c3a9d1b584` 之后。现有开发库若被直接标到最新版本而没有跑加列，实施时把 `version_state` 补进 `app/core/migration.py` 的列补齐，并把该文件加入本任务允许路径。

新上传默认仍是 `published` 且为当前版，避免现有检索测试被改成草稿。只有显式传入 `draft` 时才写成草稿且 `is_current=false`。

进入各状态的入口：

- 草稿：上传或摄取时指定。
- 待生效：`POST /documents/{id}/schedule`，写入未来的 `effective_at`，`is_current=false`。不因为日期到了就自动发布。
- 已发布：`POST /documents/{id}/publish`。
- 已替换：只由发布时顶掉同组旧当前版写入，不单独做接口。
- 已归档：`POST /documents/{id}/archive`。若它正是当前版，同一事务里把 `is_current` 改为 false。

归档不是软删除。`deleted_at` 仍只表示软删除。

### 2. 发布

`POST /documents/{id}/publish` 使用现有控制面权限。已软删或已归档返回 404。目标已经是当前发布版时直接成功，不另插一行。

否则在同一事务内：

1. 把同 `version_group_id` 里其他 `is_current=true` 的行改为 false，并把状态写成 `replaced`。
2. 把目标行写成 `is_current=true`、`version_state=published`。
3. 再提交。

这样部分唯一索引仍然只允许一个当前版。发布失败则整笔回滚。

成员看不到历史版，因此不能发布别人的文档，也不能发布自己已替换的历史版。租户管理员可发布本租户未删、未归档的版本。系统管理员跨租户发布必须带确认记录。

### 3. 二次确认

只约束系统管理员，且文档租户与操作者租户不同的删除、重解析、发布。同租户操作不需要确认。不建工单、不设审批人、不设多级流程。

新增确认表，一行就是一条记录：操作者、文档租户、文档、动作（`delete` / `reparse` / `publish`）、创建时间、消费时间。

1. `POST /operation-confirmations` 创建记录并返回编号。
2. 跨租户删除、重解析、发布必须带上这个编号。缺编号、编号不属于该操作者、文档或动作不一致、或已经消费过，一律拒绝，且不改文档。
3. 操作成功时在同一事务里写下消费时间。
4. 系统管理员可以用 `GET /operation-confirmations` 查自己的记录。不另做工单页面。

### 4. 列表与检索

`GET /documents` 增加 `version_state`。只有租户管理员和系统管理员使用它；成员传入也忽略，列表仍是自己的未删当前版。默认列表行为与现在相同。

`DocumentOut` 增加 `version_state`。详情沿用控制面权限：管理员能看到各状态；成员只能看到自己的未删当前版。

对话检索不读 `version_state`，继续排除已软删，并只取当前版。

### 5. 前端

知识库列表对租户管理员和系统管理员增加状态筛选，请求里带 `version_state`。行上徽章显示草稿、待生效、已发布、已替换、已归档；已软删仍显示「已删除」。

未删除且状态为草稿、待生效或已替换时，管理员看到「发布」。文档租户与当前用户租户不同时，发布和删除先创建确认记录，再带编号调用原接口。页面上没有重解析按钮，但重解析接口同样要求确认。

不增加恢复已软删文档的按钮。

### 6. 文档

权限 ADR 补一句：发布历史版是显式动作；跨租户删除、重解析、发布需要一次性确认记录。角色矩阵和软删除保留期不改。

生效日期 ADR 补一句：控制面用版本状态表达待生效；检索默认仍只认当前发布指针。不在本任务打开生效日期开关，也不改全量载入。

### 7. 实施顺序

1. 发布事务、缺少确认则拒绝、成员筛选被忽略的失败测试。
2. 加 `version_state` 与确认表，现有行按当前版 / 非当前版回填。
3. 实现发布、归档、待生效，以及跨租户确认校验。
4. 列表筛选与响应字段。
5. 前端筛选、徽章、发布和跨租户确认。
6. 更新两份 ADR 的对应句子。
