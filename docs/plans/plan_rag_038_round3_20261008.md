# RAG-038 第三轮整改：关闭独立复审三阻断项

日期：2026-10-08。分支 `rag-batch-20261007`。本卡 RAG-038 已两轮整改并实现
（见 [实现说明](implementation_rag_038_retrieval_deadline.md)），144 项测试通过；
2026-10-08 独立复审（[复审报告](../reviews/2026-10-08-RAG-038时限重试取消复审.md)）
判定「阻断关闭」，剩 3 项。本计划只修这 3 项，不扩大范围。

## 目标

让 RAG-038 达到关闭条件：同步本地查询可被调用方限时等待且迟到结果不伪装空知识；
零退避配置的判据/运行/日志/文档一致；嵌入成本 usage 可观测。

## 现状（复审复现，不是推断）

- **P1（阻断）**：`app/rag/vectorstore/local.py` 的 `hybrid_search` 是 `async def`，
  但方法体全是同步 SQLModel 查询、numpy、BM25，没有任何 `await`，整个跑在事件循环
  线程上。`native.retrieve` 外层的 `asyncio.wait_for(deadline.remaining())` 定时器
  无法在同步阻塞期间触发；查询跑完后 native 也不再检查预算，结果直接返回。
  复审探针实测：deadline=20ms，本地查询注入 150ms sleep，实际等了 141ms，且把超时
  结果收敛成 `no_hit`——把故障伪装成「查过了、没有」。
- **P3**：`BACKOFF_BASE=BACKOFF_MAX=0`、`deadline=1`、`MAX_ATTEMPTS=3` 时，
  配置判据 `retrieval_retry_effectively_disabled` 返回 False（认为重试有效），但
  `retry_async` 里 `wait=0` 命中 `wait <= 0 → give_up_budget`，实际只打一次。
  判据与运行不一致。
- **成本**：`openai_compatible._post_batch` 只取 `resp.json()["data"]`，丢弃
  `["usage"]`；attempt 数与延迟换算不出 token/费用，也没有显式 unknown 标注。

## 方案

### P1a 让同步本地检索可被限时等待

把 `LocalVectorStore.hybrid_search` 的**整个同步方法体**抽成同步私有方法
`_hybrid_search_sync(...)`，async 入口改为
`await asyncio.to_thread(self._hybrid_search_sync, ...)`。

- `app/core/database.py` 已对 SQLite 设 `check_same_thread=False`；一次检索内该
  request-scoped `Session` 只在 `to_thread` 工作线程内被触碰，事件循环在 await
  期间不并发使用它，因此线程安全成立；权限过滤（tenant/read_scope/index_id）逻辑
  原样保留，只是挪到线程里执行。
- 这样 `native.retrieve` 的 `asyncio.wait_for` 才能真正在 deadline 到期时让协程
  放弃等待。与 `run_blocking_with_deadline` 同一边界：线程里的底层调用无法被真正
  中断，「有界」是「调用方不再等」，超时按 `DeadlineExceededError` 上抛，不写空结果。

### P1b 拒绝迟到结果（不伪装 no_hit）

`native._retrieve` 在 `await self._store.hybrid_search(...)` 返回后、在
`drop_injected_chunks` 之前，若 `current_deadline()` 已 expired，抛
`DeadlineExceededError` 而不是把迟到 hits 往上送。与 to_thread 双保险：
to_thread 让等待有界，这里兜住「恰好在 deadline 后返回的结果」不被当成正常命中。

### P3 零退避语义与判据对齐

采用「支持零等待立即重试」（而非拒绝该配置）：

- `retry_async`：`wait <= 0` 时视为「无退避等待」，`outcome="retry"`，照常重试，
  只 `await sleeper(0)` 让出一次事件循环；不再因为 `wait<=0` 判 `give_up_budget`。
  保留 `wait >= deadline.remaining()` 才放弃等待。
- 判据 `retrieval_retry_effectively_disabled`：`base<=0` 表示退避为零、重试立即
  发生，不属于「实际禁用」；现有公式 `first_wait_upper = min(base,max)*(1+jitter)`
  在 base=0 时得 0，`0 >= deadline` 为 False，本就返回 False——与运行修正后一致，
  无需改公式；只补注释说明 base<=0 是「零退避立即重试」而非禁用。
- 同步文档：resilience.py docstring、`.env.example`、README 的相关措辞。

### 成本/usage 追踪

`_post_batch` 解析响应时保留 `usage`（`prompt_tokens`/`total_tokens`，缺省记
`unknown`），在成功事件里带上 `usage_prompt_tokens` / `usage_total_tokens`
（缺失记 -1）。日志仍严禁 api key、请求正文、命中正文。Mock/无 usage 字段的兼容
provider 不报错，按 unknown 记录。

## 非目标

- 不自动降级 BM25；不引入新队列依赖；不改 RRF k、切分、Embedding 模型。
- 不动 `app/services/`、`app/agents/`、`app/models/`（SSE reason 等越界项不碰）。
- 不改 pymilvus 无法真正中断线程的既有边界（已在实现说明 §2.5 记录）。
- 不重建真实索引、不调用真实计费模型。

## 验收

1. 同步本地慢查询（to_thread 内注入 sleep）在 deadline 到点时被 `wait_for` 截断，
   抛 `DeadlineExceededError`/`unavailable`，**不**返回 no_hit；实测等待 ≤ deadline+容差。
2. 迟到结果：store 在 deadline 耗尽后才返回 hits，native 抛 `DeadlineExceededError`。
3. 零退避（base=0,max=0,attempts=3）配置下，可重试故障实际重试到 attempts 上限，
   不出现 `give_up_budget`；判据与运行一致，有专门用例。
4. 嵌入成功日志携带 usage 字段（MockTransport 响应里带 usage 时可断言）；
   无 usage 字段时记 unknown 不报错。
5. 既有 144 项回归不破坏；`pytest tests/ -k "rag or chunk or context or embedding"`、
   `ruff check app/rag/`、`mypy app/rag/` 实际运行通过（用 conda 解释器与隔离 SQLite）。
