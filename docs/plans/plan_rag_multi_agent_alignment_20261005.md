## 3. 需要用户裁决的事项与建议

### 3.1 权限语义

ADR-0001 最新矩阵将 uploader 定义为成员列表回滚开关，检索/Agent 继续同租户共享；RAG-026 却要求 uploader 模式同租户 A/B 检索隔离。不能将其当作普通漏传 user_id 修复。

建议：批准 uploader 作为可选检索隔离开关，tenant 默认不变，并修订权限 ADR；否则修订 RAG-026 验收以遵守现有 ADR。该决定影响 019/027/030。

RAG-027 建议新增受控只读引用核验语义：只返回当前、有权限、未删除的原文证据；不扩大管理权限。能检索某段不等于能下载整个源文件，完整下载的受众必须单独明确。

### 3.2 结构、预算与超长内容

[ADR-0005](../adr/0005-rag-adaptive-chunking-context-budget.md) 仍为 Proposed，批准人/日期未填写；批准设计落盘和任务拆分不能推定架构 Accepted。

建议接受分阶段架构：结构规则优先、父内切子、准确源范围、纯 Context Builder、每次实际 payload 的预算校验；可选 LLM 边界建议与章节摘要默认关闭。该批准不包含真实索引重建、生产迁移或未授权供应商外发。

建议超长行为：chunk size 是软目标；未超过经验证 Embedding 硬限的代码/盒图整体保留；表格按完整行切并带表头；无法安全拆分的盒图/超长行标记 oversized、保留原文并说明不向量化原因。需要明确接受“部分内容待处理”的业务结果，不能静默切坏或伪称完整入库。

模型能力建议按 provider/model/deployment 版本化配置；未知模型没有批准的能力配置时拒绝调用。具体 token 计数、估算余量和数值在单卡计划中提出，不凭空设置质量指标。

### 3.3 无知识、低分与故障

RAG-037 建议知识问答模式下 no_hit/below_threshold 明确证据不足，不作知识断言；unavailable 明确服务故障，不伪装成无资料。需决定普通聊天是否允许带显式标注的通用回答。同步、流式保持同契约，不自动补低分结果。

### 3.4 模型、样本、质量与费用

017/031/035/036/040 的真实模型验证需要授权模型、样本与调用上限，以及可复现基线后提出的质量门槛。建议优先现有已授权供应商和公开/脱敏样本；不读取密钥、不把配置存在当作文档外发授权。033 的本地确定性样本和 034 的已有审核链可先核查；缺证据时只列缺项，不要求重审全部数据、不自动升级 Gold。

### 3.5 索引迁移

032→015→036 建议采用完整索引身份、新索引准备与验证、显式切换、保留旧索引回退。同维不同模型禁止混用。沿用已批准 Milvus metric，不重复选型。临时库/测试 collection 的故障验证与真实知识库重建分开，后者需明确授权。

## 4. 执行模式与候选顺序

主 Agent：单卡计划落盘、明确目标/非目标/验收/回滚/文件归属；核对 allowed_paths 与依赖；整合、最终验证、文档和任务状态、提交。

实现子 Agent：仅在范围可拆时使用两个；按文件划分互不重叠的业务实现和独立测试范围。不能两个 Agent 同时修改 service.py/任务卡；共享文件由主 Agent维护。小卡仅一个实现 Agent，避免为并行强拆任务。

第三个只读子 Agent：整合和验证后重新阅读最终 diff、规则及实际代码，给出独立审查；审查写入 docs/reviews。审查发现由主 Agent 分配修复并再次验证，不以实现者自评代替。

一次只推进一张卡，多 Agent 用于同卡协作，不同时推进多张卡。人工验收提供固定步骤、预期结果、机器证据和剩余需用户判断的业务结果；已有用户验收不重复询问。未实际验证不得标通过。
