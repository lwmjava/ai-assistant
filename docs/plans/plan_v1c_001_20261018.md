## 目标、事实和前置

目标：已确定不检索的执行路径不创建 Embedding、VectorStore 或 RAG backend；真实检索保留索引身份、租户/读域、来源和 no_hit/below_threshold/unavailable 区分。

当前事实：ChatService.chat 与 chat_stream 在 _fast_route 和管线 preflight 前调用 _build_retriever；该方法实例化 RAGService，而 RAGService.__init__ 已创建 Embedding、VectorStore 和 backend。RAG-044 将索引核验延至 retrieve，但没有延迟这些工厂。默认 self 全管线仍按现有策略尝试 RAG，preflight 短路不检索；langgraph 的 simple/tools 短路径不使用检索器，RAG 路径与 Supervisor 保持原检索行为。prepared attachments/resume 会禁止 fast 路由，仍进入原管线，不新增基于关键词的跳过策略。

前置 RAG-044：原卡 done，10-18 页面报告及 CI 绑定业务提交 673787f；当前 app/rag/service.py 和 tests/test_rag_index_init.py 与原 index-init-inputs 指纹匹配。旧实现说明中的 in_review/全量失败是历史候选结论，不据此假定当前回归失败。开工专项 60 项通过，含 legacy-index unavailable、空库 no_hit、父块与状态回归。独立工程准入另行复核，不能仅凭 done 进入本卡。

## 方案比较与推荐

1. **推荐：Service 层请求内惰性 Retriever 钩子。** ChatService 创建轻量钩子，真正调用 retrieve 时才以原 session/user 创建原 RAGService 和 HybridRetriever；初始化错误进入受控 unavailable 分支，未检索时元数据读取不触发构造。覆盖 fast、self preflight、stream、resume、regenerate，保持既有路由/默认检索策略。
2. 仅把 _fast_route 提前并在 simple/tools 时不调用 _build_retriever：改动少，但默认 self 的 preflight 短路仍被初始化故障阻断，不满足整卡。
3. 将 RAGService 全部依赖改成惰性属性：影响摄取、管理、重建及 API 错误时序，超出对话层需求，当前不采用。

架构决定见 Proposed ADR-0013；批准前不实施。

## 实施设计

- 在 app/services/chat_retrieval.py 增加仅对话使用的 request-scoped 钩子，由 ChatService 注入构造闭包，闭包复用原 RAGService(session, user.tenant_id, reader=user).make_retriever()。不将 Session、主体或检索器放全局缓存，不改 RAGService 摄取/管理生命周期。
- 钩子有明确未尝试/已成功/初始化失败状态。同请求首次真实 retrieve 时至多构建一次；初始化失败本轮不自动重建或增加重试。后续新请求可独立重试。成功后沿用真实 HybridRetriever 行为和缓存。
- last_hits、last_selected、last_status、last_outcome 的读取及 last_selected 写入是元数据访问，不触发工厂。真实 retrieve 后透传对应命中和终态；上下文选块后以 last_selected 输出来源，绝不退回 last_hits 夸大来源。
- 仅普通依赖构造故障转为 unavailable，清空命中和选块，错误仅保留受控类型，不记录原文/堆栈/凭据。取消直接传播，不转失败或 no_hit。
- **身份拒绝的具体落点**：在 ChatService 建立惰性钩子之前，同步校验 reader/read_scope 与 tenant 绑定并固定本轮主体/读域快照；这一步在三条 retrieve 消费者的异常捕获边界之外，不创建provider/store/backend。原API身份依赖、会话权限、ActiveRun逐事件复核、regenerate前后复核位置保持；guarded_chat 仅是执行互斥，不是身份校验。延迟的factory只处理已验证快照的依赖构造，不把新的权限校验放入会被外层 broad except Exception 吞掉的 retrieve 内。不得声称“proxy重抛权限异常”就能穿透现有pipeline/fast/Supervisor异常处理。
- 本卡不新增普通非流式对话的全程撤权策略；撤权/停用反例覆盖既有API拒绝、ActiveRun和重新生成的保障。若实现发现必须在 retrieve 内引入新的身份拒绝，先修订 ADR/范围及三消费者错误传播方案，不以 unavailable 代替必要拒绝。
- default self full 仍尝试检索，不能通过遇到故障后假装“已判定不检索”来达标。full 检索构造失败仍明确披露 unavailable；RAG_DISABLED 仍返回 None，不创建钩子或依赖。
- 不改 API/SSE schema、前端、工具执行器、技能接线、数据库表、供应商、配置默认值或检索算法。父块受控展开仍来自原 RAGService，保留 tenant/uploader、当前索引、生效版本、注入剔除和来源预算契约。
