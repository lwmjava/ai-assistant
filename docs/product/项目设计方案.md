### 1.1 两个项目的边界

| 维度 | 当前项目 (personal-ai-assistant) | 开源项目 (ai-assistant) |
|------|--------------------------------|------------------------|
| **角色** | 新技术实验场 / 功能开发 | 商业化平台 / 社区展示 |
| **代码风格** | 保留完整变更历史注释 | 仅保留功能说明，清理 ~300+ 变更标记 |
| **向量库** | Chroma（轻量嵌入式） | Milvus（生产级分布式） |
| **世代迁移** | 保留 dual_write.py | 丢弃（开源版从 v2 schema 起步） |
| **垂直业务** | 保留 coding/pm/interview/lab | 不迁移（开源版专注通用 Agent） |
| **社区** | 无 | GitHub 开源，接收 PR/Issue |
| **商业化** | 无 | 企业销售 / SaaS / 副业招商 |
| **共享核心** | LangGraph 五阶段 + 高级 RAG + 安全治理 + 多租户 | 同左（重构清理后） |

### 1.2 产品定位

开源项目 **不是** CowAgent 的复制品，而是 **"工程化加强版 Agent 框架"**：

- **比 CowAgent 强**：Agent 推理管线（五阶段 vs 简单工具循环）、RAG 检索质量（混合检索 + 4 种重排 vs 自动策展）、安全治理（6 层 vs 基础门控）、代码沙箱（四层防护 vs 直接执行）、多租户
- **向 CowAgent 学习**：多渠道接入（Channel 抽象层）、部署体验（Docker + CLI + 一键脚本）、自我进化（Reflect → Skill 改进 + 记忆蒸馏）

---

### 1.3 双轨持续同步机制（迁移完成后生效）

**基线方向**：ai-assistant（开源版）为共享核心的唯一上游基线；personal-ai-assistant 的共享核心模块（五阶段管线、RAG、安全治理、多租户）跟随 ai-assistant 的 release tag 对齐。

**流向一：实验场 → 开源版（功能毕业）**
1. 新功能先在 personal-ai-assistant 实验验证；
2. 稳定运行 ≥2 个迭代后，撰写《功能毕业评估》（复用 §3.2 迁移评估模板）；
3. 通过后按开源版代码规范清理（注释清理规则见第六章），以 PR 进入 ai-assistant；
4. 垂直业务模块（coding/pm/interview/lab）永不毕业（决策 D8）。

**流向二：开源版 → 实验场（缺陷回流）**
1. ai-assistant 的每个 `fix:` 提交在 Release Notes 中标注影响模块；
2. 属于共享核心模块的修复，一周内 cherry-pick 回 personal-ai-assistant；
3. personal-ai-assistant 侧不允许对共享核心做分叉修改——需要改动时走流向一流程。

**差异豁免清单**（允许双轨不一致的部分）：向量库后端（Chroma/Milvus）、世代迁移设施、垂直业务模块、历史注释风格。豁免清单之外的共享核心差异视为同步债务，每次发布前清零。

## 二、当前项目评估总结

### 2.1 架构亮点（保留）

| 亮点 | 核心文件 | 说明 |
|------|---------|------|
| LangGraph 五阶段管线 | `app/graphs/main_graph.py` | Preflight → Plan → Act → QualityGate → Finalize，含短路路径 |
| Supervisor 多 Agent 编排 | `app/graphs/supervisor.py` | 子 Agent 并行执行 + 审查纠错循环 |
| AgentState 状态设计 | `app/graphs/state.py` | ~30 个字段，add_messages reducer，拓扑专属扩展 |
| VectorStore ABC 抽象 | `app/rag/stores/base.py` | 9 个抽象方法，已预留多后端扩展 |
| RAG 检索增强 | `app/rag/port.py` | RetrieverPort + MultiKBRetriever + 异步并行检索 |
| 自适应切分 | `app/rag/adaptive_splitter.py` | 7 种文档画像，不同切分策略 |
| 混合检索 + 重排 | `app/rag/hybrid.py` + `reranker.py` | BM25 + 向量 RRF 融合，4 种重排策略 |
| 安全治理 | `app/security/` | 6 层：输入/输出/Prompt/文件/日志/限流 |
| 代码沙箱 | `app/tools/code_sandbox` | AST 白名单 + 进程隔离 + 资源限制 |
| ContextVar 依赖注入 | `app/streaming/adapter.py` | `set_graph_dependencies()` 在每次请求注入 |
| 三级配置系统 | `app/config_loader.py` | 环境变量 > YAML > 默认值 |
| 统一 Prompt 管理 | `app/prompts/registry.py` | PromptRegistry 集中组装 |
| 优雅关闭 | `app/lifespan.py` | draining 模式 + 活跃 Run 等待 |

### 2.2 关键缺陷（重构时修复）

**Critical（必须修复）**：
- Docker 部署链路完全断裂（Dockerfile / Dockerfile.unified / docker-compose 三处）
- 视频路径安全校验与配置不一致导致 403（该模块不在迁移范围，见 §2.3，开源版无需修复）

**High（优先修复）**：
- JWT 默认密钥放行（有日志告警与 health 暴露，但不阻断启动）
- Refresh Token 无法撤销
- Web 搜索工具绕过配置系统
- 前端 Prop Drilling（22 个 props）、双轨错误处理、无测试/Lint
- API 参数验证缺口

**Medium（迁移时修复）**：
- Chroma 写入锁字典无界增长（内存泄漏）
- 知识库缓存淘汰粗暴（clear 全清）
- 竞态条件（速率限制锁惰性初始化）
- 依赖版本不锁定（`>=` 导致不可重现构建）
- `.env.example` 缺少约 100 个环境变量（示例 67 个 vs 代码引用 158 个，Phase 0 需按此重新估时）
- 异常处理不完整（缺少 422 统一格式）
- `lifespan.py` 612 行违反单一职责

### 2.3 不迁移的部分

| 模块 | 原因 |
|------|------|
| `app/coding/` `app/pm/` `app/interview/` `app/lab/` | 垂直业务模块，开源版专注通用 Agent |
| `app/rag/dual_write.py` + `generation.py` | 世代迁移是内部演进产物，开源版从 v2 schema 起步 |
| `~300+` 变更历史注释 | S2/S4/W5-P1/H7/F13/P0 等标记，由 Git commit 承载 |
| `app/export/sft_exporter.py`（暂缓） | 量极小，最后阶段再迁移 |
| `app/media/`（视频生成等） | 非通用 Agent 能力，开源版不含媒体生成模块（对应缺陷"视频路径 403"随之不再适用） |
| `app/proposals/` + `routes_proposals.py` | Proposal 变更系统属内部实验性配置变更审批流，与开源产品通用 Agent 定位无关（若需类似能力由社区以 Admin 审批流另行设计） |

## 三、迁移阶段规划

### 3.1 阶段总览

```
Phase 0: 基座层（Foundation）
         ├── 配置系统 + 数据库 + LLM 路由 + Prompt 注册 + SSE 流式
         ├── 四层角色体系 + 统一权限层 + JWT 安全加固
         ├── Channel 抽象层（仅 Web）
         ├── Docker 可用 + CLI + .env.example 完整
         └── 可交付：最简对话（用户发消息 → LLM 流式回复）
             Tag: v0.1.0-foundation

Phase 1: Agent 模块
         ├── LangGraph 五阶段管线（Preflight → Plan → Act → QualityGate → Finalize）
         ├── AgentState 状态设计
         ├── Tool 注册系统 + 内置工具
         ├── Skill 系统
         ├── Supervisor 多 Agent 编排
         └── 可交付：完整 Agent 对话（工具调用 + 技能 + 多 Agent）
             Tag: v0.2.0-agent

Phase 2: RAG 模块
         ├── MilvusStore 实现（VectorStore ABC 新后端）
         ├── 文档加载 + 自适应切分 + 清洗链
         ├── 混合检索（BM25 + Milvus 向量 + RRF）
         ├── 重排序（4 种策略）
         ├── RetrieverPort + MultiKBRetriever
         ├── Parent Document Retrieval
         └── 可交付：知识库上传 + 检索增强对话
             Tag: v0.3.0-rag

Phase 3: 工作流（Workflow）
         ├── WorkflowEngine + WorkflowScheduler（cron 定时引擎）
         ├── RuntimeBridge（连接 LangGraph）
         ├── 自动化任务 CRUD + 执行历史
         └── 可交付：定时任务 + 自动化工作流
             Tag: v0.4.0-workflow

Phase 4: 记忆与进化
         ├── 对话记忆系统（窗口管理 + 压缩）
         ├── Reflect 异步反思 → Skill 改进闭环
         ├── 夜间记忆蒸馏（Evolution 调度器 + cron）
         └── 可交付：自我进化的 Agent
             Tag: v0.5.0-evolution

Phase 5: 管理后台 + SFT + 前端
         ├── 开源版基础 Admin Console（用户/租户/配额/审计查询/系统配置，边界见 PRD §3.2.1）
         ├── 用户端前端（React 重构，解决 Prop Drilling）
         ├── SFT 数据导出
         └── 可交付：完整可商用的开源产品
             Tag: v1.0.0
```

## 四、技术栈与工程基础设施

### 4.1 技术栈

| 层 | 技术选型 | 说明 |
|----|---------|------|
| **后端** | Python 3.11+ · FastAPI · LangGraph · LangChain | 与当前项目一致 |
| **向量库** | Milvus 2.4+ | 替换 Chroma，生产级分布式 |
| **关系库** | SQLite（开发）/ PostgreSQL（生产） | 与当前项目一致 |
| **前端** | React 18 + TypeScript + Vite | 与当前项目一致，重构架构 |
| **包管理** | uv + pyproject.toml | 依赖精确锁定（`==`），替代 `>=` |
| **Lint/Format** | ruff（lint + format 二合一） | 替代 flake8 + black + isort |
| **类型检查** | mypy strict | CI 中 `continue-on-error: false` |
| **测试** | pytest + pytest-asyncio | 覆盖率 ≥ 70% |
| **数据库迁移** | Alembic | schema 演进由迁移脚本承载，CLI migrate 封装 |
| **CI/CD** | GitHub Actions | lint → type-check → test → build |
| **容器** | Docker multi-stage build | 可用的 Dockerfile |
| **Commit 规范** | Conventional Commits | `feat:` / `fix:` / `refactor:`，自动 changelog |

CI 策略：
- 单元测试：mock VectorStore / LLM provider
- 集成测试：使用 Milvus Lite（嵌入式，pip 依赖）在 GitHub Actions 直接运行，无需 service 容器
- e2e：docker compose 起全栈，仅 release 前手动/夜间 workflow 运行

## 五、各模块重构设计

### 5.1 Phase 0 — 基座层

#### 5.1.1 配置系统

**保留**：三级配置（环境变量 > YAML > 默认值）的设计模式
**重构**：
- 消灭所有硬编码 URL / 模型名（修复 `web_search.py` 绕过配置系统的问题）

#### 5.1.3a Token 与角色变更语义

| 事件 | 生效方式 |
|------|---------|

#### 5.3.2 MilvusStore 实现

实现 `VectorStore` ABC 的 9 个抽象方法：

```python
class MilvusStore(VectorStore):
    """Milvus 向量存储后端。"""

    def __init__(self, kb_id: str, collection_name: str = None):
        self.kb_id = kb_id
        self.collection_name = collection_name or f"kb_{kb_id}"
        self.client = MilvusClient(uri=settings.MILVUS_URI)

    def upsert(self, ids, embeddings, documents, metadatas) -> None: ...
    def similarity_search(self, query, k=5, filter=None) -> list[Document]: ...
    def similarity_search_with_scores(self, query, k=5, filter=None) -> list[tuple]: ...
    def delete_by_doc(self, doc_id: str) -> None: ...
    def get_stats(self) -> dict[str, Any]: ...
    def count(self) -> int: ...
    def get_by_filter(self, where, limit=None, include=None) -> dict: ...
    def update_metadata(self, ids, metadatas) -> None: ...
    def get_all_documents(self) -> dict[str, Any]: ...
```

**工厂路由**：

```python
def get_vector_store(kb_id: str) -> VectorStore:
    backend = settings.VECTOR_STORE_BACKEND  # "milvus" | "milvus_lite"
    if backend == "milvus":
        return MilvusStore(kb_id, uri=settings.MILVUS_URI)
    if backend == "milvus_lite":
        return MilvusStore(kb_id, uri=settings.MILVUS_LITE_PATH)  # 嵌入式，本地文件
    raise ValueError(f"Unknown backend: {backend}")
```

配套：`.env.example` 开发默认 `VECTOR_STORE_BACKEND=milvus_lite`，生产 compose 用 `milvus`；§5.3.3"5 个文件直接引用 Chroma"修复方案不变（改走工厂）。

**Embedding 模型与维度策略**：

| 项 | 决策 |
|----|------|
| 默认模型 | `text-embedding-v3`（DashScope，1024 维），可配置 |
| 离线替代 | Ollama 本地模型（如 `bge-m3`），配置 `rag.embedding.provider: ollama` |
| 维度策略 | collection 创建时写入 `dim` 并与模型绑定；embedding 配置存于知识库元数据 |
| 变更模型 | 不允许原地切换；须新建 collection 并触发全量重建索引（复用索引状态机） |

MilvusStore collection schema 的 `vector` 字段维度取自 `rag.embedding.dimensions`；`get_stats()` 返回当前 embedding 模型名与维度，供管理后台校验一致性。

| `any` 类型滥用 | 全部替换为具体类型，`tsconfig` 开启 `noUnusedLocals` |
| 无测试 | 引入 Vitest + Testing Library |
| 无 ESLint/Prettier | 配置 ESLint + Prettier，pre-commit hook |
| 前端混合 | 路由分离：`/app/*`（用户端）vs `/admin/*`（管理后台） |

**前端迁移策略**：初期方案 A（单应用双路由），规模化后方案 B（双应用独立部署）。

## 六、代码规范

### 6.1 注释清理规则

| 标记类型 | 示例 | 处理方式 |
|---------|------|---------|
| 阶段标记 `S2:` / `S4:` | `"""S4: DualWriteRouter..."""` | 删除前缀，保留功能描述 |
| 版本标记 `v4.0` | `v4.0 升级要点（对比 v3.0）` | 删除版本对比块，改写为当前状态 |
| Wave/Phase `W5-P1` | `# ── W5-P1: Quota ──` | 删除编号，保留标题 |
| 热修 `H7` | `H7 修复：使用 Lua 脚本` | 删除编号，保留原因 |
| 功能编号 `F13` | `skip_rag: bool  # F13 不检索` | 删除编号，保留语义 |
| 优先级 `P0` | `P0 修复：新增 hydrate...` | 删除前缀，保留描述 |
| 拆分溯源 `H-1` | `从 supervisor.py 拆分（H-1）` | 整行删除 |

**保留原则**：
- ✅ 注释回答 **WHAT**（做什么）和 **WHY**（为什么这样设计）
- ❌ 删除 **WHEN**（何时添加）和 **WHAT CHANGED**（版本间差异）
- 变更历史由 **Git commit message** 承载，不进入代码
