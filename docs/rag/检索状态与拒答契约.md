# 检索状态与最终拒答契约（RAG-037）

状态：已实施（分支 `rag-batch-20261007`）
代码：`app/rag/retrieval_status.py`、`app/rag/retriever.py`、`app/agents/pipeline.py`、`app/agents/fast_path.py`、`app/api/routes/rag.py`
测试：`tests/test_rag_037_retrieval_status.py`（15 项）

## 1. 为什么要这份契约

改造前，检索只有「返回一段文本」这一个结果，三种异常路径没有任何统一约定：

| 路径 | 改造前表现 | 证据 |
|---|---|---|
| 检索故障（自研管线） | 异常冒到管线级兜底，请求整体失败 | 原 `app/agents/pipeline.py:417-424` 无异常处理 |
| 检索故障（短路径） | 异常被吞成空串，随后写「没有可用的检索结果」，模型直接用自身知识作答 | 原 `app/agents/fast_path.py:92-100` |
| 全低分 | 拒答语以**裸文本**返回，不带指令标记也不带围栏，模型可完全忽略 | 原 `app/rag/retriever.py:87-92` |
| 零命中 | 返回空串，短路径与管线措辞不一致 | 同上 |

共同问题：「没跑成」和「查过了、没有」在最终回复里**无法区分**，用户看到的都是模型照常作答。

## 2. 状态定义

`app/rag/retrieval_status.py` → `RetrievalStatus`

| 状态 | 含义 |
|---|---|
| `ok` | 有命中且至少一条通过阈值 |
| `no_hit` | 检索成功完成，但零候选 |
| `below_threshold` | 有候选，但全部低于 `RAG_MIN_SIMILARITY` |
| `unavailable` | 检索未完成（嵌入 / 向量库 / 后端异常） |

**判定顺序唯一**，由 `classify()` 实现并由 `test_classify_order_is_unique` 钉住：

1. 有异常 → `unavailable`（检索没跑完时，候选数与保留数都没有意义）
2. 零候选 → `no_hit`
3. 保留数为零 → `below_threshold`
4. 其余 → `ok`

## 3. 少返回策略

- **只减不补**：被阈值剔除的候选不回填、不重排（对齐 non_goals「不自动补位改变排名」）。
- 少返回时状态仍为 `ok`，剔除条数记在 `RetrievalOutcome.dropped_by_threshold`，`is_partial` 为真。
- 少返回**不产生**披露要求——它是正常检索结果，不是异常。
- 注入块剔除（`drop_injected_chunks`）与阈值剔除是两件事，计数分开，不混算。

## 4. 最终回复契约

披露分两层，**只有第二层是硬保证**：

**第一层（提示层，模型可不服从）**：非 `ok` 状态时把一句**指令**送进模型。指令走 system / 提示的指令段，**不加** `[UNTRUSTED_SOURCE]` 围栏——围栏是给不可信资料用的，指令不能被当成资料忽略。

| 状态 | 提示语来源 |
|---|---|
| `ok`（含少返回） | — |
| `no_hit` | `RAG_NO_HIT_NOTICE` |
| `below_threshold` | `RAG_REFUSE_MESSAGE` |
| `unavailable` | `RAG_UNAVAILABLE_NOTICE` |

**第二层（应用层，确定性）**：

| 状态 | 应用层动作 | 文案来源 |
|---|---|---|
| `ok`（含少返回） | 无 | — |
| `no_hit` | **前置**固定披露语，后接模型回答 | `RAG_NO_HIT_REPLY` |
| `below_threshold` | **终态短路**：回复就是拒答语本身，不进入后续生成 | `RAG_REFUSE_MESSAGE` |
| `unavailable` | **前置**固定披露语，后接模型回答 | `RAG_UNAVAILABLE_REPLY` |

- 拒答语本身就是面向用户的结论，交给模型改写只会把它变成一段看起来像知识回答的文字，故 `below_threshold` 不生成。
- `no_hit` / `unavailable` 不掐断对话：检索故障时把整个回答掐断是另一种极端，改为确定性标注后继续回答。
- 给模型的指令（`*_NOTICE`）与面向用户的前置文案（`*_REPLY`）**分开配置**：前者约束生成，后者保证「不冒充」不依赖模型服从。
- 总开关 `RAG_STATUS_NOTICE_ENABLED`（默认开）只控制**提示层 directive**。关闭后状态仍记录与暴露、终态拒答也关闭，但短路径的状态文案（「本次检索未完成」）不随之回退——它比旧文案更安全，所谓「完整回退旧行为」的说法不成立。
- 契约只规定「必须披露」，**不规定模型必须编出答案**，也不改变采样参数与生成长度（对齐 non_goals「不做无界兜底生成」）。

## 5. 入口 × 后端矩阵

| 入口 | 触发条件 | 后端 | 状态来源 | 异常时最终表现 |
|---|---|---|---|---|
| 同步对话（自研管线） | 非短路径 | native / langchain / llamaindex | `retriever.last_outcome` | 完成请求，行动与响应两阶段带披露指令 |
| 流式对话（自研管线） | 非短路径 | 同上 | 同上 | 流完整结束，同样带披露指令 |
| 短路径（RAG 路由） | `AGENT_ORCHESTRATION=langgraph` 且路由为 RAG | 同上 | 同上 | 用户块写「本次检索未完成」，system 带披露指令 |
| Preflight 短路 | 简单问题 | — | **不检索**，`retrieval_status` 为空 | 无披露（未检索 ≠ 检索失败） |
| Supervisor 子编排 | `AGENT_ORCHESTRATION=langgraph` 且路由为 MULTI | native / langchain / llamaindex | 图执行前统一检索一次，与自研管线共用同一套状态与披露 | 同自研管线 |
| `POST /api/rag/search` | 显式检索 | 请求级 `?backend=`，缺依赖时静默降级 native | 命中列表 + 响应头 | `503` + `X-Retrieval-Status: unavailable`，不降级为空列表 |

HTTP 检索面额外输出两个响应头：

- `X-Retrieval-Status`：成功时本端点不做相似度阈值过滤，因此只有 `ok` / `no_hit`；故障时标 `unavailable`。
- `X-RAG-Backend`：**实际生效**后端。后端工厂会在缺依赖时把 langchain / llamaindex 静默降级为 native，此前调用方无从得知。

故障时的头必须挂在 `HTTPException` 自己的响应上——在处理前给 `Response` 设的头会被异常响应丢弃。

### 空检索输入的已知简化

`HybridRetriever` 在 query 与 plan 都为空时**不调用后端**，直接按 `no_hit` settle。这与「检索成功完成但零候选」的字面定义不完全一致，属于已知简化：四状态是卡契约规定的集合，不为「未尝试」增开第五种。此处如实记录，输入契约若要统一由对应卡处理。
