## 二、发现清单

严重度定义：`高`（逻辑/安全缺陷，应尽快修）｜`中`（质量或扩展性隐患）｜`低`（可优化或需语义确认）｜`说明`（合理取舍，补文档）。

### M1（中）BM25 全 0 时把载入顺序当作稀疏排名喂给 RRF

- **位置**：`app/rag/vectorstore/local.py` `hybrid_search`（约 L190-L199）
- **现象**：

  ```python
  if any(s > 0 for s in bm25):
      sparse_order = list(np.argsort(-np.array(bm25)).tolist())
  else:
      sparse_order = list(range(len(valid)))   # 载入顺序被当成一路排名
  fused = _rrf([dense_order, sparse_order], k=rrf_k)
  ```

  当查询词项在候选集中全部无命中（BM25 得分全 0）时，稀疏路本应"无信息"，却把 `valid` 的载入顺序当作一路排序参与融合，给无关文档凭空的 RRF 贡献，扰动 dense 排序。
- **影响**：检索排序质量。中文按单字切分、BM25 命中概率较高，触发频率有限，故列中等。
- **建议**：`else` 分支改为 `sparse_order = []`，让无信息的稀疏路不参与融合。
- **成本**：一行改动。

### M2（中）生效日期开关开启后 Local 向量库退化为全量载入 + 逐块取 Document

- **位置**：`app/rag/vectorstore/local.py`（L137-L144）与 `visible_chunks_with_status`（L216-L245）
- **现象**：Flag 关闭时 SQL 层用 `is_current` 收窄；`RAG_EFFECTIVE_DATE_FILTER=true` 时 SQL 不再过滤版本，租户全部分块（含历史/scheduled）载入内存，再逐块 `session.get(Document)`。虽有 `doc_cache` 去重，仍属内存与查询放大。
- **影响**：当前默认关闭，不影响基线；是 Milvus / 生产开启生效日期前的扩展性隐患。
- **建议**：在 ADR-0002 摄取闭环或性能口径中显式记录该限制；作为生产化前置项跟踪，暂不改代码。

### L2（低）成员可删除/重解析自己的"非当前版本"文档

- **位置**：`app/rag/access.py` `can_write_document`（L46-L52）
- **现象**：管理员写路径要求 `doc.is_current`；成员路径仅校验 `doc.user_id == user.id`，不校验 `is_current`。与 ADR-0001"成员仅自己的文档"字面一致，但能否操作历史版本属语义空白。
- **建议**：与产品确认预期（多数实现禁止操作非当前版本）后再决定是否收紧。**需决策，不擅自改。**

### L3（低）单次评测模式不恢复 `RAG_HYBRID_RRF_K`

- **位置**：`scripts/run_rag_baseline.py`（`apply_rrf_k`，L111-L123；单次路径 L462）
- **现象**：单次运行改进程配置但不回滚（`run_sweep` 有 `finally` 恢复）。
- **建议**：脚本进程退出即弃，影响极小；文件头"待完善"已诚实记录，可保持现状。

## 三、说明（非缺陷；N1 / N2 建议补文档）

### L1（说明）`drop_injected_chunks` 每次调用新建检测器，正则不重编

- **位置**：`app/rag/retrieval_guard.py`（L36-L38）；`PromptInjectionDetector.__init__` 只保存 `threshold`（`app/security/prompt_injection.py`）
- **说明**：未传入 `detector` 时每次 `PromptInjectionDetector(...)`，多出来的只是一个轻对象。注入正则在模块加载时已编译进 `_INJECTION_PATTERNS`，不会随候选数或请求数重复 `re.compile`。无需为性能去缓存默认 detector。

### N1 `reject_untrusted_tool_call` 的防护边界

- **位置**：`app/rag/context_merge.py`（L30-L37）
- **说明**：`[UNTRUSTED_SOURCE]` 只是开关。上下文里出现该标记后，工具名对**整段** `context`（会话记忆、围栏内检索正文，以及之后追加的 critique）做子串匹配；名字不在用户原文里才拒绝。这能拦住检索正文（或记忆、critique）里带出的工具名，拦不住模型凭空造出、且整段 context 里也不存在的工具名。属合理取舍，建议在治理文档中点明：这不是通用工具白名单，也不是只在围栏内部查找。

### N2 QualityGate critique 追加不受 RAG 预算截断约束

- **位置**：`app/agents/pipeline.py`（L340、L441）
- **说明**：`critique` 直接拼进 `state.context`，而 `_trim` 仅在 `merge_memory_and_rag` 时生效；多轮自纠错可能使 context 逐步膨胀。当前逻辑安全（不可信主体仍在围栏内、工具名判定基于合并后整段 context），但长跑场景需留意预算。
