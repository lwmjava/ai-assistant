## 1. 结论

这版拆分已经能当作「本仓库需求文档里的企业上线清单」。上一轮指出的越权误修、重排必须变好、引用等待重排、文件写入先于工具契约，都已改掉。测试失败和 Embedding 自检也补上了。

按这个清单做完，并且剩下的 18 张 MVP 任务也做完，可以说满足本产品写明的企业上线标准：能自动回归、日志能串起一次请求、生产用 PostgreSQL、密钥不落明文、审计至少留 90 天、能备份数据库、向量库和上传文件、能演练升级回滚、有五项性能数字、检索在生产缺密钥时不会偷偷用假向量。

现在还不能说产品已经达到这个标准。这 38 张都还是 `backlog`。清单合理，不等于已经上线。

并入 `tasks.yaml` 之前再改 3 处，避免卡片自己打架：

| 任务 | 要改的一点 |
|---|---|
| `NFR-011` | 生产缺密钥时进程会直接启动失败，此时没有 `/health` 可看。验收不要同时要求「启动失败」和「`/health` 标明不可用」 |
| `NFR-009` | 检索延迟必须在真实 Embedding 上测，并依赖 `NFR-011`。假向量测出的毫秒数不能当上线数字 |
| `OPS-005` | 写明只做运维脚本，不注册成 Agent 工具，也不提供缺少人工确认的 HTTP 接口 |

## 4. 并入前仍要改的 3 处

### 4.1 `NFR-011` 的验收和现有行为冲突

`app/rag/embeddings/factory.py` 已写明：生产环境没有 `EMBEDDING_API_KEY` 时抛出 `RuntimeError`，不会改用 Mock。进程起不来，就没有 `/health` 可访问。

卡片验收同时要求「启动自检失败」和「`/health` 标明检索不可用」。两句不能同时成立。

建议改成：

- 生产缺密钥时，仍然启动失败，本卡不改这个行为。
- 进程已经在跑时，`/health` 写出 provider、模型、维度，以及当前是不是 Mock。
- 开发环境用 Mock 时，`/health` 必须标成不可作为上线证据。

### 4.2 `NFR-009` 的检索延迟不能用 Mock 测

五项指标里的「检索 P95 < 300ms」如果跑在 Mock Embedding 上，只能说明代码走通。`NFR-009` 应依赖 `NFR-011`，报告里写明 `/health` 看到的模型和维度，并且不是 Mock。机器规格按需求写清单机 4C8G。未达标可以记录处置，但不得把 Mock 结果写成达标。

### 4.3 `OPS-005` 仍可能被做成接口

验收已经要求执行前有确认、动作进审计、只在测试租户验证。允许改的目录仍包括 `app/core/tenants/` 和 `app/rag/`。实现时可能做成 HTTP 接口或 Agent 工具。

补一条非目标：只提供运维脚本；不注册成工具；不提供未经人工确认就能调用的接口。`PAGT-002` 已写「L3 在审批闭环出现之前不注册成工具」，这张卡要和它对齐。

另外，`PAGT-002` 的风险写成 L1，交付物却包含文件写入。写入默认关闭是对的，但夜间执行仍是 `true`。这张卡的夜间执行改为 `false`，避免无人值守把写工具放进注册表。
