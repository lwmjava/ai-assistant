## 2. 更正详情（实证）

### 2.1 关于 R-1 / P0 的重新定位（最重要）

初版将「cron 永不触发」判为本计划的 P0 阻断项。**这个判定越界，撤回。**

`tasks.yaml:3263-3295` 中 FLOW-001 的契约原文：

```yaml
- id: "FLOW-001"
  title: "调度在目标环境可启动（交付 D1）"
  context:
    problem: "目标环境里工作流调度不能稳定启动和停止。"
  deliverables:
    - "目标环境包含调度依赖"
    - "启动和停止测试通过"
  acceptance:
    - "目标环境中启动和停止测试通过"
```

**契约的目标就是启停，不是触发。** 计划的收窄是对契约的忠实执行，不是缺陷。

补充证据：装上 croniter 后，`_is_scheduler_runnable()` 通过 → `_task` 创建 → `stop_scheduler()` 取消，这条链路确实是通的，测试会通过，验收是真验收。

**但缺陷本身是真的**，详见第 4 节 —— 这也是本次评审最有价值的产出。

## 4. 评审中发现的独立严重缺陷（建议单独立项）

> **本节不是对 `plan_d1.md` 的批评。** 该问题落在 FLOW-001 明示的目标之外，本计划对此无责任，不构成阻断。
> 但目前 `tasks.yaml` 中**无任何任务认领**它，故在此记录并建议立项。

### 4.1 现象

`app/workflow/scheduler.py:66-76` 的 `_tick()`：

```python
nxt = next_run_time(wf.cron_expr, wf.timezone)   # after 未传
last = _last_run.get(wf.id) or _most_recent_execution_time(wf.id) or wf.created_at
if nxt <= now and last < nxt:
    _last_run[wf.id] = nxt
    await _trigger(wf)
```

`next_run_time`（`app/workflow/engine.py:44-62`）在未传 `after` 时执行 `base = after or datetime.now(UTC)`，即**以当前时刻为参照点求下一次匹配**。

croniter 的 `get_next()` 返回**严格晚于参照点**的下一个匹配（官方 README 示例：base `04:46` + `*/5` → 返回 `04:50`，跳过已过去的 `04:45`）。因此：

```
nxt > now 恒成立  →  nxt <= now 恒为假  →  _trigger() 永不执行
```

**推论：cron 定时触发在当前实现下不会被执行。** 调度循环存活、不报错、有心跳，但从不产生定时执行记录，而且是静默的。

> **证据边界声明**：本机 conda `ai-assistant` 与托管 Python 3.13 **均未安装 croniter**，本结论**未经实跑验证**，由官方 `get_next()` 语义 + 代码静态推导得出。安装依赖后须先实测校正，若与推导不符以实测为准。

### 4.2 为什么容易被漏掉

现有 `test_scheduler_runnable_and_start_stop` 只断言协程 alive/done，**不覆盖 `_tick() → _trigger()`**。装上依赖后测试全绿但功能仍然坏，是典型的 green-but-broken，违反 `AGENTS.md` §10 的红线。

**更值得注意的是能力矩阵的口径**（`docs/product/as-is-capability-matrix.md:35`）：

> Workflow 调度 ｜ `Partial` ｜ … ｜ 未安装 `croniter` 时调度器不可运行；`test_scheduler_runnable_and_start_stop` 在本环境失败

这条归因**本身准确**（未装依赖确实不可运行）。但 FLOW-001 完成后该测试会变绿，**此时若据此把该行从 `Partial` 提升为 `Implemented`，就会把一个从未真正触发过的调度记为已实现。** 建议 FLOW-001 收尾时不要改写此行，并把 cron 触发正确性单独立项。

### 4.3 修复方向（**不是可直接应用的补丁**）

初版第 3.4 节曾给出 `next_run_time(cron, tz, after=last)` 并标为「正确写法」。**这个标注过头，降级为方向。** 理由：

若 `last` 是很早的创建时间（首次运行场景），`get_next(after=last)` 返回的是创建后的第一个匹配点，落在过去 → `nxt <= now` 为真 → 触发。随后 `_last_run[wf.id] = nxt`（那个很早的点）→ 下一轮仍以它为基准 → **每个扫描周期补跑一个历史档期，直到追平当前时间**（追补风暴）。对长期未运行的任务，可能造成突发的大批量 LLM 调用。

完整修法需先对齐语义，至少明确三件事：

1. **是否补跑**：漏掉的档期要不要补？大概率应「最多补 N 期」或直接不补。
2. **基准如何取**：是否引入期望窗口（如 `base = max(last, now - 窗口)`），或改用「是否跨过点」判定替代「求下一次」。
3. **如何收敛**：补跑上限、超限后的记录方式。

这些是产品与运维决策，不是纯代码问题，必须先立项对齐，不能直接当补丁落。

### 4.4 建议动作

在 `tasks.yaml` 新增一条（建议纳入 PWFL 系列，置于 PWFL-003 之后以复用幂等语义）：

- 交付物：cron 到点触发能被真实执行；遗漏档期的处理策略明确且可验证。
- 验收：端到端用例 —— 建 `* * * * *` 工作流 → 等待一个 interval → 断言产生 `triggered_by=cron` 的执行记录；另有一条「长期未运行的任务重启后不产生批量补跑」的对照用例。
