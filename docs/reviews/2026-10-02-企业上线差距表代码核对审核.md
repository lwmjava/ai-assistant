# 审核：企业级上线差距表（代码核对）

> 日期：2026-10-02
> 对象：`docs/product/企业级上线差距-2026-10-02.md`
> 对照：`docs/product/项目产品需求方案.md` v1.1，以及当前 `app/`、`frontend/src`、`docker-compose.yml` 实际代码
> 方式：逐条查代码取证，未重跑测试，未改业务代码

## 1. 总判断

这张表作为「缺口清单」是合格的：分了版本、功能、需求口径三张表，标了核对日，写明未重跑测试，这一点比多数同类文档严谨。

但以「企业生产上线」为尺子，它现在还不能直接当排期依据，原因是三类问题：

1. **事实错误**（第 2 节）：5 行的描述与代码不一致，按现在的写法排期会做错事。
2. **严重性低估**（第 3 节）：3 行写了症状，但没写到真正卡住上线的那一层。
3. **漏项**（第 4 节）：部署密钥、多实例裁决、迁移双轨这几类生产上线硬门槛，三张表都没有开行。

另外第 5 节是表格自身的可裁决性问题，不影响结论但影响能不能拿来开工。

## 2. 与代码不符的行（必须改）

### 2.1 第 1 表 v0.2「技能不能自带工具」——错

代码事实：

- `app/agents/skills/base.py:102` — `tools: list[str] = field(default_factory=list)`
- `app/agents/skills/loader.py:75` — `tools=[str(t) for t in data.get("tools", [])]`
- `app/agents/skills/manager.py:200` — `tool_names.extend(skill.tools)`
- `app/agents/skills/manager.py:233` — `collect_tools()` 按名字从 `ToolRegistry` 取出并注入

技能**能**带工具，走 `SkillMode.TOOL` 模式。真正的限制是：只能引用**已注册**的工具名，未注册时只 `logger.warning` 跳过（`manager.py:262`），不能自带新的工具实现。

建议改法：改成「技能可声明 TOOL 模式并绑定已注册工具，但不能自带工具实现；`web_search` / `file_ops` 根本没注册，所以无从绑定」。

### 2.2 第 2 表「§5.3.4 的邮箱全局唯一，代码未强制」——错

代码事实：

- `app/models/user.py:39` — `email: str | None = Field(default=None, unique=True, index=True)`
- `app/services/auth_service.py` — `register_member` 抛 `EmailTakenError`
- `app/api/routes/auth.py:180-181` — 映射 409「邮箱已存在」

非空邮箱已经全局唯一。SQLite 与 PG 的 NULL 都不参与唯一约束，所以「多个用户邮箱为空」是允许的，这是设计选择不是缺陷。

建议改法：删掉这半句。这一行收敛为「没有手机号字段；没有验证码；没有记录哪个字段已验证」。

### 2.3 第 1 表 v0.4 / 第 2 表「工作流到点……不会写出执行记录」——因果对，结论错

代码事实：

- `app/workflow/engine.py:44` — `next_run_time()` 用 `croniter(...).get_next(datetime)`，返回的是 **now 之后的下一个**触发点
- `app/workflow/scheduler.py:74` — 判定 `if nxt <= now and last < nxt:`

下一未来时间恒大于 now，**该条件恒不成立，cron 永远不会触发**。

而 `app/workflow/engine.py:92-101` 的 `execute()` 是**会**创建 `WorkflowExecution` 并落库的。所以问题不是「不写执行记录」，是「根本走不到执行」。

叠加两个前提：`WORKFLOW_ENABLED` 默认 `False`（`config.py:220`），调度器连启动都不启动；`croniter` 是可选依赖，未安装时 `_is_scheduler_runnable()` 直接返回 False（`scheduler.py:37`）。

建议改法：拆成两行——
- 「cron 触发判定缺陷：`next_run_time` 取未来时间导致到点条件恒不成立」P1（但它是功能性的，不是文档性的）
- 「`WORKFLOW_ENABLED` 默认关 + `croniter` 可选，未装则只有手动触发可用」

### 2.4 第 2 表「PostgreSQL 生产库 …… 默认 SQLite」——半错

代码事实：

- `app/core/config.py:46` — `DATABASE_URL` 默认 `sqlite:///./data/ai_assistant.db`
- `docker-compose.yml:10` — `db` 服务是 `postgres:16-alpine`
- `docker-compose.yml:49` — app 服务把 `DATABASE_URL` 覆盖为 `postgresql://...@db:5432/...`

一键部署路径**已经是 PG 16**，且满足 §6.4 的「PostgreSQL 14+」。真缺口是 PG 上没有备份恢复演练、没有迁移回滚验证。

建议改法：口径改为「配置默认值是 SQLite；compose 已切 PG 16，但 PG 上的备份恢复演练与迁移回滚没有证据」。

### 2.5 第 2 表「审计保留 90 天 …… 本轮未看到夜间任务调用它」——对，但不完整

代码事实：

- `app/audit/logger.py:142` — `cleanup_old_logs()` 确实没有生产调用方，只有 `tests/test_audit_smoke.py:152` 调
- 但项目里有另一条保留期清理：`app/rag/import_scheduler.py:34` → `app/rag/retention.py` 的 `purge_expired_documents()`，`RETENTION_DAYS = 90`

建议改法：补一句「RAG 软删文档的 90 天清理已由 `import_scheduler` 调度；审计日志的清理没有调度」。否则会被读成「项目里没有任何保留期清理」。

## 3. 严重性低估的行

### 3.1 SSE 协议差距远大于「引用角标」

实测 `AgentEvent(...)` 全量事件类型（`app/agents/`、`app/services/chat_service.py`）：

`stage` / `token` / `tool` / `subtask` / `sources` / `code_result` / `error` / `done` / `conversation` / `rate_limit`

对照 §5.1.4 要求的协议：

| PRD 要求 | 代码现状 |
|---|---|
| 所有事件携带 `run_id` | 无 |
| `run.started` / `run.finished` | 只有 `done` |
| `node.started` / `node.finished` | 只有 `stage`（中文阶段名，无 ts） |
| `intent.classified` | 无 |
| `plan.generated` | 只有 `subtask` |
| `tool.call` / `tool.result` | 合并成一个 `tool` 字符串事件 |
| `citations` | 只有 `sources` |
| `heartbeat`（15s） | 无 |
| 断线 `Last-Event-ID` 回放 | 无；前端断线只能加载已落库全文（`frontend/src/pages/Chat.tsx:363`） |

这不是「引用侧栏」能覆盖的，是 §5.1.4 整节没有对齐。

建议：把第 2 表「引用与断线」拆成「SSE 事件协议对齐」与「引用侧栏」两行，前者标 P0。

### 3.2 会话删除是硬删除，不只是「没有归档字段」

`app/services/chat_service.py:112-121` — `delete_conversation` 直接 `session.delete(conv)`。§5.9.2 写明「创建/列表/详情/删除（软删除）」。第 2 表只写了「会话模型没有归档字段」，漏了硬删这一条。

### 3.3 覆盖率与 CI 没有独立成行

- `.github/workflows/` 不存在
- `requirements.txt` 无 `pytest-cov`
- `pyproject.toml` 无 coverage 配置（只有 ruff / pytest / mypy 三段）

现状：61 个测试文件、467 个测试函数。数量不小，但**没有度量就无法声称达标**，而 §4.5 把「覆盖率 ≥ 70%」和「CI 全绿」写成两条独立验收。

建议：第 2 表单开一行 P0「测试覆盖率度量与 CI 流水线」，不要只在「发布门禁」一行里带过。

### 3.4 备份脚本本身不存在

§6.7 要求提供 `scripts/backup.sh`。`scripts/` 下只有 4 个 Python 脚本（`_gen_remaining_tasks.py`、`milvus_five_gates.py`、`run_agent_chain_eval.py`、`run_rag_baseline.py`）。第 3 表只写了「没有 RPO/RTO 数字」，没写脚本缺失。

## 4. 以企业生产上线为标准，表里没开的缺口

### 4.1 部署与密钥（最硬的三条）

| 项 | 代码事实 | 位置 |
|---|---|---|
| CORS 默认放行全部来源 | `CORS_ORIGINS: ${CORS_ORIGINS:-*}` | `docker-compose.yml` app 环境 |
| 数据库口令可预测 | `POSTGRES_USER/PASSWORD` 默认 `aiassistant`，且明文写在连接串里 | `docker-compose.yml:11-13, 49` |
| 5 分钟旅程被无用服务拖住 | app `depends_on: milvus: service_healthy`（`start_period: 90s`），但默认 `RAG_VECTOR_STORE=local` | `docker-compose.yml:24-43, 52, 66` |

第三条直接冲击 §4.5.1 的「5 分钟上手」计时口径——等一个默认用不到的 Milvus 健康，可能就吃掉 90 秒以上。

**已经做对、不要重复开成缺口的**：`JWT_SECRET_KEY` 用 `${…:?}` 强制必填（`docker-compose.yml:50`）；镜像非 root（`Dockerfile:19, 40`）；有 HEALTHCHECK（`Dockerfile:44`）。

### 4.2 多实例必须先裁决，否则三项无法定级

- 限流：`app/security/rate_limiter.py` 进程内 `dict` + `Lock`，注释自己写了「不跨实例共享」
- Trace：`app/debug/trace.py` 内存环形缓冲
- 工作流调度：`scheduler.py:26` 进程内 `_last_run` 字典，无分布式锁 → 多副本下会重复触发

第 3 表「多实例」只写了「没有写限流、调度、Trace 在多副本下放哪」，第 2 表只记代码现状，**两边都没有合格线**。

建议：先裁决「1.0 是明确只支持单实例发布，还是必须支持多副本」。这一条不定，上面三项无法定 P0 还是 P1。

### 4.3 迁移双轨

`app/core/migration.py` 同时存在 Alembic（`cfg.set_main_option("sqlalchemy.url", ...)`，`migration.py:43`）和手写 `_ensure_quota_columns()`（`migration.py:183`，直接 `ALTER TABLE tenants ADD COLUMN`）。在生产库上，启动时自动补列与 Alembic 版本头可能互相打架。§6.7 只要求 Alembic。三张表都没有这一行。

### 4.4 可观测

- 无 JSON 结构化日志，无 request 级 `trace_id` / `user_id` / `tenant_id` 贯穿（`structlog` 只用于审计写库失败的降级，`audit/logger.py:124`）
- `app/debug/trace.py` 有 `run_id`，但 `DEBUG_ENABLED` 默认 `False`（`config.py:193`）
- 无 `/metrics`；无告警规则与接收人

第 2 表「结构化日志」一行只对了一半，应补「请求级日志与 trace 关联整体缺失」。

### 4.5 交付与合规

- 无 `CHANGELOG`（§6.7 要求 Breaking 区）
- 无 SBOM / 依赖漏洞扫描 / 许可证清单（§6.2 只要求 pre-commit 扫硬编码密钥）
- 无发布回滚演练记录

### 4.6 性能五项的一个前提

§6.1 五项（P95 <500ms、首 Token <2s、检索 <300ms、并发 ≥50、10MB PDF <30s）目前没有实测记录，第 2 表已写。补一条口径约束：`llm_availability()`（`app/llm/factory.py:47`）在无密钥时返回 `mock` 开发环境降级，Mock Embedding 的结果**不能**用来填检索延迟那一栏；填的时候必须写明 provider、模型、维度与机器规格。

现有可用资产（别浪费）：`evals/reports/` 有 `rag-v0.1-baseline-20260919.json` 与 `rag-v0.1-lexical-coverage-20261002.json`，`evals/datasets/` 有 rag-v0.1 与 agent-chain-v0.1。

## 5. 表格自身的可裁决性问题

1. **第 1 表仍把版本与后补能力缠在一起**。文首已声明后补项不是版本，但 v1.0 行的「后补能力见第 2 表」又把读者引回去。建议第 1 表只留版本。
2. **第 2 表级别列有六种非 PRD 值**：`Deferred`、`必须有，验收条件未定`、`后续`、`见第 3 表`、`不占 1.0 功能验收`、`上线`。无法按级别排序开工。建议统一成 P0/P1/P2/P3 + 一个「未定（待裁决）」。
3. **6 行写「本轮未看到 / 未逐页核对」**。这是「未核对」不是「缺口」。建议单列一节，否则会被当成已确认缺口排进任务。
4. **缺一列「证据位置」**。每行给一个文件路径 + 行号，下次复核不用重扫全仓——这次审核的取证成本基本花在这里。
