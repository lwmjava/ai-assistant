## 0. 评估口径

完整度拆成两个口径，二者差距越大，说明 "能用但没达到上线标准"：



* **功能主路径**：P0 主链能否跑通（解析 → 检索 → 编排 → 输出 的端到端可用性）。

## 2. 逐域评估

### 2.1 RAG 知识库 — 功能 85% / 企业级 75%（最强）

**代码事实（已实现）**



* 多格式解析：PDF / DOCX / TXT / MD / CSV / JSON + OCR 可选（`app/rag/document_parsers/`）。

* 10 种切分策略：fixed\_chars /format\_aware/layout\_aware /paragraph/recursive /sliding\_window/token\_aware /structured/semantic /parent\_child（`app/rag/chunking/factory.py` 注册表，与 `strategies/` 目录一致）。

* 三后端：native /langchain/llamaindex（`app/rag/backend/`）。

* 混合检索：Dense + BM25 + RRF，检索过取 + 注入块剔除 + 不可信围栏（`app/rag/retriever.py`、`retrieval_guard.py`）。

* 向量库：local /milvus 双适配（`app/rag/vectorstore/`）。

* 导入任务异步平台、版本管理、软删除 + 保留期、tenant 级权限隔离（`access.py`，ADR-0001）、生效日期过滤（ADR-0003）、记忆 / RAG 字符预算合并（`context_merge.py`）。

* 有离线检索基线 rag-v0.1（`evals/reports/`）。

**企业缺口**



* 默认向量库仍 `local`（`config.py: RAG_VECTOR_STORE="local"`），Milvus 仍为 `Partial`（ADR-0002）。

* 无独立 Reranker（仅 RRF；REL-004 已裁定不采纳）。

* 引用仅文件名 + 页码，无角标 / 侧栏摘录（`chat.py: SourceOut`）→ PRAG-003。

* 清洗链缺失（仅压空白，缺去重 / 质量 / 格式 / 元数据）；删除向量补偿无队列 → RAG-014。

* 检索低分阈值 / 拒答未做 → PRAG-004。

* 资源级 ACL（文档 / 会话级）仍 `Planned`（ADR-0001）。

* 有离线基线但无 1.0 持续测评门禁。

**建议**：RAG 主链已达标，只需补引用产品化（PRAG-003）与默认 Milvus 证据（RAG-015），避免过度投入。

### 2.2 Agent 编排 — 功能 85% / 企业级 62%

**代码事实（已实现）**



* 五阶段管线完整：理解 / 规划 / 行动 / 反思 / 响应（`app/agents/pipeline.py`）。

* Preflight 意图短路、QualityGate 自纠错（阈值可配，默认关）、工具循环（防重指纹 + 预算 `max_tool_rounds` + 拒绝策略）、Prompt 注入防护。

* 流式 / 非流式双模式；LangGraph Supervisor 可选（`app/agents/supervisor.py`）；意图分流、路由（`route.py`）。

* LLM 失败按 fallback\_chain 降级，无可用模型时有引导。

**企业缺口**



* 工具集不全：缺 `web_search` 与 `file_ops` 读能力（PAGT-001）。

* 无独立 Tool Executor / State Manager / Repository 层（Brownfield 现状，AGENTS.md 承认）；工具无统一风险分级（L0-L3）、无权限挂接、无独立审计（PAGT-002）。

* 调用预算有基础但无完整上限治理（PAGT-003）。

* Plan 仍是文本计划，不可编排（PAGT-004）。

**建议**：当前最成熟的编排层缺工具落地治理，优先补 PAGT-001（补工具）+ PAGT-002（十要素契约）。

### 2.3 沙箱 — 功能 80% / 企业级 58%

**代码事实（已实现）**



* 四层防护完整（`app/agents/tools/sandbox/sandbox.py`）：AST 白名单（+ 禁止节点 / 模块 / 内置函数）+ 进程隔离（Linux/macOS setrlimit+execv，Windows Job Object）+ 资源限制（CPU / 内存 / 磁盘 / 输出）+ 超时 kill。

* 输出截断 + 宿主机路径脱敏。

* SAND-001 / SAND-002 已完成。

**企业缺口（安全隔离深度不足）**



* 无 Linux 实机限额记录（SAND-003，缺运行证据 —— 当前主要在 Windows 上验证）。

* 无 chroot / 非特权用户 / 网络隔离；`_BLOCKED_IMPORTS` 注释明确 "SKELETON：此列表尚未覆盖完整"，且 "沿继承链拿到文件能力" 的绕过未处理。

**建议**：补 SAND-003（Linux 实机证据）+ 隔离深度（非特权用户 / 网络隔离），这是 P0-5 验收的核心证据。

### 2.4 网关 Channel/API — 功能 80% / 企业级 52%

**代码事实（已实现）**



* `/api` 前缀（`app/main.py`）、SSE（sse\_starlette；默认编排 9 种事件：conversation /stage/token /tool/code\_result /done/error /sources/rate\_limit；langgraph Supervisor 另发 subtask，共 10 种）。

* 认证 + RBAC（`require_permission`）、部分错误码（rate\_limited /quota\_exceeded）、CORS 可配置、审计 hook、健康检查、SPA 托管、Channel ABC + HttpApiChannel 已登记。

**企业缺口（失血点集中）**



* API 前缀仍是 `/api` 非 `/api/v1`（API-001）。

**建议**：网关三件套（ERR-001、SSE-001、NFR-002）卡住 "统一契约 + 可观测"，应作为上线优先级最高的一组。

### 2.5 Prompt 提示词工程 — 功能 80% / 企业级 55%

**企业缺口**

* 无 Prompt 级评估挂钩（QualityGate 是运行时质量门，不评估提示词版本本身）。

**建议**：1.0 只需保证 "Prompt / 模型版本可追踪"（Definition of Done 要求），可先用文档登记版本，不必做整套 A/B 平台。

### 2.7 Workflow 工作流 — 功能 70% / 企业级 52%

**代码事实（已实现）**



* WorkflowEngine：cron 解析、owner 失效校验、webhook 回调、执行历史落库（`app/workflow/engine.py`）。

* Scheduler：`scheduler.py:_tick` 用 `nxt <= now and last < nxt` 判定，但 `nxt`**&#x20;来自&#x20;**`engine.py:next_run_time`**&#x20;→&#x20;**`croniter.get_next()`**，返回的是基于当前时间的 "下一次未来触发时间"，恒大于 now**，故 `nxt <= now` 恒不成立 —— 到点触发实际仍不生效。

* Bridge 复用 ChatService，手动触发可用。

**结论（修正）**：差距表 / AGENTS.md 的 "到点不触发" 判断**准确** —— `nxt` 是 croniter 返回的**未来**下一次时间，`nxt <= now` 恒不成立，调度循环不会触发任何执行（FLOW-003 仍待做）。此前初审把 `_last_run` 缓存与 `last < nxt` 误判为已修复，属审查错误，本版更正。

**企业缺口**



* 无重试 / 指数退避（PWFL-001）、无超时强制 / 取消（PWFL-002，`WORKFLOW_MAX_EXECUTION_SECONDS` 有配置但未见强制 kill）、无并发控制 / 幂等（PWFL-003）、无失败告警 / 日志持久化（PWFL-004）。

* 默认关（`WORKFLOW_ENABLED=False`），croniter 为可选依赖。

### 2.8 MCP 工具连接 — 功能 60% / 企业级 32%（最弱）

**代码事实（已实现）**



* 进程级单例管理器（`app/mcp/manager.py`）容错连接 + 多传输（stdio /http/sse）。

* 工具聚合到 Agent 工具箱；调用失败以 `isError` 标记（`client.py`）。

**企业缺口（最严重 ——PRD 第五章无 MCP 章节，差距表第 3 表明言 "超时、权限、审计没有产品验收"）**



* 无调用超时（`call_tool` 直接 await，无 timeout wrapper）→ PMCP-001。

* 无重连 / 心跳 → PMCP-001。

* 无权限 / 风险分级（MCP 工具与内置工具同权）→ PMCP-002。

* 无调用审计（不进 audit logger）→ PMCP-003。

* 凭据明文配置（`MCP_SERVERS` JSON 无加密）→ PMCP-004。

* 单例为进程级，多副本各自连接。

**建议**：MCP 目前是 "无产品验收却标 P0" 的隐患最大域。应先补 PRD 产品验收，或把 PMCP-001/002/003 降级，再谈实现。

### 2.9 记忆 — 功能 85%（对话内）/ 企业级 50%

**代码事实（已实现，对话内）**



* 窗口管理：`MemoryConfig.window_size=20`，超窗滑动裁剪（`app/memory/manager.py`）。

* LLM 压缩：`summary` / `key_points` / `none` 三档策略（`app/memory/compressor.py`），`temperature=0.3`。

* 保留最近 N 轮：`keep_recent=5`。

* 上下文注入：压缩快照 → `AgentState.context` 注入管线；`wrap_history` 以系统消息插入历史最前。

* 失败降级：压缩异常返回空快照不阻塞对话，`chat_service._build_memory` 外层兜底。

* 运行证据：MEM-001 已有实跑结论（25 条只滑窗、31 条压缩并保留最后 5 条）。

**企业缺口（记忆系统层几乎未开始）**



* **快照不持久化**：`MemorySnapshot` 注释明说 "可序列化，为持久化预留"，但从未落库；`chat_service._build_memory` 每次从 DB 读全部消息且**未传&#x20;**`existing_snapshot` → 增量压缩能力实际未被启用，长会话每次请求都重算全部历史，成本与信息丢失风险随轮次累积。

* 无跨会话 / 长期记忆（§5.7 排到 v1.5）。

* 授权 / 期限 / 删除治理完全空白（差距表第 3 表：谁能读、存多久、如何删、防串租户）。

* 无记忆检索（向量相似度匹配历史记忆）；多级记忆（短期 / 中期 / 长期）无。

**建议**



* 1.0 中不构成 P0 阻断（§5.7 明确长期记忆 v1.5）。

* 低成本修正：`chat_service._build_memory` 接上 `existing_snapshot`，把已写好的增量压缩能力真正用起来。

* 若未来做跨会话记忆，必须先补 "谁能读 / 存多久 / 如何删 / 防串租户" 治理卡，避免重蹈 MCP"能力先于验收上线" 的坑。

## 3. 关键发现与漂移



1. **Workflow 到点触发仍不生效**：`scheduler.py` 用 `nxt <= now and last < nxt` 判定，但 `nxt` 来自 `croniter.get_next()`（返回未来时间），`nxt <= now` 恒不成立，调度永不触发 —— 与差距表 "到点不触发" 一致，FLOW-003 仍待做。

2. **MCP 无产品验收却标 P0**（PRD 第五章无 MCP 章节）—— 优先级虚高，应先补需求或降级。

3. **记忆快照不落库 +&#x20;**`existing_snapshot`**&#x20;未接**—— 已写好的增量压缩能力没有真正生效。

4. **沙箱隔离深度不足**（无 chroot / 非特权用户 / 网络隔离）+ 无 Linux 实机证据 ——P0-5 验收的核心证据缺口。

## 4. 综合结论与失血点排期建议

按企业上线优先级，失血点排序：



1. **网关三件套**：ERR-001（统一错误码）、SSE-001（SSE 协议）、NFR-002（结构化日志）—— 卡住 "统一契约 + 可观测"。

2. **MCP 安全三件套**：PMCP-001（超时 / 重连）、PMCP-002（权限分级）、PMCP-003（审计）—— 当前 "无产品验收却标 P0" 隐患最大的域。

3. **沙箱**：SAND-003（Linux 实机证据）+ 隔离深度 ——P0-5 验收核心。

4. **Agent 工具治理**：PAGT-001（补 web\_search/file\_ops）、PAGT-002（十要素契约）。

5. **RAG**：仅补引用产品化（PRAG-003），其余检索侧已达标，勿过度投入。

6. **记忆**：对话内已够 1.0；低成本接上 `existing_snapshot`，治理卡留待跨会话记忆时补。

## 5. 与 tasks.yaml 的对齐建议



* 校正 Workflow：FLOW-003 仍待做 —— `scheduler.py` 到点判定依赖未来 `nxt`，条件恒不成立；需改为 "以上次实际触发 / 成功执行时间为基准判断是否补触发"。

* 收口已达成代码能力的卡（如 SAND-001/002、MEM-001 之外的重复项），避免 backlog 与代码事实漂移。
