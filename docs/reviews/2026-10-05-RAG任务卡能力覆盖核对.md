# RAG 任务卡能力覆盖核对

核对日期：2026-10-05。范围：tasks.yaml 中 RAG、PRAG 及关联 QA/EVD/REL/NFR 卡，对照 app/rag、配置、对话集成、前端来源展示、测试与既有评测说明。此次为静态核对，未修改业务代码或任务卡，未重跑真实 Embedding、LLM 或 Milvus。

## 结论

现有卡能指导部分 RAG 治理和改进，但不能单独完整呈现整体能力，也不能保证全部完成后即达到企业生产就绪。任务状态与能力成熟度需要分别记录。当前任务覆盖集中在检索、文档治理和切分；生成质量、Embedding 索引兼容、解析质量验收仍缺少明确闭环。

## 优先修正的问题

1. **RAG-019 安全条件自相矛盾。** tasks.yaml:8967 将“缓存键不含权限/租户隔离信息”列为 non_goals，同时要求跨租户不串。应明确缓存隔离域包含租户与有效权限范围，命中时仍校验访问权限；文档发布、删除、重解析、权限变化需要失效。LLM 缓存还需涵盖实际上下文与模型/Prompt 配置。temperature=0 本身不证明可安全复用答案。

2. **任务文件存在引号未闭合。** tasks.yaml:8288、8290 的 RAG-020 claim 缺少结束双引号。这会影响标准 YAML 解析，应先修复并做全文件解析、唯一 ID、依赖引用校验。此次指定 conda 环境路径不存在，未取得 YAML 解析器验证结果，不报告已验证解析失败。

3. **PRAG-004 的完成范围比标题窄。** app/rag/retriever.py 过滤 similarity，但 app/rag/vectorstore/milvus.py:248 固定 similarity=1.0，不能判断真实低相关结果。全部过滤时返回的是供管线使用的提示文字；tests/test_rag_threshold.py 验证 Retriever 返回值，没有证明最终助手回复拒答。RAGService.search 也不经过该阈值。应明确入口/后端适用范围，并为 Milvus 相似度、同步/流式最终回复补验收。

4. **RAG-016 没有覆盖对话父块展开。** app/rag/service.py:419 的 search 调用 _expand_parent_chunks；:458 的 make_retriever 使用 self._backend，HybridRetriever 调 backend.retrieve，NativeRagBackend 不调用展开函数。应明确卡只验知识库搜索，或另定义对话验收；还需覆盖父块安全检查、元信息和上下文预算，不能只测结果包含父块。

5. **RAG-021 的事实描述过度概括。** format_aware 按解析块切分，layout_aware 按页和版式排序，structured 按 Markdown 标题分节；因此“全部策略均无结构边界保护”不准确。真实缺口是缺统一的代码/盒图/表格完整性保证，超长块仍可递归细分。应区分整行完整与整个结构块完整，并定义超长块处理、最大预算、重叠与覆盖率；不能只用“不切行”证明语义完整。

6. **RAG-022 目标需要指标和依赖。** 当前 auto 的文本启发式描述属实，但“可路由全部 10 种”不是质量提升指标。应以文档类型和结构的可复算决策表为验收，定义无 bbox、无 blocks、Embedding 不可用等降级。若复用 RAG-021 的质量指标，必须声明依赖。RAG-021/022 的 allowed_paths 写成不存在的 app/rag/parsers/，真实目录是 app/rag/document_parsers/；RAG-022 若改变配置还需允许同步 .env.example、README。

7. **PRAG-002 缺可执行进入条件。** 当前为 backlog，历史 REL-004 结论仍不采纳，non_goals 又要求采纳结论以 REL-004 为准。保留未来任务合理，但当前没有被批准的候选可落地；不能仅因 depends_on 的 REL-004 已 done 自动启动。需明确新的采纳证据、决策入口和暂停条件。不自行改成 cancelled。

8. **卡片事实和能力文档有漂移。** PRAG-003/004 已 done，context.facts 仍写“没有 citation”“未设置低分阈值”；应标成变更前事实并追加完成后证据。as-is-capability-matrix.md 仍为 2026-10-02 口径；AGENTS.md 对 PRAG-002 的 cancelled 描述也与当前 backlog 不一致。RAG-016 已有实现进度但待人工审查，不能直接改 done。

## 尚未形成充分任务闭环的能力

- **真实生成评测**：答案点正确性、无答案拒答、冲突/过期资料处理、逐答案点引用准确率、恶意资料下工具行为；检索命中率与 quote coverage 不能替代这些指标。
- **Embedding/索引治理**：记录 provider/model/dimension 与索引版本；同维度换模型也要检测不兼容；混用阻断、重建与切换回滚要有证据。RAG-015 的归一化/维度校验和 NFR-011 的状态展示不足以覆盖。
- **解析质量验收**：按格式、扫描 PDF、中文 OCR、双栏、表格定义样本和提取/阅读顺序指标；区分有代码、有单元测试、有真实依赖运行证据。
- **资源 ACL**：当前同租户访问语义应保留；若纳入目标版本，需先批准权限决策与专项任务，不能把 PRAG-001 的检索越权核对视为已实现 ACL。

建议先修复任务契约与状态漂移，再建立“能力 → 当前状态 → 任务 → 验收 → 证据 → 未验证项”映射。确需新增任务时，按项目规则一次拆分清楚、计划落盘；此次仅提出缺口，不追加卡、不实施。

## 补充核对：上一轮之外的问题

1. **LangChain 分数语义错误（高优先级）**：_ProjectVectorStoreAdapter.asimilarity_search_with_score 返回 h.score（RRF 融合分），LangChainRagBackend.retrieve 却将它写为 similarity。默认阈值 0.4 下，正常命中也可能全部被过滤。PRAG-004 应补 native/langchain/llamaindex × local/milvus 的分数字段契约测试，不能根据方法名认定是余弦相似度。
2. **先截 top-k 再过滤低分，不能补位**：NativeRagBackend 已 drop_injected_chunks(..., keep=top_k)，HybridRetriever 随后才按 similarity 过滤。最终不足 k 时不再取后续候选。需明确允许少返回，还是从合格候选补位；若目标是检索质量，评测必须走与对话一致的过滤链。
3. **Local 与 Milvus 混合检索并不等价**：Local 在载入候选上算 BM25；Milvus 只对向量召回候选算 BM25，纯关键词相关但不在稠密候选中的块无法被稀疏路召回。Milvus 在 BM25 全零时仍把载入顺序送入 RRF。RAG-008 明确不改 Milvus，属于有意范围限制，但 RAG-015 没有补齐此差异的质量验收；应写清语义和跨库关键切片。
4. **检索故障与无知识无法区分**：Milvus collection.search 异常被捕获后返回 []，Retriever 无结果又返回空上下文。可能使故障表现为普通无命中并继续生成。应定义 unavailable/no_hit/below_threshold 的状态、用户行为与告警；NFR-011 的静态状态展示不足以验证运行中故障。
5. **持续门禁卡缺可执行标准**：RAG-017 只依赖 RAG-005，未与负责 CI 的 NFR-001 建立依赖/集成约定；未明确 Recall@几、退化容忍量、风险切片和真实 Embedding 服务故障处理。验收命令没有实际评测入口；RAG-018 引用的 scripts/run_rag_eval.py 不存在，实际为 scripts/run_rag_baseline.py。RAG-017 allowed_paths 也未含 scripts/ 和 docs/，与实现/证据要求需协调。
6. **敏感日志验收不足**：retriever.py 记录 search_text[:200]（问题与计划），chat_service.py 记录完整 sources（含摘录）。确认了原始业务内容进入日志调用，但是否最终脱敏需另核对 formatter/filter。应增加个人信息、敏感文档摘录不会出现在最终日志的用例；结构化日志不等于内容安全。
7. **导入并发名称与执行不符**：run_import_jobs_once 将 RAG_IMPORT_MAX_CONCURRENCY 用作查询 limit，随后逐个 await _process_job，是批次大小而非并行数。任务验收应区分批处理与并发，并把进程中断后的任务恢复、原子抢占和多实例幂等映射到 OPS-001/002，不能仅凭配置名称宣传并发导入。

## 第三轮补充：跨路径一致性与失败原子性

1. **新版本失败可能使旧版本退出检索**：import_jobs.py 在调用 ingest_parsed_document 前将 previous.is_current=False 并提交。之后 Embedding/摄取失败，失败处理没有恢复旧版。应对 RAG-013/014 增加故障注入验收：新版本失败后旧当前版仍可检索，成功才原子切换。此为代码路径推导，未执行故障复现。
2. **重解析未复用上传的结构与策略契约**：service.py reindex_document_in_place 用 resolve_strategy_name(parsed.text, None) 和 split(text)，未消费 parsed.blocks，也未复用原文档的策略参数。format/layout 上传保留的信息可能在重解析后丢失，或请求级 parent_child 策略变回默认。RAG-021/022 及生命周期验收应覆盖首次上传与重解析的一致性，并明确保存/迁移策略参数。
3. **字符截断可能破坏不可信围栏，来源也可能超出实际上下文**：context_merge._trim 对完整 rag_text 直接取前 N 字符，长文本的 [/UNTRUSTED_SOURCE] 可能被截掉；sources_from_hits 则读取 retriever.last_hits，并非实际保留在预算内的块。需要按块构建预算、保留完整围栏，并区分“检索命中来源”“实际提供给模型的来源”“答案引用来源”。不据此直接认定模型已执行注入。
4. **uploader 配置没有对话检索身份闭环**：access.can_read_document 有 uploader 限制，但 ChatService._build_retriever 只传 tenant_id，Local.hybrid_search 也只按租户/版本过滤，没有上传者身份。默认 tenant 语义符合现状；不能把 uploader 宣传为已经验证的检索回滚隔离方案。若保留此配置，应补端到端测试或明确不支持范围。
5. **同租户可检索与引用详情权限不一致**：默认 tenant 允许命中他人文档；get_document/list_chunks 使用控制面权限，普通成员只能访问自己的当前版。来源跳到知识库文档可以不等于能读取相应分块。PRAG-003/RAG-020 应用 A 上传、B 同租户提问并查看引用的完整用例验收；需批准只读溯源权限契约，不能放宽删除/重解析权限来解决。

以上需先修正契约，再按任务边界实施。无需为每个观察另加一张卡：版本失败、重解析可补生命周期验收，围栏/来源可补上下文与引用验收，身份问题补权限验收。真实影响仍需指定环境中的契约与故障注入测试证明。

## 第四轮补充：评测数据治理、对话预算合并与调用稳定性

1. **评测数据集本身缺分级治理**：rag-v0.1 基线的 35 例来源、Gold/Silver/Adversarial 判定与可复现性未明；AGENTS.md 要求“AI 生成数据默认不是 Gold”。检索命中率/quote coverage 之外，基线数据集的 Gold 判定与越权切片可复现性需单独验收，否则基线不可信。
2. **RAG 注入与对话 Memory 的预算合并未成闭环**：现有对 rag_text 预算/裁剪与“实际提供 vs 检索命中 vs 答案引用”来源区分已有覆盖，但 RAG 命中与对话历史/Memory 按预算合并的优先级、超长裁剪对两路的一致影响（AGENTS.md「Memory/RAG 按预算合并」）未定义验收。
3. **Embedding/检索调用缺超时与重试稳定性**：现有覆盖“embedding 不可用降级”与 Milvus 故障返回 []；但 embedding provider 调用超时、慢查询保护、失败重试与降级到 BM25 的路径未定义，影响上线稳定性。
