## 1. 评审目的与结论

本次评审检查四份文件能否清晰、一致地指导 `tasks.yaml` 中任务卡的执行，重点关注事实一致性、任务准入、审批、完成条件、验证要求和长期维护成本。

主要问题是：长期规则、当前进度和历史指导混在一起，已经出现事实漂移；任务启动、审批和完成条件也缺少明确的执行契约。这些问题可能导致 AI 选择错误任务、重复请求确认，或对“完成”产生不同理解。

现有的范围控制、Mock 限制、权限边界和可复现证据要求应保留。优化重点是消除冲突、明确适用条件、减少重复维护，并通过自动检查防止再次漂移。

本报告区分已确认问题和规则优化建议。不据此直接切换向量库、升级能力状态、修改任务状态或批准架构变更。

## 3. 问题与优化建议

### 3.1 Milvus 定位存在直接冲突

**性质：已确认的文档冲突。优先级：高。**

证据：

- README 核心特性仍写“正式 Local，Milvus 实验，升格须另开 ADR”。
- 迭代指导第 3 节漂移表、第 4.7 节也保留相同旧说法。
- 同一指导第 4.1 节、AGENTS 和 ADR-0002 已明确：正式目标为 Milvus，Local 用于当前默认、评测和回退。
- ADR-0002 明确本修订取代旧决定，不再另开 ADR。

影响：AI 可能重复发起已经完成的架构决策，或按旧决定实施。

建议：统一使用“正式目标、当前默认、实际能力状态”三个独立概念。旧决定移到历史记录并明确失效，不继续使用现在时描述。

### 3.2 Milvus 门槛通过后的处理规则没有闭合

**性质：已确认的规则与状态解释缺口。优先级：高。**

证据：AGENTS 第 14 节写五条门槛已有通过证据，但仍保持默认 `local`、Milvus 为 `Partial`；ADR-0002 第 5 节规定五条满足后可以标为 `Implemented` 并切换默认。

保持保守状态可以合理，但目前缺少明确说明：已有证据为什么尚不足以触发状态或默认配置变化。

影响：执行者无法判断应该切换默认、继续补证据，还是等待另一项批准。

建议：分别定义“集成测试通过、能力状态升级、默认配置切换、生产部署批准”的门禁，列出尚未满足的条件、负责人和对应任务。本报告不建议直接修改默认配置。

### 3.3 任务统计和当前推进顺序已经过期

**性质：已确认的事实漂移。优先级：高。**

本次实际解析结果：

| 来源 | 任务数量和状态 |
|---|---|
| tasks.yaml | 183 条：80 done、102 backlog、1 in_review |
| AGENTS 第 14 节 | 147 条 |
| 迭代指导文首、第 5 节 | 147 条 |
| Harness 规范第 20 节 | 104 条 |

影响：多个文件都描述“当前”，却指向不同快照，容易影响任务选择和阶段判断。

建议：任务状态只在 `tasks.yaml` 维护，统计自动生成。指导文件保留排序原则、入口链接和带日期的历史快照，不手工复制实时数量与大段完成记录。

### 3.4 README 内部存在默认配置矛盾

**性质：已确认的事实漂移。优先级：高。**

证据：README 默认配置说明和配置表写 `RAG_ENABLED=true`，能力表仍写“默认未注入对话”；`app/core/config.py` 中默认值为 `True`。

影响：AI 和使用者对默认对话行为的理解不一致。

建议：对文档中的默认值、配置名和能力表建立自动一致性检查。同一事实尽量保留一个维护源。

### 3.5 任务启动与状态流转不够明确

**性质：执行契约优化建议。优先级：高。**

四份文件要求“一次一条任务、检查依赖、获得要求的确认”，但没有集中定义：

- `backlog → ready` 的准入条件及批准人。
- 用户明确指定 backlog 卡时能否直接实施。
- 依赖未完成时，谁可以批准例外。
- `in_review → done` 需要哪些审核证据。

影响：有的 AI 会停在计划阶段，有的会直接开工，任务执行缺乏一致性。

建议：增加任务状态迁移表，明确每次迁移的执行人、必备证据和阻断条件。在任务卡中结构化记录批准、批准范围及依赖例外。

### 3.6 任务完成、业务验收和发布合格需要分开表达

**性质：完成语义优化建议。优先级：高。**

证据：AGENTS 通用 DoD 要求相关验证通过；第 14 节记录 `REL-003` 为 done，但发布检查失败。对照任务卡，`REL-003` 的交付是执行并记录门禁结果，因此 done 本身可以成立。

问题在于规则未说明任务类型差异，容易将“记录工作完成”误解为“发布合格”。

建议明确：

- 记录型任务：检查执行完整、报告可信即可完成。
- 实现型任务：验收断言必须通过。
- 发布资格：另行判断，不能由任务 done 推导。
- 人工验收未完成时：保持 `in_review`，记录待验收事项及责任人。

### 3.7 确认要求与停止条件容易引发过度暂停

**性质：执行规则优化建议。优先级：中。**

证据：迭代指导第 8.4 节提示词要求“得到确认后再修改”；AGENTS 第 12 节包含“无法证明最终业务结果就停止”。

对普通实现任务，最终结果通常要在实施后才能验证。现有表述可能被理解为开工前必须证明结果，或每次都重新请求计划批准。

建议：明确哪些方向性和高风险决策必须批准，哪些可在已授权范围内自主处理。将相关停止条件明确为“缺少必要的验收条件，且无法通过当前授权范围补齐”。已经批准的计划应有授权延续规则，避免反复确认。

### 3.8 Brownfield 渐进治理与强制要求之间缺少适用边界

**性质：规则适用范围优化建议。优先级：中。**

证据：Harness 规范第 7 节将时间、成本预算和步骤关联等列为 MUST，同时承认这些能力尚未补齐；第 18 节要求进入相关开发前处理、登记或阻断已知差距。

影响：修改一个小功能也可能被要求补齐整套运行时治理，扩大任务范围。

建议：为规则补充“适用对象、触发条件、当前最低要求、目标要求”。存量差距关联治理卡；本次修改不得扩大差距，但无需自动承担整项历史债务。安全红线仍必须执行。

### 3.9 测试与 Evaluation 要求需要按变更类型细化

**性质：验证规则优化建议。优先级：中。**

证据：

- AGENTS 第 9 节对每项任务要求先写失败测试或 Evaluation Case，但文档评审、调查和门禁记录并不都适合失败测试。
- 迭代指导第 7.5 节要求每条答案有 `exact_quote`，未明确无答案、拒答和升级案例如何证明预期。
- 第 7.4 节的私有资源案例要求，需要与当前“资源 ACL 为 Planned”的能力边界分开。

建议：建立按变更类型选择验证的矩阵：文档使用链接和事实检查，确定性逻辑使用单元/契约测试，模型行为使用版本化 Evaluation。无答案案例记录语料快照和核验范围；未实现的目标权限案例单独标识，避免混入当前验收结论。

### 3.10 文档分工与自动检查不足

**性质：已确认的维护问题及优化建议。优先级：中。**

AGENTS 包含大量进度日志、类型检查复盘细节和机器路径；迭代指导保留历史排期及重复提示词；Harness 规范再次复制任务进度；README 也承担部分内部治理规则。多个维护源增加了同步成本。

另有两个具体问题：

- README 配置表被限流说明正文打断，后面三行无法正常延续原表。
- README 称支持六种切分模式，而策略工厂注册了十种。应注明只列常用模式，或补齐清单。

建议采用以下分工：

| 文件 | 主要职责 |
|---|---|
| AGENTS.md | 短而稳定的执行规则、优先级、停止条件、文档入口 |
| AI辅助开发迭代指导.md | 任务实施方法、验证方法和按需阅读指引 |
| agent-harness-engineering.md | 架构边界、工程契约、渐进治理与例外机制 |
| README.md | 安装、使用、配置、当前能力与限制 |
| tasks.yaml | 任务状态、依赖、范围、验收和证据索引 |

## 4. 建议优化顺序

1. 修复 Milvus 定位、门槛解释、任务统计和 RAG 默认值等事实冲突。
2. 明确任务准入、状态迁移、审批、依赖例外和人工验收契约。
3. 按任务类型明确完成条件、验证要求及治理规则适用范围。
4. 精简重复进度和历史内容，按文档职责保留维护源。
5. 增加任务统计、文档链接、默认配置、能力清单等自动一致性检查。

上述建议尚未拆成任务卡，也未获实施批准。如后续实施，应按项目规则一次推进一条边界清晰的任务，并先落盘实现计划。
