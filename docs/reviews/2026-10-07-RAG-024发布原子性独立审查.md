## 4. 发现的问题

### F-01（Medium）外部索引补偿的覆盖方向与实际写操作相反：真实发生外部写的两条路径都没有记录

**可复现证据**（`.workbuddy/tmp/rev024-review/test_rev024_adversarial.py`，注入 `SpyExternalStore` 记录调用）：

```
[F] 重解析成功 status=success
[F] 外部库调用=['delete_by_document']  （delete 已真实发生且不可回滚）
[F] trace 数=0 stages=[]

[J] job status=failed
[J] 外部库调用=['delete_by_document']  （delete 已不可逆地执行）
[J] trace stages=['import_job']          ← 没有 external_index_compensation
```

对照「新版发布」路径（每一次成功都记一条，但整条路径从未触碰外部索引，见 F-04）：

```
[E] 第1次成功 status=success 外部库调用=[]
[E] 全库 compensation trace 数=2
```

**分析**
1. `_process_job` 的重解析分支在 `import_jobs.py:515-527` 提前 `return`，补偿记录块（`:551-562`）被绕过 → 外部模式下**重解析成功**不留任何记录，尽管 `service.py:1031` 已不可逆地删掉了该文档在外部索引里的全部向量。
2. `service.py:1030-1037` 的 `ImportTraceError` 包装**只覆盖 `delete_by_document` 本身抛错**。反例 J 表明：若外部删除已成功、其后主库写入/提交失败，`session.rollback()` 只回滚主库，外部索引已删的数据无法找回，而追踪记录只写到通用 `stage="import_job"`，没有 `external_index_compensation` 标记。这正是本卡承诺「外部索引补偿有记录」最该覆盖的场景。
3. 结论：验收项 3 只在新版发布路径上成立（而该路径当前根本不写外部索引），并未覆盖真正产生外部写操作的路径。**建议**：要么把记录扩展到「重解析成功」与「外部删除成功后的任何失败」，要么在验收里显式写明本卡只负责新版发布路径。

> 注：第 2 点的外部写操作本身先于本卡存在，本卡只是未把它收进补偿记录；因此定级 Medium 而非 High，但它是「验收是否真的达成」的判断依据。

### F-02（Medium）「一组一当前版」的部分唯一索引在实际运行库中不存在，缺少数据库层兜底

**证据**

```
[I] rag_documents 索引: [...只有 ix_* 单列索引，无 uq_rag_documents_one_current_version]
[L] 默认测试库 索引含唯一当前版约束: False
```

**成因**：`alembic/versions/d4e8b1c7a902_one_current_document_per_group.py` 建立了部分唯一索引，但 `app/core/migration.py:355-381` 的 `_stamp_if_schema_already_at_head()` 在检测到「导入平台三张表已由 `create_all` 建出且配额列齐备」时直接 `stamp(head)`，不执行增量迁移；随后 `auto_migrate` 走到 `pending 为空` 分支只调用 `_ensure_rag_schema_columns()`，而该函数（`migration.py:204-265`）只补 `ix_*` 索引，**不补这个唯一约束**。任何由 `SQLModel.metadata.create_all()` 起来的库（含本次回归临时库与默认 `data/test_ai_assistant.db`）都缺这个约束。

**影响**：验收「成功只一个 current」目前**仅靠应用层单事务逻辑**（`demote_other_current_versions` 的 SELECT+UPDATE）保证，没有数据库兜底。RAG-013 设计文档里「这样部分唯一索引仍然只允许一个当前版」的前提在这些库上不成立。属**既有问题（RAG-013 遗留），本卡未引入也未修复**，但直接决定了本卡验收项的强度。

### F-03（Low）发布已提交之后新增了一段可抛错代码，存在「已发布却报失败」的窗口

**证据**（反例 G：把 `app.rag.vectorstore.factory.get_vector_store` 注入为抛错）

```
[G] job status=failed error=发布后取向量库失败
[G] 版本数=2 current 数=1
    v2 is_current=True state=published   ← 新版本已原子提交且不可回滚
[G] trace stages=['import_job']
```

**分析**：`ingest_parsed_document` 内部（`service.py:432`）已提交，其后 `import_jobs.py:551-562` 若抛异常，任务会被标记为 `FAILED` 并记录失败追踪，而实际发布已经生效。旧实现在这一点上更「干净」——提交之后只有两行赋值，不可能抛错。当前 `MilvusVectorStore.__init__` 是惰性的、 `_record_external_index_compensation` 只是 `session.add`，实际触发概率低，故定级 Low。另需注意：若 URL 任务在此窗口失败，`except` 分支的 `_drop_attempt_source`（`import_jobs.py:582/589`）会删掉本次拉取的源文件，而新版本文档的 `storage_path` 正指向它 → 悬空引用（FILE 任务无此现象，反例 G 实测源文件仍在）。

### F-04（Low）补偿记录无消费方、无去重与清理，外部模式下每条成功导入都会永久留一条

**证据**

```
[E] 第2次成功 status=success 外部库调用=[]
[E] 全库 compensation trace 数=2
    job=e5aa99b3 ... msg=外部索引待补偿：document=ee4a0f4b…；新版分块已写入主库，外部向量索引尚未确认同步
    job=4baed972 ... msg=…
```

补充静态事实：
- 全仓没有 `ImportJobTrace` 的读取方（`grep -rn "trace" app/api/routes/*.py` 零命中）→ 记录只能直连数据库查，运维面不可见。
- 全仓 `_vector_store.` 的调用只有 `service.py:1031` 一处 `delete_by_document`，**没有任何地方向外部向量库写入**（无 `store.add(...)`）→ 新版发布路径上的这条待补偿永远无法被「补偿成功」，也不会被清除或去重。

**影响**：消息措辞用了「尚未确认同步」的保守表述，不构成虚假断言；但会形成只增不减、无人消费、无法闭环的记录。建议后续（非本卡）补一个读接口或清理机制。

### F-05（信息级，需知会）旧版 `version_state` 由 `published` 变为 `replaced` —— 经取证**不构成** non_goals 违反

**结论：不是违反，是对既有产品语义的对齐；但需要在验收说明里显式知会。**

**证据链**

1. `docs/plans/plan_rag_013_version_states.md:41-46` 的语义表定义：`published` = 已发布，该版本组的当前版，`is_current=true`；`replaced` = 曾是当前版，被新的发布顶掉，`is_current=false`；且第 63 行明确「已替换：**只由发布时顶掉同组旧当前版写入**」。导入新版发布正是「发布时顶掉同组旧当前版」。
2. 反例 K（变异验证）：还原旧实现后，旧版变成 `is_current=False` + `version_state=published` —— 即**旧实现自己制造了违反 RAG-013 语义表的不一致态**。
3. `app/core/migration.py:246-253` 的既有历史库修复逻辑，正是把 `NOT is_current AND version_state IN (NULL,'','published')` 的行批量改成 `replaced` —— 说明本仓库早已认定该形态应当归一为 `replaced`。
4. 反例 A：导入发布后版本形态（`v1 replaced/False`、`v2 published/True`）与手工 `POST /documents/{id}/publish`（`service.py:930-932`，同一 `demote_other_current_versions`）产出形态完全一致：

```
[A] 导入发布后各版本: v1 is_current=False version_state=replaced / v2 is_current=True version_state=published
[A] 手工 publish 后各版本: v1 is_current=True version_state=published / v2 is_current=False version_state=replaced
```

**仍需知会的可观测差异**：`service.py:819-820`，kb_admin 调用 `list_documents(version_state="published")` 时，以前能看到被导入顶掉、状态仍残留为 `published` 的旧版本，现在它们正确地归入 `replaced`。这是修正，不是回归。
