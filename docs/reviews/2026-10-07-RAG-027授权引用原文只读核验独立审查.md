## 1. 结论

**不建议关闭 RAG-027。**

实现本身**行为正确**：我自建的 14 条反例（换主体、范围收紧、文档转态、存在性对比、管理员后门、父块自动放行、控制面复用、注入、服务层直连、时效开关）**全部通过**，五条硬契约在当前代码上全部成立。简言之：**没有发现任何一个"当前就能被攻破"的缺陷，High 项为 0**。

不能关闭的原因是**三条承重契约没有被测试锁住**，变异证明它们可以被无声撤回：

1. **M-01（Medium）**：ADR-0007 §4 明文要求「来源标识和缓存文本不能充当授权证明、每次核验重新检查」，`docs/plans/implementation_rag_027_source_verification.md:91` 也把「不缓存」写成设计取舍。但「同一 `chunk_id` 先被有权主体核验成功、再被无权主体请求」这个方向**零覆盖**；我在 `_document_is_verifiable` 处植入"复用上次授权结论"的缓存后，**21 项专项测试全绿（21 passed / exit=0）**。
2. **M-02（Medium）**：ADR-0007 §5 要求未生效/已过期版本不得通过普通引用核验读取。该情形唯一落在 `_document_is_verifiable()` 的 `RAG_EFFECTIVE_DATE_FILTER` 分支（`app/rag/evidence.py:118-120`），而开关默认 `False`（`app/core/config.py:166`）且**没有任何测试打开它**。删掉整个分支后，027 套件与 RAG-026/access 套件合计 **42 passed / 0 failed**。把变异体与「开关打开」组合起来实测，这两种版本**真的被放行**了（证据见下方 M-02）。
3. **M-03（Medium）**：本卡最有争议的一条裁决（管理员是否绕过 uploader 限制）在代码里没有双向约束。给 `TENANT_ADMIN` 开后门会被抓红（✅），但**反向**去掉 `SYSTEM_ADMIN` 现有豁免后，全仓 **42 passed / 0 failed**，无人发现核验面与检索面就此脱钩。

三条都是**一两行测试**的量级，但按项目既定的门禁原则（"测试通过数不算证据，只有能被具体行为变异抓红的断言才算"），在补齐前关闭等于把 ADR-0007 的 §4、§5、§3 三条硬保证放到无回归保护的状态下。

另有 **6 条 Low**（其中 2 条也是"删了不变红"的覆盖缺口）与 **6 条 Info**。**没有 High。**

## 4. Medium（关闭前必修）

### M-01（Medium）「不缓存 / 每次请求重新鉴权」缺 allow→deny 方向的约束

**现象**：把 `_document_is_verifiable()` 的判定结果按 `chunk_id` 缓存并复用后，`tests/test_rag_027_source_verification.py` **21 passed / exit_code=0**。

**位置**：`app/rag/evidence.py:194-195`（判定点）；缺失的守卫应在 `tests/test_rag_027_source_verification.py:359`（`test_uploader_mode_peer_cannot_verify_owners_chunk`）附近。

**实测证据**（变异 M3，脚本 `.workbuddy/tmp/rev027/mutate.py`）：

```text
M3 exit=0  tail="21 passed in 14.34s"  failed_tests=[]
```

变异体为：

```python
# app/rag/evidence.py:194（变异期间）
    if _PREV_OK.get(chunk_id):  # MUTATION-M3 复用上次授权结论
        pass
    elif not _document_is_verifiable(doc, user, moment):
        raise EvidenceDeniedError("document not verifiable for subject")
    _PREV_OK[chunk_id] = True
```

即：**owner 先核验成功 → peer 再请求同一 `chunk_id` → 拿到 owner 的正文**，而 21 条测试一条都不红。

**为什么现有测试抓不住**：唯一的双主体用例 `test_uploader_mode_peer_cannot_verify_owners_chunk`（:359-374）的顺序是 **peer（被拒）→ owner（通过）**，成功结果后面没有任何第二次请求。`test_soft_deleted_document_is_denied`（:233）等正反对照也都先走被拒的一方。

**危害**：ADR-0007 §4 的核心就是「来源标识和缓存文本不能充当授权证明」；ADR-0001 §10 更直接要求「切换范围须使缓存重新授权/失效，不能沿用越权缓存」。这条与缓存直接相关的缺陷是最容易被"为了性能加个缓存"顺手引入的一类，且一旦引入，危害期会从"权限变化立即生效"变成"最长缓存期内持续越权读"。

**建议修法**（最小两步）：
1. 在 `test_uploader_mode_peer_cannot_verify_owners_chunk` 末尾补反向顺序的断言，或新增一条 `test_previous_verification_is_not_reused_for_another_subject`：owner 先 200、peer 后 404，**同一个 `chunk_id`、同一个进程**。
2. 再补一条「同一主体在同一进程内两次请求，中间把文档置为软删」：第二次必须 404（我在探针 `test_a1_document_state_change_is_effective_immediately` 里已写好可用版本）。

### M-02（Medium）时效分支（`RAG_EFFECTIVE_DATE_FILTER`）全仓零覆盖

### M-03（Medium）管理员语义只有单向约束，核验面 = 检索面这条不变量没有被钉住

**现象**：`can_read_document()` 里去掉 `SYSTEM_ADMIN` 豁免（即收紧管理员）后，027 + RAG-026 + access 三套用例 **42 passed / 0 failed**（定向变异 E1）。反向"给 `TENANT_ADMIN` 开后门"才会变红。

**位置**：`app/rag/access.py:79-80`（`can_read_document` 的豁免）与 `app/rag/access.py:57`（`read_scope_for` 的豁免）——**两处必须同真同假**，但没有人守住这个耦合。

**实测证据**：

```text
M1  （给 TENANT_ADMIN 开后门）        exit=1  1 failed  test_uploader_mode_tenant_admin_is_not_exempt
M1b （去掉 SYSTEM_ADMIN 豁免）        exit=0  21 passed
E1  （M1b 放到 026 + access 用例集）  exit=0  42 passed in 163.77s
A3  探针：{"peer":404,"tenant_admin":404,"system_admin":200}
     检索面命中：{"system_admin":true,"tenant_admin":false}
     can_read_document：{"peer":false,"tenant_admin":false,"system_admin":true}
     read_scope_for().uploader_id：{"tenant_admin":"a3-tadmin","system_admin":null}
```

**危害**：`can_read_document`（行级判定，核验用它）与 `read_scope_for`（SQL 过滤，检索用它）是**两个函数**。E1 的变异在法律上是"合法收紧权限"，但它直接制造了「检索能命中却不能核验」——这正是 ADR-0007 想消灭的、会把调用方逼向控制面详情接口的旁路诱因（`docs/plans/implementation_rag_027_source_verification.md:83-85` 自己论证过这个因果）。而这一现象在 42 条测试里没有一条会发现。

反向同样重要：`read_scope_for` 与 `can_read_document` 是两个独立函数，任何人改动其中一个都必须同步另一个，而这项目前**纯靠人自觉**，没有任何一条测试把「两个函数对同一角色给出同样结论」钉住。

**建议修法**（不需要改任何业务行为）：新增一条不变量用例，对 `MEMBER(owner) / MEMBER(peer) / TENANT_ADMIN / SYSTEM_ADMIN` 四角色逐个断言

```python
assert (检索能否命中该块) == (evidence 能否返回 200)
```

（检索侧用 `RAGService.search` 实测而非只读 `can_read_document`，否则等于用实现验证实现。）探针 `.workbuddy/tmp/rev027/probe_test.py::test_a3_admin_backdoor` 已把四个角色的取值方式跑通，可直接改成参数化断言。这样两个方向的偏移都会变红，同时把"I-02 里那条历史偏差"固定成可执行的决定。

### L-04（Low）核验结果的浏览器端缓存不随登出失效

`frontend/src/api/rag.ts:137-146`：`useChunkEvidence` 用 react-query，`staleTime: 60_000`、`retry: false`，queryKey 只有 `['chunk-evidence', chunkId]`（**不含用户维度**）；`frontend/src/store/auth.ts:42-44` 的 `logout()` 只清 token，**没有 `queryClient.clear()`**（全仓 `grep -rn "queryClient" frontend/src/main.tsx | head` 只有构造处）。
后果：同一浏览器会话换账号后 60s 内（gcTime 内更长）再展开同一 `chunkId`，会先显示上一账号拿到的原文，之后才可能 refetch。后端每次仍会重新鉴权，所以不是越权读，只是**已读内容的跨账号残留**。这是仓库既有模式（文档列表、分块列表同样如此），本卡新增了这一条。
**建议**：`logout()` / `reset()` 里 `queryClient.clear()`，或把 `userId` 并入所有 RAG 查询的 queryKey。

```text
delta(forbidden-missing)=0.4395ms  pooled_sd=4.3244ms  cohens_d=0.102
single-sample 错分率: missing 判成 forbidden=37.50%, forbidden 判成 missing=37.50%
```

成因直观：命不存在的 ID 时 `:182-184` 少一次 `session.get(Document)`，少一次 SQL。单次请求基本不可分（错分率 37.5%、Cohen's d 0.10），但大样本均值可分离约 0.44ms。ADR-0007 §4 要求"不返回正文或存在性细节"，这里的严格解读也包含"不提供区分手段"。
**建议**：不要求做到严格等时（代价大且收益低），二选一 —— ① 在错误路径上也做一次等价查询把两条分支的语句数对齐（几行）；② 在实现文档 §5 如实登记这个已知残留，并约定"存在性只能通过是否返回正文来判定"。我倾向②。

### I-02（Info）实现现状与 ADR 字面的偏差：`SYSTEM_ADMIN` 在 uploader 模式下是被豁免的

## 4. 新增用例的可证伪性核验（不是"看着对"就行）

**M-03 的期望取值表是否落实** —— **落实了**，这是本轮我核得最细的一条：

```python
# tests/test_rag_027_source_verification.py:55-62
_EXPECTED_FACE: dict[str, dict[str, bool]] = {
    "tenant": {"owner": True, "peer": True, "tenant_admin": True, "system_admin": True},
    "uploader": {"owner": True, "peer": False, "tenant_admin": False, "system_admin": True},
}
# :892  两面同真同假
assert retrieval == verified, f"{scope} 核验面与检索面脱钩：检索={retrieval}，核验={verified}"
# :896  同时钉住期望取值，防「全都不可见」也能通过等价断言
```

有 `:896` 这一行，"把所有角色都变成不可见"这种偏移**不可能**通过——那正是我上一轮担心的真空通过。取值表本身也与 RAG-026 CE-1 记录一致（`SYSTEM_ADMIN=True`、`TENANT_ADMIN=False`）。

**同时确认检索侧不是"用实现验证实现"**：用例用 `RAGService.search(...)` 真实检索（:884-886），不是只读 `can_read_document`。

### R2-1（Low，不阻断）等价性用例的第二个循环泄漏了第一个循环的变量

```python
# tests/test_rag_027_source_verification.py:845-874  ← 循环一：按 scope 建 tenant/marker/roles 并 ingest
    for scope in (_TENANT_SCOPE, _UPLOADER_SCOPE):
        ...
        tenant = f"rag027-equiv-{scope}-{uuid4().hex[:8]}"
        marker = f"RAG027EQ{uuid4().hex[:10]}"
        ...
        target_chunk_id = chunk_id.id
# :876-889  ← 循环二：重新声明 observed 后直接用 tenant / marker / roles / target_chunk_id
    observed: list[str] = []
    for scope in (_TENANT_SCOPE, _UPLOADER_SCOPE):
        monkeypatch.setattr("app.rag.access.settings.RAG_KB_SCOPE", scope)
        expected = _EXPECTED_FACE[scope]
```

循环二**没有重新创建数据**，因此它两次迭代用的都是循环一最后一次（uploader）留下的 `tenant / marker / roles / target_chunk_id`：标称的「四角色 × 两种范围」实际是「同一份 uploader 数据集 × 两种范围」。

**约束力是否因此丢失？没有** —— 我用 M10（把 tenant 模式改成本人可见）实测：该用例仍然变红（15 红之一），因为角色与 scope 都是真实的，检索/核验两侧都会随之改变，且 `expected` 的 tenant 行是"四角色同 True"，偏移后必然不等。所以这是**整洁性问题，不是门禁漏洞**。

**建议**（顺手可做，不必单独开卡）：把两个循环合成一个，或在循环二里重建数据，让"两种范围各自一份数据集"名副其实；否则下一个人读这段代码会误以为 tenant 半边验的是 tenant 数据集。
