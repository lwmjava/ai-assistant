## 1. 结论

**不建议关闭。**

护栏的**主链路**做得扎实：`chat()` 与 `stream_chat()` 都在发请求前核对同一条不等式，`intent`/`fallback` 各跳按自己的 `base_url + model` 现解析，工具返回与 critique 轮次因按真实 messages 现算而天然计入，被拦下的调用实测 0 次 HTTP，兜底链不把预算错误当可恢复故障，用户可见文案不含异常原文/模型名/计数，日志不含请求正文与 base_url。内置能力表的三个数字我联网核对过厂商当前页面，**全部属实**，登记行为本身没有越过「不猜未知上限」这条红线。

但有三项必须修完才能关：

1. **两个提交本身跑不起来**——`app/core/config.py` 的五个设置项只存在于工作树，没有进任何提交；在 `b27fde8` 的干净检出里 `settings.LLM_CAPABILITY_GUARD_ENABLED` 直接 `AttributeError`，即每次真实调用不是被拦而是崩。
2. **「每次实际 payload Guard」有一处真实缺口**——云 OCR 视觉调用（`app/rag/ocr/openai_vision.py`）直接 `httpx` POST `/chat/completions`，完全绕过 `OpenAICompatibleProvider`，实测护栏参与 0 次、HTTP 1 次，而它送的是 base64 图片，是系统里最大的单次生成 payload。
3. **运营者声明通道有两个口子**，合起来可以让一行配置把护栏整体失效：声明不绑定部署（与实现自己在 `capabilities.py:4-5` 立的「部署参与身份」不变式自相矛盾），且声明值没有任何合理区间。

另有一项**覆盖盲区**：官方计数器分支零有效覆盖——变异「去掉只认 `api.openai.com` 的限定」完全存活，因为 tiktoken 未安装时该分支永远提前返回 `None`，现有断言是空跑。

发现统计：**High 3 / Medium 5 / Low 6**。Embedding 侧不并入统一表的决定我**认可**（理由见 §6），但它没有落到卡面，属于台账缺口而非设计错误。

## 4. 发现清单

### High（3）

#### H-01 两个提交不包含 `app/core/config.py`，干净检出下每次真实调用都崩

`app/llm/openai_compatible.py`、`app/llm/factory.py`,`app/llm/capabilities.py` 都读 `settings.LLM_CAPABILITY_GUARD_ENABLED` / `LLM_CAPABILITY_DECLARED` / `LLM_CAPABILITY_DECLARED_SOURCE` / `LLM_BUDGET_SAFETY_MARGIN` / `LLM_OUTPUT_RESERVE_TOKENS`，但这五个字段只在**工作树**里，没进 `86acb26` 也没进 `b27fde8`：

```bash
$ git show b27fde8:app/core/config.py | grep -c LLM_CAPABILITY
0
$ git diff 671901f..b27fde8 -- app/core/config.py      # 空
$ git diff --stat -- app/core/config.py                # 工作树 14 行新增未提交
```

在 `b27fde8` 的干净 worktree 里实测：

```
RESULT=BROKEN AttributeError: 'Settings' object has no attribute 'LLM_CAPABILITY_GUARD_ENABLED'
```

后果不止「跑不起来」：`Settings` 是 `extra="ignore"`（`app/core/config.py:26-30`），所以在一台没有那 14 行的机器上，运维按 `.env.example` 填的 `LLM_CAPABILITY_DECLARED=...` 会被**静默忽略**——护栏照旧拒绝一切，而放行开关看起来「填了却没用」，排障方向被彻底带偏；另一侧，已带 14 行的机器则每次真实调用先撞 `AttributeError`，是崩不是拦。

必修：把 `app/core/config.py` 的改动并入 RAG-028 的提交（或补一个提交），使 `b27fde8..` 任一点检出可用。

#### H-02 云 OCR 视觉生成调用完全绕过 Guard

`app/rag/ocr/openai_vision.py` 不走 `LLMProvider`，直接拼 `/chat/completions` 请求体并 `httpx` POST（`app/rag/ocr/openai_vision.py:60-73` 异步、`:76-92` 同步），`app/llm/*` 的护栏完全不参与。反例 CE-6 实测：

```
CE-6 实际结果：HTTP=1 budget调用=0 返回={'choices': [{'message': {'content': '完成'}}]}
```

它送的 payload 是 `data:image/png;base64,...`（`app/rag/ocr/openai_vision.py:14-32`），是系统里**最大的单次生成 payload**，恰恰是最需要预算核对的那一类；而它回落到 `LLM_BASE_URL / LLM_API_KEY / LLM_DEFAULT_MODEL`（`app/core/config.py` 云 OCR 段注释），即与对话同一个 deployment，却不受同一套窗口约束。

当前 `RAG_OCR_ENABLED=False`、`RAG_OCR_PROVIDER="tesseract"`（`app/core/config.py:184-185`），所以缺口是休眠状态——但 `app/rag/` 在本卡 `allowed_paths` 内，运营者一旦开启 `cloud` 就是无护栏的真实外发调用。

必修二选一：让云 OCR 走 `OpenAICompatibleProvider`（或至少显式调一次 `enforce_generation_budget`）；或在本卡明确记一条「该路径不在本卡范围」并把统一纳入单开卡，同时在 `RAG_OCR_PROVIDER=cloud` 的入口打一条「未纳入预算护栏」的告警。

#### H-03 声明通道两个口子：不绑定部署 + 无合理区间

`declared_capability` 按**模型名**登记、`deployment` 恒为 `"*"`，且只校验 `> 0`：

```python
# app/llm/capabilities.py:30-31
OPERATOR_DECLARED_DEPLOYMENT = "*"
# app/llm/capabilities.py:206-211
context_window = int(window_text.strip()); max_output_tokens = int(output_text.strip())
if context_window <= 0 or max_output_tokens <= 0: return None
```

反例实测：

```
CE-1 声明 huge=1000000000:999999999 → 5,000,000 字符 payload 被放行，HTTP=1
CE-4 为 gateway-a 声明 shared-model=32768:4096 → evil-gateway.example 上同名模型同样拿到 32768
```

第二个口子与实现自己写下的不变式直接冲突：

> `app/llm/capabilities.py:4-5`：部署参与身份……窗口不能跟着模型名一起被借走

内置表守住了这条，声明通道没有。后果是「未知模型无批准配置拒绝」可以被一行配置整体绕过：声明一次，任何部署上的同名模型都拿到同一个（可能是 1e9 的）窗口，且没有上界告警。`README.md` 与 `.env.example` 只写了声明格式，**没有说明声明按模型名生效、不区分部署**，运营者会被误导。

必修（至少一项）：声明也带 deployment（格式扩成 `deployment|model=窗口:输出` 或单独一条按部署声明）；或对声明值设合理区间并在越界时告警拒绝；无论如何 `README.md` / `.env.example` 必须写明「声明按模型名生效，不绑定部署」。

### Medium（5）

#### M-01 Supervisor 编排把预算超限吞成「请稍后重试」

`AGENT_ORCHESTRATION=langgraph` 时 `ChatService._build_pipeline` 返回 `SupervisorGraph`（`app/services/chat_service.py:264-268`），而 `SupervisorGraph.run` 的编排级兜底不区分异常类型：

```python
# app/agents/supervisor.py:298-303
except Exception as exc:  # 编排级兜底
    logger.exception("Supervisor 编排执行失败")
    state.error = str(exc)
    if not state.answer:
        state.answer = "抱歉，多 Agent 协作处理时出现问题，请稍后重试。"
```

`ContextBudgetExceeded` 到这里就被换成一句诱导重试的文案，而重试必然再次被拦——与 `_failure_text`（`app/agents/pipeline.py:58-67`）给出的「请缩短输入或拆分后重试」正好相反。`app/agents/` 在 `allowed_paths` 内，且现有 29 条用例只覆盖 `AgentPipeline` 与 `ChatService` 两条路径。

必修：`supervisor.py` 复用 `_failure_text`（或对 `ContextBudgetExceeded` 单独分支），并补一条 `AGENT_ORCHESTRATION=langgraph` 下的端到端断言。

#### M-02 默认配置下「开箱即全量拒答」，且放行路径不够醒目

仓库自带 `.env` 是 `LLM_DEFAULT_MODEL=deepseek-chat` + `https://api.deepseek.com/v1`，不在内置表内；护栏默认 `True`。这不是 bug——它严格符合「未知模型无批准配置拒绝」——但意味着**默认环境升级后所有对话只剩一句固定提示**，而 `.env.example` 只在注释里给了示例值、`LLM_CAPABILITY_DECLARED` 默认为空。建链告警（`app/llm/factory.py:97-114`）能指路，但只在有 api_key 时触发。

必修：把「升级后必须做的第一步」写成 README 顶部的迁移步骤（含可直接复制的 `deepseek-chat` 声明值），并保证 `deepseek-chat` 这类已知默认模型在启动日志里给出可复制的那一行。

#### M-03 官方计数器分支零有效覆盖（存活变异）

`official_counter_for` 开头就限定部署：

```python
# app/llm/counters.py:67-68
if not (deployment or "").startswith("api.openai.com"):
    return None
```

变异 M6（把这两行改成永不返回）后 **29 条用例全绿**：

```
=== M6 官方计数器不再限定 OpenAI 官方域名 (app/llm/counters.py) ===
exit=0  汇总行: 29 passed
```

原因是 tiktoken 未安装，`official_counter_for` 永远在 `import tiktoken` 处提前返回 `None`，`test_official_counter_is_not_claimed_for_other_vendors` 断言的 `None` 无论变异与否都成立——这条断言是空跑的。「别家的 token 不用 OpenAI 的 tokenizer 数」这条规则因此没有任何可执行证据；一旦装上 tiktoken，该分支第一次被执行，而它从未被验证过。

必修：用 monkeypatch 注入一个假 `tiktoken`（或在 `sys.modules` 里塞桩）让官方计数器可达，再断言 deepseek/自建网关仍返回 `None`。

#### M-04 多模态 content 按 `str()` repr 计数，图片 token 完全不计

```python
# app/llm/counters.py:36-40
if isinstance(message, dict):
    return str(message.get("content") or "")
return str(getattr(message, "content", "") or "")
```

content 是 list/dict（OpenAI 多模态格式）时，计的是 Python repr 的字节数。反例 CE-5 实测：

```
CE-5 多模态消息估算=75
```

一条 `image_url`（短 URL）只算 75，真实是几百到上千 token——**方向是低估，而且低估得很彻底**。当前 `ChatMessage`（`app/llm/base.py:22-26`）只接受 `str`，所以生成侧暂时不会触发；但 `estimate_messages_tokens` 的签名是 `Sequence[Any]`、是公共入口，H-02 那条视觉 payload 一旦接入 Guard 就会踩中。

必修：`message_content` 遇到非字符串 content 时，要么按 `image_url` 显式加一个保守的每张图固定开销，要么直接拒绝（视为无法计数 → 按未批准处理）。

#### M-05 `errors="ignore"` 静默丢弃不可编码字符，计数被低估到 0

```python
# app/llm/counters.py:49
return len((text or "").encode("utf-8", errors="ignore"))
```

反例 CE-5 实测：

```
CE-5 孤立代理项字节数=0     # 1000 个不可编码字符计 0 字节
```

注释里写「避免计数本身把请求打挂」，方向可以理解，但这是**唯一一个明确低估**的路径，且与「宁可拦下也不放行」的自我定位冲突。触发条件罕见（孤立代理项等畸形串），所以定 Medium 而非 High。

必修：改 `errors="replace"`（按替换后的字节计），或显式拒绝含不可编码字符的输入。

| CE-10 100 条空消息 | 消息框架开销 | 计 403（3 + 100×4）→ **达成** |

**关于「UTF-8 字节估算会不会低估 token」的结论**（负责人点名要判断）：对 BPE 类 tokenizer，每个 token 至少对应 1 个字节，因此 **token 数 ≤ 字节数恒成立**，字节估算在原理上不会低估；CE-5 的 6 类常规输入全部印证这一点。真正的低估不在这条启发式本身，而在三处：**不可编码字符被 `errors="ignore"` 丢弃（M-05）、非字符串 content 只数 repr（M-04）、以及声明值本身的正确性无人校验（H-03）**。

## 6. 关于 Embedding 侧不并入统一表：明确表态

**我认可这个决定，它不应成为关闭的阻塞项。**

1. **ADR-0005 §9 把两者分开写**：「021 的特定 Embedding 护栏沿用，不能当成全部生成预算已实现」——ADR 本身就没有要求合成一张表。
