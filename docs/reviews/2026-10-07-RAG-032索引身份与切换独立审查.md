# RAG-032「Embedding 索引身份与切换治理」独立审查

- 审查日期：2026-10-07
- 审查提交：`671901f`（基线 `eaadade`）
- 审查角色：独立审查人，未参与实现
- 契约：`tasks.yaml` RAG-032、ADR-0008

## 1. 结论

**不建议关闭。** 当前实现只完成了索引登记表、Local 分块归属和部分写入阻断；同维异模型查询仍可命中旧向量，重建链路无法在旧索引继续服务时写入 preparing 索引，强行切换后又会删除旧索引分块，激活/回退校验可绕过，Milvus 路径没有接入身份治理，因而原始 acceptance 与 ADR-0008 的多项硬约束未达成。

发现统计：**High 6 / Medium 5 / Low 1**。仍有必修项；至少全部 High 必须修复并补端到端测试后才能关闭。

## 4. 发现清单

### High（6）

#### H-01 同维异模型只在写入侧阻断，查询侧仍会混用

代码路径：

```python
# app/rag/backend/native.py:49-60
embedding = (await self._embedding.embed([query]))[0]
hits = await self._store.hybrid_search(embedding, ...)

# app/rag/vectorstore/local.py:161-171
read_index = resolve_read_index(self.session, "local")
...
if len(query_embedding) != read_index.dim:
    raise IndexIdentityError(...)
stmt = stmt.where(col(DocumentChunk.index_id) == read_index.id)
```

`LocalVectorStore` 不接收当前查询 provider 的 identity；模型名不同但维度相同就通过。反例：先以 `model-a/dim=8` 建 active 索引并写一块，再用同类 `model-b/dim=8` 的 `RAGService.search()` 查询，当前代码没有拒绝且返回 A 的块。临时反例测试 `test_query_with_same_dim_different_model_is_rejected` 实测为红，错误显示返回一个旧 `ChunkResult`。

必修：在生成查询向量前/后，将**实际生效 provider 的完整 identity**与 active index 比较；Local/Milvus/三种 RAG backend 共用同一不可绕过的校验点。

#### H-02 `rebuild` 无法向 preparing 索引写入；强行先切换又会删除旧索引数据

代码路径：

```python
# scripts/rebuild_embedding_index.py:203-205
index = ensure_index(session, identity)
index.status = IndexStatus.PREPARING.value

# scripts/rebuild_embedding_index.py:231-237
service = RAGService(session, doc.tenant_id, embedding_provider=provider)
asyncio.run(service.reindex_document_in_place(...))

# app/rag/index_registry.py:131-140
active = active_index(session, identity.backend)
...
if active.identity_key != identity.key():
    raise IndexIdentityError(...)
return active
```

脚本没有把 `index.id` 作为 rebuild 写目标传给服务；新 provider 与旧 active 不同会整批失败。若为了让写入成功而先激活新索引，`app/rag/service.py:1064-1088` 会删除旧块并只写新 `index_id`，旧索引登记行虽保留但数据为空。

反例 1：active=A、preparing=B、用 provider B 调 `RAGService._write_index()`，实际抛 `IndexIdentityError`，不能返回 B。反例 2：active=A 写文档，先激活 B 后重解析，旧 `index_id` 下分块集合由非空变为空。两条临时测试均红。

必修：提供明确的“写 preparing 目标”上下文，按新索引新增一套分块/外部向量而不是就地替换；完成校验前旧 active 继续读，回退后旧数据必须真实可读。

#### H-03 激活/回退可以绕过配套模型和完成度校验

代码路径：

```python
# app/rag/index_registry.py:93-115
target = session.get(EmbeddingIndex, index_id)
...
target.status = IndexStatus.ACTIVE.value
...
session.commit()
```

核心 `activate_index()` 对 target 原状态、`chunk_count`、实际分块数、身份、授权、抽样检索和故障校验均不检查，`preparing`、`failed`、空索引都能激活。脚本保护也不完整：

```python
# scripts/rebuild_embedding_index.py:80-85
if (index.model, index.dim, index.index_version) != (
    expected.model, expected.dim, expected.index_version,
):
```

这里漏掉 provider、deployment、backend、normalization、metric；`cmd_activate`/`cmd_rollback` 随即调用可绕过的 `activate_index()`（`scripts/rebuild_embedding_index.py:129-151`）。临时反例已证实：（1）空 preparing B 可直接替换 A；（2）provider/normalization/metric 全不符但 model/dim/version 相同，`_assert_config_matches()` 不抛错。

必修：完整身份比较和可激活状态/校验凭证必须下沉到不可绕过的领域入口，脚本只是调用者；失败索引和未完成索引不得激活。

#### H-04 Milvus 完全没有接入本卡的身份与 collection 切换治理

代码路径：

```python
# app/rag/vectorstore/milvus.py:64-74
name = settings.MILVUS_COLLECTION
fields = [..., FieldSchema(name="embedding", ..., dim=settings.EMBEDDING_DIM)]

# app/rag/vectorstore/milvus.py:103-108
existing = {f.name for f in (collection.schema.fields or [])}
if _DOCUMENT_ID_FIELD not in existing:
    raise MilvusUnavailableError(...)

# app/rag/vectorstore/factory.py:13-19
if settings.RAG_VECTOR_STORE.strip().lower() == "milvus":
    return MilvusVectorStore(session)
return LocalVectorStore(session)
```

Milvus 固定使用基础 collection 名，不使用 `EmbeddingIndex.name`；schema 无 `index_id`/身份元数据，`_verify_schema` 只检查 `document_id`，工厂不验证 active identity，`hybrid_search` 的 SQL 回查也不按 `index_id` 过滤（`app/rag/vectorstore/milvus.py:188-238`）。提交对 `milvus.py`、`factory.py`、三种 backend 均为零 diff。`MilvusVectorStore.add()` 仍无 `app/` 调用点，写链路断开这一事实在文档中有披露，但“Milvus 侧身份校验走 `_verify_schema` 扩展点”的声明（`docs/rag/索引身份与切换.md:98-99`）与代码不符。

此外父块复核也无 index 条件：`app/rag/service.py:722-747` 只检查 chunk/document/tenant/删除态；把 retired 索引的 stale hit 送入 `_expand_parent_chunks()`，临时反例实际返回该旧块。当前 Milvus 正会产生这种缺少 identity 约束的候选。

必修：RAG-015 可以继续承担 Milvus 真实写入闭环，但 RAG-032 作为其前置卡不能把索引身份校验留空；至少要有基于 active registry 的 collection 解析、完整身份校验、SQL 回查/父块复核和不可误报为已实现的测试。

#### H-05 无 active 登记时，未知历史分块被自动当作兼容数据检索

代码明确放宽：

```python
# app/rag/vectorstore/local.py:161-165
read_index = resolve_read_index(self.session, "local")
if read_index is None:
    # 尚未登记任何索引：保持未启用索引治理时的行为，避免存量库整体失检索。
    logger.debug(...)
```

此分支不加 `index_id` 条件，`index_id IS NULL` 的数据会直接参与检索；这与 ADR-0008 `:22` 及实现说明 `docs/rag/索引身份与切换.md:59-72` 的“默认不参与检索、显式 adopt”相反。专项测试还把放宽固化为期望：

```python
# tests/test_rag_032_index_identity.py:214-221
async def test_no_registered_index_keeps_legacy_read_behaviour(...):
    ...
    assert [h.id for h in hits] == [row.id]
```

反例：全新 registry + 一条 `index_id=None` 历史块，严格期望为空，实际返回该块。将代码变异为无 active 时 `return []` 后，上述官方测试变红，证明测试正在阻止 ADR 要求的严格行为。

必修：无 active identity 应返回明确 unavailable/需要登记状态，不能查询未知向量；升级流程应先显式 adopt 或重建。

#### H-06 `provider` 身份取实现类名，不足以区分真实服务提供商

```python
# app/rag/index_identity.py:109-124
model = str(getattr(provider, "model", "") or "unknown")
deployment = str(getattr(provider, "deployment", "") or "")
...
provider=type(provider).__name__

# app/rag/embeddings/factory.py:31-48
provider = settings.EMBEDDING_PROVIDER.strip().lower()
...
return OpenAICompatibleEmbeddingProvider(...)
```

除 Mock 外，配置的 OpenAI、Ollama 以及兼容服务都可落为同一个 `OpenAICompatibleEmbeddingProvider` 类；`OpenAICompatibleEmbeddingProvider` 保存 `base_url` 但不声明 `deployment`（`app/rag/embeddings/openai_compatible.py:32-38`）。两个不同兼容端点、相同 model/dim 的 identity key 实测完全相同。与此同时，脚本 `_identity()` 又使用配置字符串 `settings.EMBEDDING_PROVIDER`（`scripts/rebuild_embedding_index.py:60-70`），导致脚本登记的 provider 与运行时登记的类名不一致。

必修：定义稳定、可验证的实际 provider/deployment/revision 标识，并让运行时与脚本使用同一身份生产函数；不包含密钥，但必须能区分不同向量空间。

### Medium（5）

#### M-01 `adopt --confirm` 只有维度校验，没有当前配置核对或可追踪兼容证据

`cmd_adopt` 直接取 active index，只打印 `name/dim`，不调用 `_assert_config_matches`（`scripts/rebuild_embedding_index.py:155-176`）。`adopt_legacy_chunks` 仅解析向量并比较长度，随后批量回填 `index_id`（`app/rag/index_registry.py:168-195`）。因此模型 A 的未知历史向量与模型 B 同维时，只需 `--confirm` 就会被重新标为 B；确认人、依据、原模型/版本均未落 `notes` 或审计记录。

复现：active=B/dim=8，插入一条未知 A/dim=8 分块，执行 adopt；当前实现成功写成 B。必修建议：完整显示并校验当前有效配置，要求范围与证据输入并持久化；无法证明时只能 rebuild。

#### M-02 normalization/metric 只是身份标签，没有驱动实际写入/检索行为

`app/core/config.py:105-107` 和 `.env.example:94-100` 把 `EMBEDDING_NORMALIZATION` 描述为“写入前归一化方式”、metric 描述为可选约定；但 `RAGService._embed_texts()` 原样返回 provider 向量（`app/rag/service.py:632-639`），Local 无论配置为何都在查询时归一化并做点积（`app/rag/vectorstore/local.py:218-227`），Milvus 建索引/查询均硬编码 `COSINE`（`app/rag/vectorstore/milvus.py:118-127,136-144`）。配置可登记 `none/ip/l2`，实际算法却不变。

必修建议：要么只允许且校验当前真实约定，要么真正按配置执行；health/identity 必须报告实际行为，不能报告未生效配置。

#### M-03 历史隔离的可观察性不足，检索为空时终端用户没有提示

health 确实暴露全局 `legacy_chunks`（`app/api/routes/health.py:74-109`），实现文档也明确升级影响（`docs/rag/索引身份与切换.md:59-72`）；但：

- health 的整体状态只看数据库与向量库连接，identity `unknown` 或 `legacy_chunks>0` 仍返回 200/`ok`（`app/api/routes/health.py:112-138`）；
- Local 过滤后无行直接返回普通空结果，无 warning/状态原因（`app/rag/vectorstore/local.py:171-179`）；
- 唯一 `no_active_embedding_index` 日志是 DEBUG，且该场景反而继续读取历史块（`app/rag/vectorstore/local.py:162-165`）；
- README 只新增三个配置项（`README.md:404-408`），未写“升级后历史知识库会查不到”和 adopt/rebuild 步骤，违反实现计划 `docs/plans/implementation_rag_032_index_identity.md:164-171` 自己声明的文档门槛。

结果是 active 建立后若全是历史块，业务查询表现为正常 no-hit，只有主动查看 health 的运维人员才能发现。

#### M-04 19 条专项测试只覆盖局部组件，并固化了一个违背 ADR 的兼容分支
