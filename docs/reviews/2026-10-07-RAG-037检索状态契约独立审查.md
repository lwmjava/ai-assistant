## 总结论

**不建议关闭 RAG-037。**

四状态分类器对合法计数输入的优先级是唯一的，`HybridRetriever` 对“后端直接抛异常”的主路径也能产生 `unavailable`；同步、流式和短路径的披露提示接线基本存在，低分要求同时进入行动与最终响应阶段，少返回计数没有被注入块污染，HTTP 成功响应头可取得。

但验收核心仍有两个直接反例：

1. Milvus 搜索异常在向量库内部被吞成空列表，最终状态变为 `no_hit`，把“后端故障”伪装为“知识库无命中”。
2. 所谓“必须披露/最终拒答”只有模型提示，没有任何最终文本约束；一个忽略提示的合法 LLM provider 可在同步、流式、`ChatService.chat_stream` 和短路径上输出“根据知识库……”且原样返回、持久化。专项测试甚至明确接受故障场景的最终答案只是普通“答案”。

此外，后端返回 `None` 会在异常捕获范围之外触发 `TypeError`，langgraph + MULTI 的 Supervisor 完全不调用已注入的 retriever，均使状态契约不闭合。

## 逐条取证

### F-01（High）Milvus 故障被错报为 `no_hit`

**断言**

`HybridRetriever.retrieve()` 只能识别从 `backend.retrieve()` 抛出来的异常。Milvus 的 `hybrid_search()` 在 `collection.search()` 失败时自行捕获任意异常并返回 `[]`，所以故障到达 `HybridRetriever` 时已经不可区分于真实零命中。

**源码证据**

- `app/rag/vectorstore/milvus.py:202-216`：`except Exception` 后记录 `fallback=empty` 并 `return []`。
- `app/rag/backend/native.py:49-62`：Native backend 原样接收向量库返回并传给 `drop_injected_chunks`。
- `app/rag/retriever.py:96-115`：基于 `len(results)` 分类；空列表且无 `error_type` 必然成为 `no_hit`。
- `app/rag/retrieval_status.py:88-94`：只有非空 `error_type` 才会成为 `unavailable`。

**独立实测**

向 `MilvusVectorStore` 注入一个 `search()` 抛 `RuntimeError("milvus-search-down")` 的 collection，再走真实 `NativeRagBackend -> HybridRetriever`：

```text
rag_vector_search_failed backend=milvus fallback=empty exception_type=RuntimeError
milvus_swallow={"output": "", "status": "no_hit", "error_type": "", "notice_is_no_hit": true, "notice_is_unavailable": false}
```

原始输出：`.workbuddy/tmp/rev037-review/rev037_probe_output.txt:50,76-77`。

**判断**

这是本卡验收阻断项。文档只记录了 Milvus 相似度恒为 1.0，却没有记录搜索异常被伪装为 `no_hit`；见 `docs/rag/检索状态与拒答契约.md:75-84`。

### F-02（High）最终回复不保证披露或拒答

**断言**

实现保证的是“提示里有要求”，不是“最终回复明确提示”。只要模型忽略要求，模型输出会未经校验直接成为 `state.answer`、流式 token 和数据库正文。因此“故障不冒充知识回答”和“低分最终回复验收”都没有形成确定性契约。

**源码证据**

- 自研管线把 directive 放在 user 内容：`app/agents/pipeline.py:370-398`、`app/agents/pipeline.py:445-459`；`_messages()` 的 system 仍只是阶段 system，见 `app/agents/pipeline.py:304-308`。
- 同步最终答案直接取模型返回：`app/agents/pipeline.py:525-529`。
- 流式最终答案直接拼接模型 delta：`app/agents/pipeline.py:750-758`。
- 短路径也直接拼接模型 delta：`app/agents/fast_path.py:50-70`。
- `ChatService.chat_stream` 收到 `done` 后直接持久化收集到的 token，没有按 `retrieval_status` 校验：`app/services/chat_service.py:382-405`。
- 专项测试仅断言 prompt 含 notice，并明确允许 `state.answer == "答案"`：`tests/test_rag_037_retrieval_status.py:167-188`。

**独立实测**

使用一个始终忽略披露、返回“根据知识库，员工年假固定为 5 天。”的 LLM：

```text
sync={"status": "unavailable", "answer": "根据知识库，员工年假固定为 5 天。", "notice_prompt_calls": 2, "answer_contains_notice": false}
run_stream={"status": "unavailable", ..., "last_event": "done", "answer": "根据知识库，员工年假固定为 5 天。", "notice_prompt_calls": 2, "answer_contains_notice": false}
chat_service_stream={..., "last_event": "done", "done": "根据知识库，员工年假固定为 5 天。", "persisted": ["根据知识库，员工年假固定为 5 天。"], "notice_prompt_calls": 2, "final_notice_role": ["user", "user"]}
fast_path={"route": "rag", "status": "unavailable", "last_event": "done", "notice_in_system": true, ..., "answer": "根据知识库，员工年假固定为 5 天。"}
below_threshold={"status": "below_threshold", "directive_in_action": true, "directive_in_respond": true, ..., "answer": "根据知识库，员工年假固定为 5 天。", "answer_contains_refusal": false}
```

原始输出：`.workbuddy/tmp/rev037-review/rev037_probe_output.txt:57-64`。

**判断**

流完整结束、提示确实进入模型，但最终回复仍能违反契约。这不是“模型质量问题”：验收措辞是“最终回复明确提示/不冒充”，强制语义不应委托给可不服从的外部模型。`below_threshold` 宜直接返回固定拒答；`no_hit/unavailable` 至少应由应用层确定性追加披露，流式也要以固定 token 前缀或受控终态实现。

### F-03（Medium）Supervisor 是真实入口缺口

**断言**

文档“Supervisor 从不检索”的事实属实；但将其列为“不在本卡范围”不足以通过入口验收。`AGENT_ORCHESTRATION=langgraph` 且 `RouteKind.MULTI` 时，`ChatService` 确实构造 `SupervisorGraph` 并传入 retriever，图却完全不调用它，状态为空。Supervisor 的调度提示甚至写“调用工具/检索进一步调研”，实际 research worker 明确不检索。

**源码证据**

- MULTI 不走 fast path：`app/services/chat_service.py:208-215`。
- langgraph 分支把 retriever 传给 Supervisor：`app/services/chat_service.py:250-266`。
- Supervisor 只保存 `self.retriever`：`app/agents/supervisor.py:96-109`；全图节点无调用。
- research worker 只调用 LLM：`app/agents/supervisor.py:163-184`。
- draft prompt未使用 `state.context`，也没有知识来源约束：`app/agents/supervisor.py:186-207`。
- 文档承认该缺口：`docs/rag/检索状态与拒答契约.md:75-84`。

**独立实测**

```text
supervisor={"route_kind": "multi", "fast_route": null, "retriever_calls": 0, "retrieval_status": "", "answer": "根据公司的内部制度，员工年假固定为 5 天。"}
```

原始输出：`.workbuddy/tmp/rev037-review/rev037_probe_output.txt:70-71`。

**判断**

会产生“冒充知识回答”的可达链路，应算本卡验收缺口。至少需要二选一：让 Supervisor 调用 retriever 并传播 `RetrievalOutcome`；或明确将 MULTI 定义为非检索入口，同时从调度/撰写提示中移除“检索/内部依据”暗示并禁止声称使用知识库。

### F-04（Medium）异常收敛边界不完整：`None` 与自定义 Retriever

**断言**

`HybridRetriever` 的 `try` 只包住 `await backend.retrieve()`；返回值验证、阈值过滤和计数在 `try` 外。后端返回 `None` 时抛 `TypeError`，`last_status` 仍是构造时的 `no_hit`。此外，管线协议允许任意 Retriever，但 `_fill_retrieval()` 不收敛其异常，只有外层通用兜底，结果是请求级通用失败而非 `unavailable`。

**源码证据**

- 捕获范围结束于 `app/rag/retriever.py:82-95`，对返回值的迭代在 `app/rag/retriever.py:96-99`。
- 初始状态预设为 `no_hit`：`app/rag/retriever.py:58-64`。
- `_fill_retrieval()` 直接 await，无异常到状态转换：`app/agents/pipeline.py:422-436`。
- 同步/流式外层只给通用错误：`app/agents/pipeline.py:532-539`、`app/agents/pipeline.py:759-766`。
- 短路径反而对外部 Retriever 有正确的 `unavailable` 适配：`app/agents/fast_path.py:109-124`。

**独立实测**

```text
none_backend={"raised": "TypeError", "message": "'NoneType' object is not iterable", "last_status": "no_hit", "backend_calls": 1}
```

原始输出：`.workbuddy/tmp/rev037-review/rev037_probe_output.txt:52-55`。

**判断**

虽然 `RagBackend` 类型契约声明返回列表，运行期边界仍应把非法返回识别为 backend failure，不能保留误导性的旧状态。建议将返回值校验和过滤也置于收敛边界内；管线层同步采用短路径已有的外部 Retriever 兜底。

- HTTP 入口对空 query 直接 400，说明“空输入”并不等价于真实检索零命中：`app/api/routes/rag.py:946-947`。

**独立实测**

**判断**

### F-11（Medium）专项测试有价值，但不能证明验收闭环
