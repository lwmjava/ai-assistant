## 2. 受托判定的三个问题

### (1)「统一总时限」是否真的达成？——**部分成立**

真实的共享发生在 `app/rag/backend/native.py:75-89`，**不依赖** retriever 层绑定：

```
75:        deadline = current_deadline() or Deadline(settings.RAG_RETRIEVAL_DEADLINE_SECONDS)
78:        with bind_deadline(deadline):
80:                return await asyncio.wait_for(
81:                    self._retrieve(query, tenant_id, top_k, read_scope),
82:                    timeout=deadline.remaining(),
83:                )
```

`NativeRagBackend.retrieve` 自己建 deadline 并绑进 ContextVar，下游
`app/rag/embeddings/openai_compatible.py:71`（`current_or_new_deadline()`）与
`app/rag/vectorstore/milvus.py:286`（同）因此拿到**同一个实例**。
所以「嵌入 + 向量检索共享一个总 deadline」在**一次 `backend.retrieve`** 粒度上成立，
实测证据见探针 C2（§5 Low-01）。

但**「一次用户请求」粒度不成立**：调用方不绑定时，`native.py:75` 每次都走
「新起一个」分支，N 次检索 = N × deadline。实测（探针 A5）：

```
[A5] 不做请求级绑定时：一次「用户请求」触发多次检索的总耗时
      3 次检索，每次各自新起 0.4s deadline → 实测总耗时 1.204s,
      抛错=['DeadlineExceededError', 'DeadlineExceededError', 'DeadlineExceededError']
```

当前三条线上路径（`app/agents/fast_path.py:120`、`app/agents/pipeline.py:460`、
`app/agents/supervisor.py:255`）**每请求只调一次** `retriever.retrieve`，因此现网未触发。
README.md:413 的措辞（「一次检索（嵌入 + 向量检索）的**总**时限」）是诚实的，
与卡片 deliverable「统一总时限」的粒度存在可读性偏差 → 见 **Medium-02**。

## 5. 发现

### High

#### High-01　写入/导入路径被检索总时限误伤（卡片范围外的回归）

- **现象**：`OpenAICompatibleEmbeddingProvider.embed()` 无条件起一个**检索**总 deadline
  （`RAG_RETRIEVAL_DEADLINE_SECONDS=8.0`），而这个 deadline 覆盖 `embed()` 内的**所有批次**。
  文档导入时 `RAGService._embed_chunks` 一次性把全部分块交给 `_embed_texts`
  （`app/rag/service.py:698` → `app/rag/service.py:664`），一篇 200 分块的文档 = 20 批。
  只要总耗时超过 8s，**即使每一批都在自己的单次 timeout 内成功返回**，也会在第 16 批
  抛 `DeadlineExceededError`，整篇导入失败。
- **代码位置**：
  - `app/rag/embeddings/openai_compatible.py:71` — `deadline = current_or_new_deadline()`（无差别复用检索预算）
  - `app/rag/embeddings/openai_compatible.py:74-83` — 所有批次共用该 `deadline`
  - `app/rag/service.py:664` — 写入路径唯一的 embed 入口
  - `app/rag/chunking/strategies/semantic.py:51` — 语义切分同样走这条 `embed()`，同样受影响
- **实测证据**（探针 `.workbuddy/tmp/rev038/probe_b.py`，每批 0.5s、全部成功、无任何故障注入）：

  ```
  [B1] 写入路径：200 条文本 = 20 批，每批 0.5s（全部成功、无故障）
       ★ 抛错 DeadlineExceededError: 检索总时限 8.000s 已耗尽，不再发起后续子调用
       已发出批次=16/20，实测耗时=8.22s，结果=DeadlineExceededError
       → 写入被检索总时限误伤（回归）
  ```

  同一份探针、把 `app/rag/embeddings/openai_compatible.py` 换成 `e978819^` 的版本后（其余不变）：

  ```
  [B1] 写入路径：200 条文本 = 20 批，每批 0.5s（全部成功、无故障）
       成功，向量数=200
       已发出批次=20/20，实测耗时=10.33s，结果=ok
  ```

  （该临时替换已还原，`git diff --exit-code HEAD -- app/rag/embeddings/openai_compatible.py` → exit 0。）
- **影响量化**：可承受批数 = `8s / 单批耗时`。单批 1s 时只有 8 批 = 80 分块 ≈ 4 万字
  （按 `RAG_CHUNK_SIZE=500` 约 20 页 PDF）就会导入失败。现有 183 个受影响子用例
  全部使用瞬时替身，**没有任何用例会抓到这条回归**。
- **建议修法**：写入路径不该复用检索预算，二选一：
  1. `app/rag/embeddings/openai_compatible.py:71` 改为只复用**已绑定**的 deadline
     （`deadline = current_deadline() or Deadline(settings.RAG_EMBED_WRITE_DEADLINE_SECONDS)`），
     新增写入侧独立配置项（建议默认 `0`=不设总时限，或按批数折算），三处同步
     `app/core/config.py` / `.env.example` / `README.md`；
  2. 或在 `app/rag/service.py:664` 的 `_embed_texts` 里显式 `bind_deadline(写入预算)` 覆盖内层默认值。
  并补一个用例：**多批次 + 每批都成功 + 总耗时 > 检索 deadline** 时导入仍应成功。

#### Medium-02　「总时限」的粒度是「一次 retrieve」而非「一次用户请求」，且无守护

- **现象**：调用方不做请求级绑定时，`app/rag/backend/native.py:75` 每次都新起预算，
  N 次检索总耗时 = N × deadline。README.md:413 把「总」定义为「一次检索（嵌入 + 向量检索）」，
  措辞诚实，但与卡片 deliverable「统一总时限」的字面可读性有偏差；
  实现文档与专项测试都没有说明「每请求多次检索不累加有界」，
  也没有任何用例锁住「每请求只调一次检索」这个当前赖以成立的前提
  （`app/agents/fast_path.py:120` / `app/agents/pipeline.py:460` / `app/agents/supervisor.py:255`）。
- **代码位置**：`app/rag/backend/native.py:75`；`app/rag/retriever.py:85`（`HybridRetriever.retrieve` 未绑定）
- **实测证据**（探针 A5）：

  ```
  [A5] 不做请求级绑定时：一次「用户请求」触发多次检索的总耗时
        3 次检索，每次各自新起 0.4s deadline → 实测总耗时 1.204s
  ```
- **建议修法**：二选一
  1. 在 `HybridRetriever.retrieve`（`app/rag/retriever.py:85` 的外层）
     用 `with bind_deadline(Deadline(settings.RAG_RETRIEVAL_DEADLINE_SECONDS)):` 包住后端调用，
     并补一个「同一请求内两次 `retrieve` 共享预算、总耗时 ≤ deadline + 容差」的用例；
  2. 若认定「一次检索」就是契约边界，就在 `README.md:413` 与实现文档里显式写出
     「每请求触发 N 次检索则总耗时按 N × deadline 累加」，并把这条写进卡片验收，
     同时补一个用例锁住「每请求只调一次检索」这一前提。

  断言读超时序列单调受剩余预算夹住且总耗时 ≤ 1.0 + 容差。

#### Low-02　嵌入单次超时默认 60s → 15s，写入路径同步受影响（有意改动，缺影响说明）

- **现象**：`app/rag/embeddings/factory.py:46` 由 `settings.LLM_TIMEOUT`(60.0) 改为
  `settings.EMBEDDING_TIMEOUT_SECONDS`(15.0，`app/core/config.py:120`)。
  方向正确（短请求不该复用对话超时），但写入/导入路径同样吃这个值，
  `.env.example:122` 的注释只提了「会被检索总时限夹住」，没提导入。
- **代码位置**：`app/rag/embeddings/factory.py:46`；`.env.example:120-122`
- **建议修法**：在 `.env.example:122` 注释补一句「写入/导入路径同样使用此超时」。
  （与 High-01 是同一个根因的两面：写入路径被读路径的预算/超时配置牵连。）

#### Low-03　milvus 侧复用共享 deadline 没有独立断言

- **现象**：`app/rag/vectorstore/milvus.py:286` 的 `current_or_new_deadline()` 没有一个用例
  直接断言「拿到的就是 native 绑定的那个实例」。变异 M2 虽被抓红（2 failed），
  但那是嵌入侧连带变化导致的，不是 milvus 侧自己的断言。
  实际上 `app/rag/backend/native.py:80-83` 的外层 `asyncio.wait_for` 会先兜住，
  所以 milvus 是否共享只影响错误文案（`MilvusUnavailableError` vs `DeadlineExceededError`），
  不影响「有界 / 不伪造空知识」。
- **代码位置**：`app/rag/vectorstore/milvus.py:286`
- **建议修法**：补一个用例断言 milvus 内部拿到的 deadline 与 `current_deadline()` 是同一对象
  （或在 native 绑定 1.0s 时断言抛的是 `MilvusUnavailableError` 而非 `DeadlineExceededError`）。

## 6. 结论

**不建议关闭。**

必修项：

1. **High-01** — 写入/导入路径不得复用检索总时限（`app/rag/embeddings/openai_compatible.py:71`
   是接线点），并补多批次导入成功的用例。这是实测到的真实回归：改前 20/20 批成功、
   改后 16/20 批就抛 `DeadlineExceededError`。
2. **Medium-01** — 补一个穿过真实 `NativeRagBackend.retrieve` 的取消注入用例
   （变异 M14 存活，探针 A3 在同变异下判红）。
3. **Medium-02** — 二选一：在 `app/rag/retriever.py:85` 做请求级 `bind_deadline` 并补用例，
   或在 `README.md:413` / 实现文档显式声明「每请求 N 次检索 = N × deadline」并补用例锁住
   「每请求只调一次检索」这一前提。

建议一并处理（不阻断关闭）：Low-01（多批次用例）、Low-02（`.env.example` 注释）、
Low-03（milvus 共享 deadline 的独立断言）。

非缺陷、无需处理：Info-01（M12/M13 等价变异）。
