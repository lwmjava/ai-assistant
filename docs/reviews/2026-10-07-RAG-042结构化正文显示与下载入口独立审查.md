## 1. 结论

**不建议关闭。**

先说清楚哪些是**真凭实据、我认为已经站得住**的：

1. **「缩进和列位置保留」成立。** 我原本最怀疑的一环是 `whitespace-pre` 只是个 class 字符串、Tailwind purge 可能扫不到。为此做了**构建产物级查证 + 决定性对照实验**：把源码里注释中的 `whitespace-pre` 字面量全部抹掉、只留 `chunk-content.ts:75` 的字面量常量，重新构建后产物 CSS 仍产出 `.whitespace-pre{white-space:pre}`；而 2026-10-06 的基线产物 CSS 里**没有**这条规则。也就是说这条规则确实由常量本身编译而来，不是靠注释意外蹭出来的。purge 疑虑解除。
2. **「不执行上传文本中的 HTML/脚本」成立。** 渲染级断言不是自欺：`renderToStaticMarkup` 渲染的是**生产组件本身**，`<script>` / `<img onerror=>` 确实变成 `&lt;...&gt;`；我独立复核 `frontend/src` 下 `dangerouslySetInnerHTML` / `innerHTML` 生产代码零处（`app/` 下同样零处）。把组件改成 `dangerouslySetInnerHTML` 后正好是那两条 XSS 断言变红，说明断言有真实约束力。
3. **「未授权 / 源文件缺失 / 服务失败有明确反馈」在文案层成立，且不泄漏内部信息。** 五种状态码各有独立中文文案（测试断言了互不相同）；后端 detail 只在 404 且含「源文件」三字时才拼接，后端该分支的 detail 只有 `源文件不存在` / `文档不存在或无权访问` 两个固定串，**不含路径等内部信息**。
4. **「现有管理权限不变」在当前代码状态下成立。** `app/` 在 `b27fde8..e90683e` 范围内零改动；前端 `canControlDocument` 与后端 `can_control_document` 逐条一致（见第 3 节 M-01 的逐行比对）；前端只决定按钮显隐。
5. **越界检查全部通过。** 改动只落在 `frontend/` 与 `docs/`；`package.json` / `package-lock.json` / `.env` / `app/` / `requirements` 均未改动；`react-dom` 是 18.3.1 既有固定版本依赖，未新增任何依赖，符合 non_goal「不新增渲染依赖」。

**但仍有两条我不能放行：**

- **验收条款 2 的第一句「下载原始文件成功」零证据**——既无自动化，也无任何人工验证记录，实现方在文档 §6.2 中自认。验收条款写的是「下载成功」，不是「下载失败提示正确」。这是字面上的未满足项。
- **与「权限不变」直接相关的前端镜像 `canControlDocument` 零测试覆盖。** 我做了变异：让它对所有已登录用户返回 `true`，25 条测试**仍然全绿**。当前逻辑我逐行比对过是对的，但没有任何东西阻止它下次被改坏。

这两条都不难补（见第 6 节），补完即可关闭。

## 3. 发现清单

### High（1）

#### H-01 验收条款「下载原始文件成功」零证据

验收条款 2 的第一句是「下载原始文件成功」。目前这条**既没有自动化验证，也没有任何人工验证记录**——实现方在 `docs/plans/implementation_rag_042_structured_display.md:273-274` 中自认：

> **下载成功路径没有自动化验证**。401/403/404/5xx/网络的文案映射有单测，但「blob 落盘」依赖浏览器 `URL.createObjectURL`，未在自动化测试中执行，需人工点一次下载按钮确认文件可保存、文件名与 `source` 一致。

现有 25 条测试覆盖的是**失败文案映射**，没有一条触达成功路径。这构成一个字面意义上的验收缺口：卡片要求证明「下载成功」，而交付物只证明了「下载失败会说人话」。

**同时，实现方「未自动化」的理由有一部分不成立**，详见 M-02 与第 5.3 节：我用一个约 40 行的最小 DOM 桩在 Node 内置 runner 里跑通了 `saveBlobAsFile` 的落盘、文件名与 objectURL 释放（3/3 通过，零新依赖），探针已删除。

```ts
# frontend/src/api/rag.ts:95-107
export async function downloadDocumentSource(doc: DocumentOut): Promise<void> {
  let blob: Blob
  try {
    blob = await api.blob(`/rag/documents/${doc.id}/download`)
  } catch (err) { ... }
  saveBlobAsFile(blob, doc.source || doc.title)
}
```

### Medium（3）

#### M-01 权限镜像 `canControlDocument` 零测试覆盖，变异可完全逃逸

后端 `app/rag/access.py:84-92`：

```python
def can_control_document(doc: Document, user: User) -> bool:
    if user.role_enum == Role.SYSTEM_ADMIN:      return True
    if not same_tenant(doc.tenant_id, user):     return False
    if user.role_enum == Role.TENANT_ADMIN:      return True
    return doc.user_id == user.id and bool(doc.is_current)
```

前端 `frontend/src/lib/permissions.ts:73-79`：

```ts
export function canControlDocument(doc: DocumentOut, user: UserInfo | null): boolean {
  if (!user) return false
  if (user.role === 'system_admin') return true
  if (doc.tenant_id !== user.tenant_id) return false
  if (user.role === 'tenant_admin') return true
  return doc.user_id === user.id && doc.is_current
}
```

**逐条比对结论：五条判定一一对应，语义一致。** `is_current` 在 `types/api.ts:201` 为 `boolean`，与后端 `bool(doc.is_current)` 等价；`Role` 联合类型含 `system_admin` / `tenant_admin`，取值与后端枚举一致。前端额外加的 `if (!user) return false` 是空守卫，不改变任何一条语义。下载入口的启用条件是 `canRead && canControlDocument(doc, user)`（`Knowledge.tsx:617`），正好镜像后端 `require_permission("knowledge_bases","read")` + `can_control_document` 的**合取**，不多不少。

**但这个函数零测试。** 我在函数体第二行插入 `return true`（对所有已登录用户放开入口）后，**25 条测试仍全部通过**。也就是说：这个唯一承载「权限不放宽」的前端逻辑，改坏了没有任何信号。

需要说清楚风险边界：由于后端 `rag.py:744` 仍会独立过一遍 `can_control_document`，前端镜像改坏**不会真的放行下载**，最坏后果是「按钮点了弹 403」或「该有按钮的没出现」这类体验问题。因此这不是安全漏洞，而是**回归守护缺失**——但卡片验收条款「现有管理权限不变」在前端侧的唯一表达就是它，零覆盖不可接受。文档 §6.5 自己也承认「若后端规则变更需同步」，恰恰说明它知道自己是个漂移点，却没给它上锁。

#### M-02 下载接线 `downloadDocumentSource` 无测试，且在当前基建下不可测

`frontend/src/api/rag.ts:95-107` 是失败文案映射与落盘的**组装点**：它决定 401 会话失效是否原样上抛、ApiError 是否被换成中文文案、文件名取 `doc.source || doc.title`。这一段没有任何测试，而且**用 Node 内置 runner 测不了**——`api/rag.ts` 顶部 `import { api, ApiError, isSessionExpiredError } from '@/lib/http'`，`@/` 别名 Node 22 不解析 tsconfig paths，直接加载会失败。

因此「下载失败反馈」目前只有**纯函数级**证据（`sourceFileFailureMessage` 7 条），缺少**接线级**证据。例如把 `isSessionExpiredError` 判断删掉、或把 `doc.source || doc.title` 写成 `doc.title`，现有测试全部无感。

顺带说明：这部分确实不像 `saveBlobAsFile` 那样能靠一个 DOM 桩解决，需要给 Node 加别名解析（import map / `--import` loader）。如果短期内不引入 vitest，最低成本的做法是把这段纯逻辑（文案选择 + 文件名选择）再抽一层无别名依赖的纯函数。

### Low（4）

#### L-01 窄屏横向滚动缺少人眼确认

CSS 规则已确认存在，父容器是普通块级盒（`Knowledge.tsx:195`、`:248`），`white-space:pre` + `overflow-x:auto` 作用在 `<p>` 自身，结构上没有 flex 不收缩导致的溢出风险。但「窄屏真的能横向滚」仍需一次人眼确认：上传一份含盒图的文档 → 检索 / 展开分块 → 在窄视口看是否出现滚动条且盒图不被压扁。这是本卡唯一真正只能人工的一条。

#### L-02 文件名兜底与后端不一致

前端 `api/rag.ts:106` 用 `doc.source || doc.title`；后端 `rag.py:755` 用 `doc.source or Path(file_path).name`。当 `source` 为空时，前端落到文档标题，后端落到磁盘文件基名。只在 `source` 缺省的边界下出现差异，不影响下载内容，但两者会不一致。建议在后端补 `has_source_file`（文档 §4.1 已列为后续项）时一并对齐。

#### L-03 产物 CSS 缺少类存在性守护

`chunk-content.ts:75` 的类名是字面量常量，Tailwind 能扫到——这点已实测确认。但**没有测试或 CI 步骤守护这个事实**。我做过变异：把常量改成 `` `${WS}pre font-mono ...` `` 拼接形式，25 条测试**全绿**（因为 `structuredClassTokens()` 仍返回同样的 token），而此时 CSS 是否还有 `.whitespace-pre` 只剩注释在兜底。建议两者择一：在 Tailwind `safelist` 里显式列出这三个类，或在 CI 里加一步「构建后 grep 产物 CSS 必须含 `.whitespace-pre{`」。成本都很低。

#### L-04 `tasks.yaml` 卡片状态未随实现翻转

`tasks.yaml:10225` 的 `status` 仍为 `backlog`。`allowed_paths` 明确包含 `tasks.yaml`，关闭前需翻转为对应状态并补 `deliverables` 的实际落点，否则卡片与代码不一致。

**第五步：决定性对照实验——排除「靠注释蹭出来」的可能**

我在做拼接变异时意外发现：即使类名改成 `` `${WS}pre ...` ``，`whitespace-pre` 在源码里只剩注释里还有，产物 CSS **仍然**含有 `.whitespace-pre{white-space:pre}`。这说明 Tailwind 的提取器也扫注释（它是对文件原文做正则，不剥注释），所以**注释本身就能产出这条规则**——这意味着「CSS 里有这个 class」一度无法证明「常量真的被扫到」。

为排除这个混淆，我做了决定性实验：**保留常量为字面量不变，仅把注释里的 `whitespace-pre` 全部替换掉**，使 `src` 下独立出现的 `whitespace-pre`（排除 `whitespace-pre-wrap` 与测试文件）只剩常量本身：

```
$ grep -rn "whitespace-pre" src/ --include=*.ts --include=*.tsx | grep -v "whitespace-pre-wrap" | grep -v "\.test\."
src/lib/chunk-content.ts:75:  'whitespace-pre font-mono overflow-x-auto text-sm leading-relaxed text-text-muted'
```

重新构建后：

```
$ grep -o '\.whitespace-pre[^{]*{[^}]*}' dist/assets/index-D6SNo6pV.css
.whitespace-pre{white-space:pre}
.whitespace-pre-wrap{white-space:pre-wrap}
```

**结论：在注释被清空、只剩字面量常量的情况下，产物 CSS 仍产出 `.whitespace-pre{white-space:pre}`。** 这证明该规则确实由 `chunk-content.ts:75` 的常量编译而来，purge 疑虑**彻底解除**。实验后已 `git checkout` 还原并重建，产物回到 `index-D6SNo6pV.css`。

### 5.6 关于 `ChunkContent.ts` 用 `createElement` 而非 JSX 的取舍

- 它换来的是「渲染级断言打在**生产组件**上」而不是打在组件的复制品上——这是本次交付里最有价值的一块证据（变异 2 证明了它真能抓住 XSS 回归），这个价值值得付一点语法代价。
- 代价被限制得极小：只有一个单元素组件（`ChunkContent.ts:21` 一行 `createElement`），不是全项目推行。
- 替代方案（挂 esbuild loader 钩子）会往仓库塞测试基建并依赖传递依赖，确实不划算。

**可维护性风险有，但可控，需要注意两点：**

1. 这个组件是全仓唯一用 `createElement` 写法的展示组件，后来者看到会疑惑。组件头注释（`ChunkContent.ts:6-13`）已经写清原因，**建议保留这段注释**，不要当作冗余清理掉。
2. 一旦将来组件长出第二个元素或条件分支，`createElement` 的可读性会明显劣于 JSX。届时要么引入 vitest 后改回 JSX（文档 §6.6 已列此路），要么在组件内加注释说明。**建议在组件注释里补一句「若本组件需要第二个元素，请优先考虑引入 vitest 后改回 JSX」**，把触发条件写死，避免后人无意识地往里堆 `createElement`。
