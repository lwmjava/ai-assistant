## 2. 独立反例与整改建议

复现脚本：`data/t/review032_probe.py`，合成固定向量与记录型 Milvus，只换远端集合边界；保留真实 Service、target 路由和 CLI 状态变化。每次新 UUID SQLite，无费用、无生产数据。

```
P1 malformed dim error=IndexIdentityError
P1 preparing remote rows before=1 after=0
P2 active CLI before=<old active id> after=None rc=1
P3 canceled upsert target status=preparing notes=None residue=1
```

### F1 / High：CLI 对已 active 身份 rebuild 会下线唯一旧索引

`scripts/rebuild_embedding_index.py:287` 不区分 ensure_index 返回新目标还是已有 active，直接置为 preparing 并提交。独立探针先建立有效 A，CLI 当前 provider 仍为 A，再运行 rebuild --apply；注入重建入口普通 RuntimeError 后 fresh Session 的 active_index 为 None。CLI 却输出“旧索引仍是 active，读路径未受影响”。这违背原卡旧版持续可读及失败保留旧读路径。

建议在任何状态写入/外部操作之前拒绝 active 身份原地 rebuild，要求新 index_version/目标身份；prepare 已有 active 的无操作分支不能替代 rebuild 自身守卫。增加无故障和故障的 active 目标 CLI 回归，断言 active 状态及远端 ID 不变。

### F2 / High：upsert 后取消绕过事务回滚与持久补偿

`app/rag/service.py:1076` 只捕获 Exception。在真实 store.add 完成后抛 asyncio.CancelledError，包装入口不执行 rollback/补偿；即使调用方随后 rollback，fresh Session 仍见 target=preparing、notes=None，远端残留一条。当前不是调用取消即所有外部操作撤销，必须如实持久记录残留和禁止错误激活。

建议专门处理 CancelledError 的 SQL 回滚与补偿记录，再原样重抛；不能把取消收敛为成功/普通检索故障，也不能宣称已删除在途远端操作。加入 SQL 回滚后新 Session 的状态/notes、旧 active 不变和重试残留清理断言。

### F3 / Medium：错误维度直到目标清理之后才被拒绝

Service 先生成 vectors，再于 `app/rag/service.py:1174` 对有旧 preparing 块的目标执行远端 delete，到 `milvus.py:add` 才校验 vector dim。探针先成功重建目标一块，再令合法声明 dim=8 的 provider 返回 16 维向量，得到 IndexIdentityError，但该目标远端 rows 从 1 变成 0，SQL rollback 后已有目标 SQL 块仍保留。旧 active 未受损，但未满足此次计划“目标/身份/维度在副作用前拒绝”的校验要求，重复准备的有效目标数据被无必要破坏。

建议在目标 delete 前完成候选向量与完整批次归属校验，复用确定性校验函数，勿以连接前 add 校验替代所有副作用前校验。故障断言应检查新旧目标远端 ID 均不变，而不只是最终抛异常。

### F4 / High：真实远端故障重试留下额外向量

独立完整运行实现者的真实生命周期脚本，以全新 collection prefix `rag032_synthetic_efcbbf0c21d74fdda29180a5849bdc9c` 和隔离 DB 验证。C 部分 upsert 后故障、显式 prepare/rebuild 重试执行到 snapshot(c_retry_completed) 时失败：SQL=3、远端=4，残留 ID `7257fba38aec47f6ad6644068292345c`，目标 `21a7ceaa08ad47b9888ea9e38dbf55d4`。旧 active 仍为 `fcc805087ac0461bb718f961fe4572b8`。

随后独立只读 Strong 查询，残留与新块 `fea18cd847d34a46b9b9a064b3e229b3` 同属文档 `6b615b7648bf47b4ba3afc735a50c270`，SQL 只有新块。结果保存 `data/t/rag032-review-real-failure.json`。这是实际持久残留，不能用读可见性延迟将最终 4/3 差异解释为通过。

静态根因候选：`delete_by_document` 默认 query 查询后，若未看到 ids 就 return 0、不发 delete；刚 upsert 的失败残留在 Milvus 默认 Bounded 一致性下可能尚不可见。此处的弱一致空查询不足以证明不存在待补偿向量。建议按明确补偿记录对目标文档执行可靠的限定删除，并核验；不能将缓存/可见性空值等价于补偿完成。缺陷机制的最终修法由实现者复现确认，当前事实是完整实际脚本失败及 Strong 回读仍有额外块。
