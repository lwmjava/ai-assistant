## 发现

### F1 / P1：SQL 自匹配不能证明 Milvus 目标可检索

位置：`app/rag/index_registry.py:269`，尤其295–348行；激活调用194行。

`_probe_retrieval_hits` 直接读 SQL 分块、在 numpy 中做向量自匹配，不访问目标 collection。只要 SQL 中有合法向量就能通过，即便 Milvus 连接失败、collection 不存在或远端向量为空，也会把旧 active 转 retired。后续真正检索可能失败或无命中，违反 ADR-0008 的检索校验和失败保留旧读路径要求。

独立反例在真实 `activate_index` 入口配置 Milvus 目标、提交合法 SQL 分块，将唯一远端连接边界 `_connect` 设为不可用；期望拒绝激活。实际没有抛异常，反例报 `DID NOT RAISE`，因为入口根本未尝试远端读取。没有替换激活逻辑或 probe。

建议：保留线程内独立 Session 的安全边界，同时对目标后端做实际目标检索校验；SQL 合法性自检不能代替外部读路径。校验失败应保持原 active。实现说明将该缺口转交 RAG-015 并不能使本卡的激活门禁成立。

### F2 / P1：部分重建可提前激活并隐藏未重建文档

位置：`app/rag/index_registry.py:166`、194行。

数量门禁仅要求目标索引块数非零；登记数量不符时自动改成实际数量，不核对完整重建所需文档覆盖，也没有重建完成标记。旧 active 覆盖两篇当前文档，target 只覆盖第一篇时，激活成功并退役旧索引。第二篇的旧块仍保存，但正式读路径只读新 active，因而第二篇退出检索。

独立反例使用真实 Local 索引、同租户两篇当前文档及不同模型 target，仅向 target 写入第一篇的块，然后通过真实 `activate_index` 切换。期望拒绝不完整重建，实际未抛异常。这对应 CLI 逐篇提交后在两篇之间中断留下 preparing 目标的可达状态，不涉及并发治理。

建议：切换前验证本次受控重建范围的完整覆盖/完成记录，明确合法排除及失败文档；完整性未证实就保留旧 active。不能仅把目标自报数量改为当前块数来满足数量验收。

### F3 / P2：自检忽略调用方数据库绑定

位置：`app/rag/index_registry.py:293–295`、355–365行。

`probe_retrieval_hits(session, target)` 忽略传入 Session，固定从全局 `app.core.database.engine` 开会话。调用方使用其他已初始化 Engine/隔离数据库时，目标索引和分块在正确库存在，自检却查另一个库，错误返回零并拒绝激活；全局库未初始化时还可能产生 SQL 错误。Session 参数保留但其绑定被丢弃，领域入口与调用方数据源不一致。

独立反例在调用方 SQLite 保存完整合法目标，再把全局 engine 指向另一份全新空 SQLite；调用真实 `activate_index`。实际抛出“抽样检索命中数为0”，有效目标不能切换。此反例没有替换 Session 或查询结果。

建议：从调用方取得经校验的数据库绑定，在 worker 内新建独立 Session，不跨线程共享原 Session。Connection 绑定和未提交候选的可见性需要明确契约，不可静默切换到另一个数据库。
