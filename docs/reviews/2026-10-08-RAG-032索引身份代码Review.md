## 3. 新发现问题清单

### High（1）

#### H-R1：`probe_retrieval_hits` 跨线程复用 SQLAlchemy Session，存在连接竞争与可见性风险

**位置**：`app/rag/index_registry.py:309-321`

```python
def probe_retrieval_hits(session: Session, target: EmbeddingIndex) -> int:
    try:
        asyncio.get_running_loop()
    except RuntimeError:
        return asyncio.run(_probe_retrieval_hits(session, target))
    with ThreadPoolExecutor(max_workers=1, thread_name_prefix="index-probe") as pool:
        return pool.submit(asyncio.run, _probe_retrieval_hits(session, target)).result()
```

**问题分析**：

当调用方已有运行中的事件循环（FastAPI 请求处理中调用 `activate_index`），probe 会被扔到独立线程跑 `asyncio.run`，但传入的 `session` 是主线程的 SQLAlchemy Session。SQLAlchemy Session **不是线程安全的**：

1. **连接竞争**：Session 内部维护的数据库连接绑定在创建它的线程上下文里，跨线程使用可能导致两个线程同时操作同一连接。
2. **Flush 可见性**：`_apply_switch` 做了 `session.flush()`（切换状态已写入 Session 但未 commit）。同一线程内 flush 立即可见，但跨线程的另一个 asyncio 事件循环通过同一 Session 查库时，看不到这个 flush 的状态变更——probe 可能读到切换前的旧 active 索引，导致检索校验误判。
3. **事务损坏**：极端情况下跨线程访问同一 Session 可能触发 `InvalidRequestError` 或事务回滚异常，影响主流程。

**影响范围**：
- CLI 脚本路径（`cmd_activate`）是同步调用，没有运行中的事件循环，走 `asyncio.run` 分支，**不受影响**。
- 未来如果有 API 路径在请求处理中触发索引激活（例如管理接口），就会命中跨线程分支，产生并发风险。

**建议修复**：

方案 A（推荐）：probe 内部新建独立 Session。
```python
async def _probe_retrieval_hits(session: Session, target: EmbeddingIndex) -> int:
    from app.core.database import engine
    from sqlmodel import Session as NewSession
    # 用独立 Session，不与主线程共享连接和事务状态
    with NewSession(engine) as probe_session:
        store = get_vector_store(probe_session)
        ...
```

方案 B：把 probe 改成纯 SQL 层面的校验（不调用 `hybrid_search`），例如统计 active 索引下分块数、抽样检查向量维度与登记 dim 一致，完全避免异步调用和跨线程。

### Medium（4）

#### M-R1：`adopt_legacy_chunks` 内部硬编码 `session.commit()`，与 `activate_index` 的可配置 commit 不一致

**位置**：`app/rag/index_registry.py:460`

`activate_index` 提供了 `commit: bool = True` 参数，支持嵌入业务事务中调用。但 `adopt_legacy_chunks` 无条件 `session.commit()`：

```python
session.add(index)
session.commit()
```

CLI 脚本每次都是新 Session，没有问题。但如果将来有 API 路径在业务事务中调用 adopt（例如管理接口批量登记历史数据），会提前提交半个事务。

**建议**：加 `commit: bool = True` 参数，默认行为不变，但提供事务嵌入能力，与 `activate_index` 保持一致。

---

#### M-R2：`activate_index` 的切换 + 检索校验 + 回退依赖「同一 Session 内 flush 可见」，跨线程时失效

**位置**：`app/rag/index_registry.py:192-203`

```python
previous = _apply_switch(session, target, retired_rows, now)  # flush
try:
    if chunk_count_for(session, target.id) > 0 and probe_retrieval_hits(session, target) == 0:
        raise IndexIdentityError(...)
except Exception:
    _revert_switch(session, target, previous, retired_rows)
    raise
```

这是 H-R1 的衍生问题。`_apply_switch` 做了 flush 但未 commit，同一 Session 内立即可见。但 `probe_retrieval_hits` 在独立线程里用同一个 Session 跑 `hybrid_search`，而 Local 后端的 `hybrid_search` 会重新查 `DocumentChunk` 表——跨线程 Session 的 flush 可见性没有保障。

**修复 H-R1 时一并解决**：probe 用独立 Session，只查自己能看到的数据（未 commit 的切换对 probe 不可见），这时需要调整 probe 的语义——probe 校验的是「目标索引名下的分块能否被检索到」，而不是「当前 active 索引能否被检索到」。因此 probe 应该直接按 `target.id` 过滤查询，不依赖 active 状态。

---

#### M-R3：`MilvusVectorStore._collection` 实例级缓存没有 TTL 或失效机制

**位置**：`app/rag/vectorstore/milvus.py:86-87`

```python
if self._collection is not None and self._collection_name == target_index.name:
    return self._collection
```

`MilvusVectorStore` 实例与 `RAGService` 同生命周期。索引切换后（运维脚本操作），同一进程内的旧 `_collection` 缓存仍然指向旧集合。虽然 collection name 变了会触发重连，但重连前 `self._collection` 一直是旧的。

**影响**：
- 单进程 CLI 脚本：每次都是新实例，无影响。
- 多实例部署：一个实例切换索引后，其它运行中的实例需要重启或等待 collection 缓存失效才能感知新索引。

**建议**：
- 在文档中说明「索引切换后各实例建议重启」；
- 或给 `_collection` 加 TTL（例如 5 分钟后自动重连）；
- 当前阶段接受这个行为，因为 Milvus 本身就是 Partial 状态，RAG-015 补真实写入闭环时再一并处理多实例一致性。

---

#### M-R4：`health._embedding_index_view` 默认 `supported=True`，异常分支不降级

**位置**：`app/api/routes/health.py:104, 158-159`

```python
view: dict = { ..., "supported": True, ... }
try:
    ...
except Exception as exc:
    logger.warning("embedding index view failed: %s", type(exc).__name__)
```

如果索引查询抛异常（数据库暂时不可用、连接超时等），view 返回 `supported=True` 且 `status=unknown`。虽然 `status=unknown` 已经暗示有问题，但 `supported=True` 可能误导运维以为配置层面是 OK 的。

**建议**：except 分支里把 `supported` 设为 `None` 或 `"unknown"`，不要默认 True。

### Low（2）

#### L-R1：`EmbeddingIndexIdentity.deployment` 默认空串，无非空校验

**位置**：`app/rag/index_identity.py:80`

```python
deployment: str = ""
```

手工构造时 `deployment=""` 能通过 `__post_init__` 校验，但与运行时（从 base_url 派生非空 deployment）的身份永不匹配。生产路径都走 `identity_from_provider()`，问题不大。

**建议**：在 docstring 中明确说明「不要手工构造身份，请用 `identity_from_provider()`」。

## 4. 做得好的地方（值得保留）

| 设计点 | 评价 |
|---|---|
| **身份全字段比对** | `identity_matches_row()` 直接比 `key()`，不做字段挑选，杜绝了「只比 model/dim 就放行」的绕过路径 |
| **历史数据隔离显式** | `index_id IS NULL` 默认不进检索，health 里能看到 `legacy_quarantined` 状态和数量，运维不会被静默空结果坑到 |
| **激活五道校验** | 状态（非 failed）→ 身份（全字段 key）→ 数量（非空）→ 检索命中（抽样自匹配）→ 失败自动回退 |
| **CLI 与运行时共用身份生产函数** | H-07 修复彻底，`--model/--dim` 从「覆盖」改为「断言」，从根上杜绝脚本自造假身份 |
| **旧索引不删** | retired 索引的分块和登记行都保留，rollback 后旧数据真实可读，不是只留空壳登记行 |
| **补偿记录独立事务** | 远端重建失败时用另一个 Session 保存 `compensation_required`，不会被主流程 rollback 掉，重试时能精确清理残留 |
| **写入侧目标身份校验** | `write_index_id` 分支不仅校验目标索引存在，还校验完整身份匹配、状态为 active/preparing |
| **父块复核按 index_id 收窄** | `_expand_parent_chunks` 传入 `index_id`，retired 索引的 stale hit 不会在展开层被绕过去 |
