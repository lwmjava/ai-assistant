## F1 / P1：超时放弃 local 查询后，后台线程仍使用请求 Session

位置：`app/rag/vectorstore/local.py:154-172`，尤其 `asyncio.to_thread(self._hybrid_search_sync, ...)`；请求会话清理由 `app/core/database.py` 的 get_session 和 `app/api/deps.py` 的 get_db 负责。

本次改动把同步查询移入线程，使 native.wait_for 能及时结束等待，但仍把同一个请求 Session 留给后台线程。超时或用户取消后线程不能中断，调用方会继续处理异常、使用 Session 或执行请求依赖清理；此时线程仍可能正在 SQL 查询或身份查询中。因此注释中“await 期间不并发使用，线程安全成立”的前提在超时后不成立。SQLite 的 check_same_thread=False 仅放开驱动线程检查，并不解决 Session 的生命周期和并发所有权。

复现使用真实 SQLModel Session 子类跟踪 close/exec：在真实 local.resolve_read_index_for 调用点注入可控阻塞，native 在 50ms 预算后抛 DeadlineExceededError；模拟请求依赖清理关闭 Session，然后允许后台线程继续真实 SQL 查询。记录确认 exec 发生在 close 之后，`not late_reads` 断言失败。该 Session 默认还能重新打开连接，故“本次未崩溃”不能证明资源安全。

实际影响是请求会话与后台查询发生竞争，以及清理后重新取得数据库连接的风险；本反例证明清理后的访问，没有声称已经复现生产锁死或数据损坏。既有专项慢查询用例使用 `Session=None`、最终返回 None 的 resolver，无法验证这条边界。

建议后台读工作持有独立 Session，在工作线程内打开并在结束时关闭，绑定调用方实际数据库，而不共享请求 Session；同时补齐超时和取消后的会话清理测试。不能通过让调用方继续等待慢查询来牺牲已有总时限保证。

## F2 / P1：可选检索后端绕过统一总 deadline，可把慢查询写成正常空结果

位置：`app/rag/backend/langchain_backend.py:220-237`；相同静态缺口在 `app/rag/backend/llamaindex_backend.py:215-232`。

总预算只在 NativeRagBackend.retrieve 建立和绑定。LangChain/LlamaIndex 自己调用 Embedding 和 store，不经过 native，没有绑定或外层 wait_for；local.hybrid_search 本身仅 to_thread，不自行强制 deadline。于是设置 RAG_BACKEND=langchain + local 时，RAG_RETRIEVAL_DEADLINE_SECONDS 无效。使用真实 OpenAI 兼容 provider 时，未绑定上下文还会被当成写入路径，各批另起写入预算；Milvus 也只能约束自己的远端子调用，无法覆盖 Embedding + 查询的累计耗时。

复现：通过真实 get_rag_backend 工厂创建已安装的 LangChain 后端，明确断言 name 为 langchain，配置总预算 50ms，注入异步 store 查询 sleep 180ms 后返回 []。真实 retrieve 正常返回 []，预期 DeadlineExceededError 未抛出。说明这个缺口不是缺失依赖回退 native 引起的。若上层将空列表归为 no_hit，就会把超出预算的迟到空结果当成“查过但未命中”。

LlamaIndex 当前环境缺依赖，相关正式测试跳过；其缺口来自代码核对，不宣称本次运行过该后端。缺口并非 HEAD 新加的一行代码，但属于本卡“统一总时限”的未交付路径，不能只用默认 native 测试宣布全部后端完成。

建议在所有实际检索入口复用统一预算包装，或在共有组合层实施，并对已安装的可选后端增加故障注入测试；保留取消传播和 unavailable/no_hit 的区分。

## F3 / P2：Embedding 的单批总时限只在调用前检查，慢速响应体可超时成功

位置：`app/rag/embeddings/openai_compatible.py:86-94,106-111`；`app/rag/resilience.py:370-374,413-418`。

未绑定检索预算时，embed 为每批创建 RAG_EMBED_BATCH_DEADLINE_SECONDS，但 retry_async 直接 await operation：没有以剩余预算包装操作，也没有成功后复核 deadline。_post_batch 只把剩余预算填进 httpx timeout；该参数约束各阶段等待，不能替代整个批次的总耗时限制。服务端持续以较小间隔发送响应体时，可以超过单批总预算仍被记录为成功。

先用 MockTransport 流式响应暴露问题，再用本机实际 TCP/HTTP 服务排除 MockTransport 不执行超时的影响。最终反例在 127.0.0.1 临时端口发送真实响应体，配置单批预算 50ms，每 15ms 发送 8 字节，完整响应需要多次等待、累计超过预算；真实 httpx/provider 接收完整合法向量并成功返回，预期 DeadlineExceededError 未抛出。测试服务和客户端退出时均关闭，无外部数据或费用。

首次真实 HTTP 反例因测试 key 为空，Bearer 尾部空白被 httpx.LocalProtocolError 拒绝；此轮不算慢响应证据。改用无敏感含义的合成测试头后取得上述有效断言失败。

native 外层 wait_for 可以保护默认检索路径，因此不宣称所有 native 调用都受此缺陷影响。影响主要是实现说明明确承诺的写入/导入/重建单批预算，以及 F2 中没有绑定共享预算的可选检索路径。无需恢复“几十批共用一个检索预算”的旧设计；应在每批自己的剩余预算内限制整个操作并拒绝迟到成功。
