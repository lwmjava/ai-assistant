## 3. 根因分析

9 个发现可归入 5 个系统性根因：

- **R1 · 验证与实现同源——内部/推导证据替代外部运行证据（最核心）**：RAG-015 F1 从"SQL 行没删"推导"文档仍可见"；RAG-032 F1 用 SQL 自匹配替代真实远端检索；RAG-036 F3 用 tasks.yaml 的 done 字段替代前置卡运行证据。实现者与验证者共享同一心智模型，默认"内部状态等价于外部行为"。
- **R2 · 关闭门禁走过场——"未验证也关闭"**：RAG-015 F3 把真实 Milvus 验证标为"未验证"、称"无服务"却仍关闭（仓库实际有 10-07 真实 pass 报告、compose 三服务 healthy）；RAG-036 F3 宣称"RAG-032 前置缺口已闭合"，与同 HEAD Review 结论相反。关闭时未真正执行"原始要求 ↔ 证据 ↔ 结论"对账，done 退化为"代码改了 + 测试绿了"。
- **R3 · 失败边界从未测试——对抗性反例缺失**：数值边界（NaN/Inf/溢出）、失败路径（远端不可用）、部分成功（部分重建）、跨租户（错误候选）、身份不符（响应模型名）、数据源绑定（错库）全部漏测；只覆盖了成功路径。
- **R4 · 依赖链证据传递错误——缺口沿链放大**：RAG-032 将激活门禁缺口"转交 RAG-015"，RAG-015 带缺口关闭，RAG-036 又据 done 字段宣称前置已闭合，同一缺口被三次传递。
- **R5 · 实现完成 ≠ 任务完成**：三卡核心代码基本正确（RAG-036 修复正确、RAG-015 正常路径 89 passed、RAG-032 四项远端重建修复入回归），但切换可见性语义、激活门禁语义、租户隔离、证据完整性等交付契约未兑现。

## 4. Skill 结构缺陷

Skill 的问题是**结构性的：规则不缺，缺的是让规则被强制执行的机制**。

| # | 缺陷 | 后果 |
|---|---|---|
| D1 | 门禁条款与执行脱钩：契约对账表、证据有效性、关闭判定写得很好，但无强制机制，也未要求"未验证项"原样写入 tasks.yaml 备注 | "未验证也关闭"（RAG-015 F3） |
| D2 | 独立审查的"独立性"与"入口级"未定义：未要求从真实领域入口构造反例（单元级自审可蒙混）、未规定 review 未通过禁止关闭 | 自匹配/自检证据通过审查（RAG-032 F1/F3） |
| D3 | 证据分级未制度化：只写"Mock 仅证明链路"，未把推导证据、自检证据、历史证据列为无效验收证据 | "SQL 行没删→文档可见"式推导被接受（RAG-015 F1） |
| D4 | 失败边界清单不是必交付物：验证维度列了，但"边界与反例清单"不是计划的硬产出 | NaN/溢出、跨租户、部分重建全部漏测（R3） |
| D5 | 依赖链复核深度未定义：只说"核对前置卡有效证据"，未说前置有未决 P1 时依赖卡禁止 done、同会话多卡需独立证据 | 缺口沿链放大（RAG-036 F3） |
| D6 | 缺"Review 驱动修复回路"：外部 review 发现缺陷后，无强制"登记→补反例→修复→独立复核→更新证据"闭环 | 缺口被"转交下一卡"了事（RAG-032→RAG-015） |
