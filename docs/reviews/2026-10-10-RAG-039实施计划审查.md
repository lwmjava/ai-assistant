## 测试图与失败门禁

```text
runner/start_scheduler
  -> 验证有限正整数预算
  -> 恢复 orphan running [排除 active / Engine 绑定]
       -> 已提交凭据 -> 补终态，不重发
       -> 未提交且有预算 -> pending
       -> 次数耗尽/身份错误 -> failed + trace
  -> claim [SQL CAS + job/source/global容量]
       -> busy -> 保持 pending，不能伪装 idle
       -> owned -> 独立 Session 实际摄取
            -> 同源串行；异源并发
            -> 失败/取消 -> rollback、旧读路径保留、正确源文件清理
            -> 成功 -> 提交凭据 + 终态 + 持久批次统计
  -> until_idle [有 pending/active 时等待或明确忙态]
```

验收采用 E2：真实代码、隔离 SQLite、合成文件/provider，不证明检索质量。必须覆盖线程重复 runner、并发上限/批次上限实测、同源重复上传与重解析互斥、orphan running 新进程恢复、终态提交窗口中断、普通失败有限重试、active 排除、两 Engine、跨租户 job/batch/源文件/目标绑定、无权用户、数值边界、批次混合成功失败。

补充的两个关键反例要求已发送实现者/主 Agent，须进入计划与正式回归：

- 真实 Tenant 且设置 storage_limit 的两个不同 URL 并发。begin_source_quota 会持 SQLite 写锁，必须验证跨 await 没有另一任务同步等待写锁导致失败；不得仅用不存在 Tenant 的合成场景证明并发。
- 一个 runner 占满容量时调用 until_idle，或 pending 都与 active 来源冲突时，不能把 claim=0 误认为数据库已无待执行任务。兼容 limit 作为批次上限，并定义等待/忙态。

每个新失败路径均须检查终态、trace、源文件副作用和新 Session 的最终行；仅断言异常不足。权限/幂等/恢复在正式实现和独立 review 时仍可能出现缺陷，本计划评审不预先宣称通过验收。
