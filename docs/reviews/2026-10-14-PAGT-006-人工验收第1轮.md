## 本轮独立人工操作

1. 隔离 fixture 预置同消息已完成工具 1，租户消息上限为 1；将工具换成带真实契约的计数函数，使用真实 Registry（不关闭审计），ChatService 使用合成决策提供商。
2. 执行真实服务流：工具 2 产生观测后注入 CancelledError。实际 Executor 注入成立；关闭该 Session 后新 Session 读到 running、round_no=2、counted-2 观测和一条真实用户/租户绑定审计。审计字段恰为 risk/allowed/reason/latency_ms，无参数正文。
3. HTTP `/api/chat/stream` 使用相同消息 ID 续跑，再提出工具 2。响应 200 与 done；实际工具仍只执行 `[2]`；新 Session 中 done/round_no=3。重复尝试消耗预算符合批准契约，不能错误地要求轮次仍为 2。
4. 新 Session 中用户消息为 1，assistant 分别是 stopped 空文本与 complete answer。取消发生在零 token 时，既有 ChatService finally 保存 stopped（仅已展示文字）；恢复保存 complete。与既有 `test_chat_controls::test_stop_persists_partial_and_does_not_append` 所定义的停止保存语义一致，不是额外扣费用户消息或重复工具。此既有测试仅读源核对，本轮未执行。
5. 同消息再次恢复 `/api/chat` 返回 409；跨租户 system_admin 请求 `/api/chat/stream` 返回 404；工具调用仍 `[2]`，消息数量仍为 3，没有拒绝后的新增副作用。
6. web_fetch 指向临时 `127.0.0.1` ThreadingHTTPServer 返回固定文本，实际 httpx 请求两次，两条观测完全相同、status ok、attempts 1；该观测兼容探针只将审计挂钩关闭，未使用共享 DB，不把它作为审计证明。服务器 shutdown/server_close/join 后结束。
