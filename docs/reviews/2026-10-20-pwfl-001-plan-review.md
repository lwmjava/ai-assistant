## 结论

**必须先改计划。** 重试放在同一次 `execute`、不改调度比较、默认不重试、上限夹到 3，这四点和当前代码事实一致，也可以对上原始交付。按当前写法实施，会改到允许路径外的 README，退避等待没有上界，创建者失效只在首轮检查，第 5 节也证明不了第二条验收和指数退避。

## 与原始契约

| 原始要求 | 计划 | 审查 |
|---|---|---|
| 失败按指数退避重试并设上限 | 第 n 次重试前等待 `min(base * 2^(n-1), max_delay)`，额外次数夹在 0 到 3 | 公式对齐。等待上界和第 5 节的证明没有绑定，见阻断项 |
| 重试次数与退避参数可配置 | 三个进程级配置，默认次数 0 | 对齐 §5.6.2 的默认 0、最大 3。模型没有 `retry_count` 列，不新增表是对的 |
| 注入一次临时失败后可自动重试成功 | 同一条执行记录，第一次失败、第二次成功 | 行为对齐。测试只强制了这一条 |
| 持续失败达到上限后停止并记录原因 | 调用次数等于 1 加上限，`error` 保留最后一次异常并写明上限 | 行为写在第 4 节，第 5 节没有要求断言 |
| 不做分布式重试协调；不改 cron 触发机制 | 不改 `scheduler.py` 的到期判定，不新增表、迁移或前端 | 比较逻辑可以不动。无上界的睡眠会拖住串行 tick，见阻断项 |
| 不实现超时、取消、并发池或告警 | 计划已排除；`CancelledError` 不捕获 | 对齐。`WORKFLOW_MAX_EXECUTION_SECONDS` 仍未被执行，本卡不要接上它 |

前置 FLOW-001 的状态是 done。到期槽被执行记录挡住，依据的是当前 `scheduler.py`：进入 `_trigger` 前写入 `_last_run`，水位取同租户、`triggered_by=cron`、全部状态里最近的 `created_at`。`execute` 在调用 bridge 之前就提交了这条记录。因此重试必须留在同一次 `execute` 内。这个判断成立。

## 分项

**架构。** 重试留在 `WorkflowEngine.execute`，手动和定时仍共用这一入口，不新造 Runtime，也不需要新的 ADR。同一条记录从 pending 到 running，成功或最终失败后结束，和现有状态字段一致。Webhook 仍只在最终成功后发送。

**兼容。** `WORKFLOW_RETRY_MAX` 默认 0 时，bridge 仍只调用一次，现有失败测试不必改预期。小于 0 按 0、大于 3 按 3，符合产品上限。成功时清空 `error` 是必要的，计划已经写了。回滚把该配置设为 0 或撤回接线，已有执行记录不删除、不重放，和任务卡一致。

**权限。** 进入 bridge 之前，创建者禁用或租户不匹配会停用任务并不调用 bridge，这条覆盖的是现有首轮检查。退避把下一次调用推迟之后，计划没有要求再查创建者。`WorkflowBridge.execute` 每次都调用 `ChatService.chat`，而 `chat` 在模型返回前就经 `accept_user_message` 新建会话并计入创建者租户配额。第 4 节的幂等只保证不新增第二条 `WorkflowExecution`，没有写明对话和配额会按尝试累加。`ChatService` 不在允许路径内。

**失败路径。** 创建者失效不重试、`CancelledError` 继续抛出、最终失败留下原因和上限，这些边界是对的。所有 bridge 异常都重试，包括确定性失败；在默认 0、最多 3 次额外尝试的前提下可以接受，本卡不必先做错误分类。配额不足若发生在 `chat` 内部，也会落入同一次重试，本卡不单独处理。

**测试。** 第 4 节的观察结果够用，第 5 节却只要求先写「上限至少为 1 时，一次临时失败不会停在 failed」，然后做最小实现。只满足这一个测试时，固定重试一次且不等待也能通过，第二条验收和指数退避都没有证据。公共执行链上的无筛选 pytest、ruff、mypy 范围正确。不改前端时，本地前端检查不适用。最终提交的三项 CI 仍要等该提交出现后再核对。

**性能。** 调度循环对每个到点任务串行 `await`。重试睡眠算在这次 `execute` 的 `duration_ms` 里，并推迟同一 tick 的后续任务和下一轮扫描。次数已经有上限。基数和单次等待只把非有限数、负数收成 0，正的大数没有上界。不能把这条计划写成性能达标。

## 最小修正

只改计划，不扩大实现范围：

1. 删掉「若 README 已有工作流配置行，只补这两项参数」。`README.md` 不在本卡允许路径，本卡不改它。三个配置只写入 `app/core/config.py` 和 `.env.example`。README 配置表因此暂时不会列出这三项；这是允许路径造成的文档漂移，不在本卡补。
2. `WORKFLOW_RETRY_BASE_SECONDS` 和 `WORKFLOW_RETRY_MAX_DELAY_SECONDS` 在现有规则之外再加有限上界：单次等待超过 30 秒按 30 秒，基数大于这个上界时按上界。非有限数和负数仍为 0。写明这段等待发生在已被调度器串行等待的同一次 `execute` 内，`duration_ms` 含等待；不改 `scheduler.py` 的到期比较，也不声称缩短 tick 或通过压测。不要用尚未生效的 `WORKFLOW_MAX_EXECUTION_SECONDS` 充当本卡超时。
3. 每次调用 bridge 之前，用现有规则再确认创建者仍启用且属于该任务租户。否则停止重试、停用任务、记下原因，不再调用 bridge。写明每次 bridge 尝试仍可能各留下一条本租户对话并计入配额。本卡不改 `ChatService`，验收在 bridge 替身注入失败。不把「只有一条执行记录」写成对话或配额恰好一次。
4. 第 5 节在实现完成前必须绑定这些断言：持续失败时 bridge 调用次数等于 1 加上有效上限，状态为 failed，`error` 含最后一次异常文本和该上限；注入的等待序列依次为 `min(base * 2^(n-1), max_delay)`；上限为 0 时只调用一次；创建者失效时 bridge 调用次数为 0，且任务被停用。临时失败成功时仍是同一条 `success` 记录，`error` 为空，webhook 只在最终成功后发出。
