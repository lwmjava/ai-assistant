# Harness 效能审计与开发治理整改建议

日期：2026-10-22。来源：WorkBuddy 初稿及本次仓库核对。用户已批准按讨论后的建议调整文档规则。
基线：`3fcca05b54ce2acadbf39fb7856e78c77551a101`；执行记录：[开发治理减负实施记录](../plans/plan_harness_workflow_simplification_20261022.md)。

## 1. 结论与证据边界

现有开发治理有重复阅读、记录和审核的成本；尚无足够工时、业务验收周期和缺陷数据证明 Harness 整体负收益或质量下降。整改采用按需阅读、风险分级、记录复用和明确退出条件，保持测试、安全及发布门禁。

开发治理（任务/计划/审查）与产品运行时 Harness（工具执行、权限、预算、状态恢复）分别评价。本轮优化开发流程，不以此否定或重建运行时能力。

## 2. 本轮采用的修复方案

### 2.1 最小上下文与单一来源

- 每次读取AGENTS.md、适用规则、tasks.yaml的全局策略、当前卡和直接依赖摘要；只对失效证据、未闭合前置或相关设计继续展开。
- 产品/ADR/历史指导/评审按触发条件读取相关章节，不扫描整目录，不因台账重复must_read字段重复读取。
- 规则入口集中在AGENTS.md第2节；tasks.yaml的rules仅指入口，其他文档目录是索引，不是新增必读清单。
- 移除规则中的历史完成流水账。保留有效批准、进入条件和来源链接；不删除被引用的29份历史文件。旧指导中的架构状态标明历史基线，不批量冒充最新事实。

### 2.2 按风险组织交付

- 普通任务：目标、事实、方案、非目标、验收在一份卡内记录或交付记录中说明；实现后原位补结果。无须另写计划、实现说明、关闭对账三份文档。
- 权限/租户、公共执行链、持久化/迁移、架构与高风险变更：明确方案、必要ADR和独立审查；仍可复用已有批准计划。分级不以50行或工时机械决定。
- 批次围绕可演示用户结果组织，明确清单、边界和终点；各卡仍逐一满足验收，不能拿模块存在代替主链可用。无批次授权不得自动推进全部backlog。
- 技术验证、独立审查、业务接受分别记录。Agent检查不得命名为人工审核；受托自动操作验收需记录授权、场景和证据，主观业务判断仍由用户决定。

### 2.3 评审退出与有效证据复用

- 评审覆盖原始契约、最终diff、调用方和相关反例；不设置最低问题数。
- 范围内阻断问题修复验证后结束本轮；只有新相关改动、新失败或新证据才重开。无关建议不阻塞交付，也不顺手实现。
- 已批准范围内常规可逆修复连续执行；新范围、架构/权限、费用、数据外发和重要数据操作按现有规则升级。
- 第10节检查和版本绑定保持。相关输入或环境变化使对应证据失效；相同有效证据可在记录间引用，不因更换审查者或补说明重复跑。
- 不以“已有旧失败”“文档已整理”关闭未通过的业务任务；夜间准入、生产及发布授权保持。

### 2.4 文档、代码与产物归属

| 用途 | 新增内容的推荐位置与处理 |
|---|---|
| 人读说明、计划、评审结论、ADR | docs对应目录；单份记录覆盖同一交付 |
| OpenAPI、图像、HTML等文档配套资源 | docs中明确位置，可保留JSON；按用途判断而非后缀白名单 |
| 可复用导出/维护/验证执行器 | scripts；维护工具注明目标、授权与回滚 |
| 持续回归测试 | tests；必须核对默认收集入口及CI |
| 版本化评测输入和长期基线 | 复用evals现有布局；不改冻结基线与holdout |
| 一次性探针、重复日志、覆盖率、中间指纹 | 优先现有被忽略的data/validation/<run-id>/；CI产物按明确保留策略保存 |
| 必须长期追溯的证据 | 在交付记录链接受控归档，记录版本/摘要和保留方式；不能只依赖会过期的CI链接 |

历史文件暂留。本轮不移动测试、脚本或注册表，不删除旧证据，不重打包历史ZIP。后续迁移先查引用、导入、路径推导和收集配置，再验证调用方。不得把本轮文档例外用于豁免后续测试/脚本迁移的必要回归。

## 3. 执行范围与次序

本轮只有GOV-003一张治理卡：修订本报告 → 统一AGENTS/台账元策略 → 同步Cursor、指导/治理、工作流、检查清单、模板及交付技能 → 文档与流程案例验证。实现结果记在同一实施记录中。原业务卡内容与状态不变。

下列是后续进入条件，不在本轮创建一批治理卡或宣称完成：

1. 下一项涉及相关测试的任务，先解决docs测试收集/正式归属，迁移后核对收集数量、执行结果与最终CI。
2. 再次出现重复验证执行器需求时，复用/提取现有scripts能力，统一解释器、隔离测试库、唯一临时目录、日志和退出码；不建设新的治理平台。
3. 审查发现可复现缺陷，纳入正式tests/evals；临时探针不能代替长期回归。
4. 引用、依赖、状态、收集等确定性检查，只对反复耗时或出错的项目逐步自动化；规则存在不等于hook/CI已安装。
5. 最后按触达范围迁移历史产物；长期证据保留和删除需先确定授权、保留期及引用替代。

## 4. 验收和效能试运行

本轮文档验收：YAML可解析、旧201卡语义不变、新卡唯一、改动链接有效、全局流程无强制重复文档/“人工审核Agent”、AGENTS第10节逐字不变，保留已批准方向与安全边界。流程案例覆盖低风险简化、单行鉴权高风险、证据失效、重复审查退出和业务接受缺口。

接下来三个自然进入实施且获授权的业务任务试用新流程，不为试验自动开工。每项直接在交付记录填写：开工/可验收/接受时间、等待和重复验证耗时、首次接受结果、验收后7天内缺陷/重开。没有计时或观察窗口未结束写未知，不估算填零。比较任务范围和复杂度；不以代码行数、文档数、引用率或done比例替代业务效能。

未验证：实际提速、验收后缺陷变化、跨宿主技能行为、全部历史文件引用/收集情况。出现安全/质量回退时先处理具体失败并调整对应规则，不无条件追加整套流程。

## 5. 回滚与状态

规则变更可通过本轮diff逐文件恢复，保护用户后续改动；不重置工作区，不删除证据或业务数据。业务配置、CI、测试及运行时Harness本轮未改。规则实施和实际检查结果以链接的实施记录为准，不能把建议写成已经安装的自动控制。
