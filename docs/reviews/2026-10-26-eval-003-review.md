## 已确认发现

### P2：Agent 用例异常/取消时丢失已消耗调用记录

定位 `app/services/evaluation_orchestrator.py:440-441` 与 `:393-397`。Agent 的预算只累加到 `_ExternalBudget.used`，只有 `_run_isolated_agent` 正常返回后 `_persist_case` 才把差额保存到 `EvaluationJob.external_calls_used`。若请求已经发出后抛异常、任务取消或超时，该路径被跳过；`execute_job` 仍会保存 failed/cancelled 终态，但不会保存该用例的已消耗次数。此前已完成用例的计数会保留，本次失败用例的调用却表现为零。

复现：使用现有 `adapter_session` 的隔离内存库，通过正式 `create_real` 创建 max_external_calls=1 的 Agent 任务，经正式 `execute_job→run_real_evaluation→_run_agent`；仅将底层 Agent 执行替换为“consume 一次后失败/取消”。两种终态均确定收敛，内存 consumed=1，重新读取持久任务 external_calls_used=0。探针无真实网络请求，不用它证明模型质量。

影响：任务/API/审计回溯无法如实反映失败或取消前已发生的调用，无法完整解释预算消耗；现有内存取消测试只断言 budget.used，未覆盖持久结果。建议在实际尝试前持久预占调用，或在所有退出路径以单调、幂等方式保存差额，并补跨请求失败、取消、超时回归。

### P2：高层模型包装无法约束 fallback 的实际尝试数

定位 `app/services/evaluation_orchestrator.py:110-114`，直接调用方 `app/llm/factory.py:get_llm_provider` / `app/llm/routing.py:FallbackChain.chat`。评测在一次 delegate.chat 外只 consume 一次；当正式工厂返回多个真实 hop 的 FallbackChain，首跳连接异常、429 或可兜底的服务端错误会在包装内部继续调用下一跳，其前面没有再次进行评测预算预占。默认链允许 chat/fallback 和 intent/chat/fallback，具备多个有效配置时可以触发。

复现：使用真实 FallbackChain 类装配两个纯合成 Provider，第一跳抛 ConnectError，第二跳成功，外层 `_BudgetedLLM(...,_ExternalBudget(1))`。调用正常返回，Provider 尝试序列为 primary/secondary 共 2 次，预算仍为 1/1。这里统计的是 Provider 尝试；正式 OpenAI-compatible Provider 每次 chat 会发 HTTP，因此相同组合在真实端点下会扩大外部请求数。

影响：Agent/Workflow 的 max_external_calls 不是实际外部尝试硬上限，失败兜底可在已批准次数之外额外调用。建议把评测预占回调放到每个实际 hop/HTTP 尝试之前，或在评测上下文禁止隐式 fallback；复用生产链时不可仅增加预期总调用次数掩盖差异。
