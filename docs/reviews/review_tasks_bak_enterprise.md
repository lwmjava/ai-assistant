## 1. 结论

这 36 项作为「MVP 二十个交付包之后的企业上线清单」是合理的。它们补的是流水线、观测、工具契约、工作流可靠性、检索与 MCP 加固、PostgreSQL、多实例、密钥、审计保留、备份恢复和压测，和需求第六章以及当前 `Partial` 缺口对得上。

不能按 `tasks.bak.yaml` 的现状直接替换 `tasks.yaml`。有 4 项会改变已批准口径或把实验送上 MVP 关键路径，并入前必须改任务卡。另外有 2 项上线缺口这 36 张没覆盖，建议另开卡。资源级 ACL、Query Rewrite、ClamAV、SSO、K8s 这次不要加。

| 判断 | 数量 | 含义 |
|---|---|---|
| 保持 | 30 | 问题、优先级和非目标说得通，可进企业阶段 backlog |
| 并入前改写 | 4 | `PRAG-001`、`PRAG-002`、`PRAG-003`、`PAGT-001` |
| 建议新增 | 2 | 阻塞 CI 全绿的既有测试失败；生产环境禁止用 Mock Embedding 上线 |
| 这次不加 | — | 见第 6 节 |

三处对旧任务的依赖改写也不要一起并入：

- `SKILL-001` 继续依赖 `FLOW-001`。创建技能不依赖先做出 `web_search` 和 `file_ops`。
- `REL-001` 继续只依赖 `CLI-001`。它的标题是覆盖当时已有端点。Citation 和 MCP 若改契约，在各自任务的验收里更新 OpenAPI。
- `REL-003` 增加「不新建 CI」这条非目标可以保留，它只是划清边界。

## 2. 评审范围

`tasks.bak.yaml` 的项目头与 66 张 MVP 任务顺序、状态一致：48 张 `done`，18 张 `ready`。新增 36 张全部是 `backlog`。旧卡正文只有三处不同：`SKILL-001` 的前置、`REL-001` 的前置、`REL-003` 的一条非目标。

新增分布：验证 2、工具与计划 5、工作流 4、检索 4、MCP 5、企业运行 16。优先级 P0 11 张、P1 16 张、P2 9 张。唯一 L3 是 `OPS-005` 租户彻底清除。

本评审不实现这些任务，也不重跑测试。事实来自上述文档和已有评测报告。

## 3. 为什么整体合理

需求 MVP 的 `REL-001`～`REL-004` 只要求：Swagger 对过账、写清备份并做一次恢复、留下测试命令和退出码、检索实验有结论。需求 §6.1～§6.7 还要求 CI、结构化日志、PostgreSQL、审计保留不少于 90 天、密钥扫描、API Key 加密、备份脚本、升级回滚和性能数字。这 36 张补的是这一段，没有把 §4.4 明确排除的拖拽工作流、多渠道、SSO、K8s、技能市场、计费写进来。

和现行交付排期的关系也清楚：二十个交付包仍到 2027-03-25 的 D4 为止。企业阶段应排在 D4 之后。`NFR-001`、`NFR-002` 没有前置，可以和剩余 MVP 并行，因为它们不改对话语义。

下列卡片问题真实、范围可回滚，建议原样保留：

| 组 | 任务 | 保留理由 |
|---|---|---|
| 验证 | `NFR-001`、`NFR-002` | 仓库没有 CI；日志还不是带 trace、用户、租户的 JSON。需求 §4.5、§6.5 的 P0 |
| 工具 | `PAGT-002`～`PAGT-005` | 十要素、预算、可编排步骤、技能版本，对应治理规范和需求 §5.1。`PAGT-002` 不做审批界面是对的 |
| 工作流 | `PWFL-001`～`PWFL-004` | 重试、超时、并发、失败可追查。当前调度仍是 `Partial` |
| MCP | `PMCP-001`～`PMCP-005` | 超时、权限、审计、凭据、版本。MCP 默认关闭，这些是启用前的条件 |
| 运行 | `ERR-001`、`NFR-003`～`NFR-010`、`OPS-001`～`OPS-007` | 对应需求 §6.6、§6.7 和多实例。`ERR-001` 只依赖 `SEC-002`，可以在 C6 之后就做，不必等到 D4 之后 |

`PRAG-004` 低分拒答可以保留，优先级 P2 合适。它不应挡发布。

`OPS-005` 保持为运维脚本，不要做成 Agent 可调用的工具或普通 API。脚本执行人就是人工门禁。任务里「不做审批流界面」可以保留，但验收要写明：执行前有确认记录，清除动作进审计，且只在测试租户验证。

## 4. 并入前必须改的 4 张卡

### 4.1 `PRAG-001` 的前提已经过时

卡片把 `rag-026`、`rag-036`、`rag-037` 写成仍在发生的越权，证据是 2026-09-19 冻结基线里的 `violation_rate` 0.1875。这三例不能当成待修的检索越权：

- `rag-026` 在 holdout，`forbidden_document_ids` 为空。案例说明写明：同租户命中运维备忘不是越权。用它当实现目标，违反「不得用 holdout 调参」。
- `rag-036`、`rag-037` 带 `acl_planned`。ADR-0001 和数据集说明写明：资源级 ACL 仍是 `Planned` 时，同租户当前文档被检索到不算越权。生成层不得回答编制编号或绩效规则，那是拒答，不是检索过滤。
- 2026-09-24 的官方评测 `evals/reports/rag-v0.1-rrf-k60-20260924.json` 中，已看到的 `violation_cases` 为 0。冻结的 2026-09-19 报告不能改写，也不能把其中的旧计数当成今天仍复现的缺陷。

建议把这张卡改成核对，而不是修复：用现行评测器重跑官方集；越权仍为 0 则关闭；若出现新的跨租户命中再单独立项。不要在这张卡里实现资源级 ACL，也不要把它设成 `PRAG-002` 的前置。权限过滤一旦改了候选集，后面的重排就不再是单变量实验。

### 4.2 `PRAG-002` 不能把「必须提升」写成验收

交付排期 D4 写明：重排最多一轮，有指标则保留，无提升则记录不采纳并结束。卡片验收却要求 Recall@1 相对基线有提升。无提升时这张卡会永远完不成。

验收改为：开关对照报告可复现；关闭时与基线一致；给出采纳或拒绝。拒绝也算完成。前置去掉 `PRAG-001`。保留「不改切分、Embedding、Query Rewrite」和「不用 holdout 调参」。

### 4.3 `PRAG-003` 不要依赖重排

结构化引用改的是响应形状，和有没有 Reranker 无关。现在的链是 `PRAG-002` → `PRAG-003` → `REL-001`。重排实验一旦不做或做完不采纳，Swagger 门禁会被挡住。

`PRAG-003` 改为依赖已经完成的来源字段任务（`QA-002`），在自己的验收里更新 OpenAPI。`REL-001` 的前置恢复为只有 `CLI-001`。

### 4.4 `PAGT-001` 不要先于工具契约暴露写能力

`file_ops` 含写。卡片是 L2，却排在十要素契约 `PAGT-002` 之前，并且 `nightly.eligible` 为 true。夜间流程只允许 L0 或已批准的 L1。

建议：`web_search` 与 `file_ops` 的读可以先做；写路径要么和十要素同一张卡交付，要么等 `PAGT-002` 把该工具标成 L2 且默认关闭后再开。未单独批准的 L2、L3 新卡，`nightly.eligible` 改为 false。抽查 `PRAG-001`、`PRAG-003` 也是 L2 且夜间可执行，并入时一并改掉。

`SKILL-001` 不要改成依赖 `PAGT-001`。现行技能任务的交付是成员能创建并选用技能，不要求搜索和文件工具先存在。两个新工具作为并行 P0 即可。

## 6. 建议补充的 2 张卡

### 6.1 既有测试失败

草案已经指出：约 65 个测试 error，集中在导入任务、权限语义和沙箱，会挡住 `NFR-001` 的全绿。36 张卡里没有这一张。

建议新增一张 P0：修到这几组测试可收集、可判定，不把失败改成跳过。`NFR-001` 不依赖它也能先把流水线接上。企业上线的「CI 全绿」依赖它。

需求 §4.5 还有「覆盖率 ≥ 70%」。不要为此再开一张凑覆盖率的卡。测试可收集之后，在 `REL-003` 或 CI 里报告覆盖率数字即可。

### 6.2 生产检索不得使用 Mock Embedding

`AGENTS.md` 写明：没有真实 Embedding 时，开发环境可以用 Mock，只能证明链路。生产缺密钥时检索应失败。36 张卡里的压测、重排、引用都没有这道门。用 Mock 跑出的 Recall 或延迟不能当上线证据。

建议新增一张 P0：生产配置缺少 Embedding 密钥时，启动自检或 `/health` 标明检索不可用，检索请求失败且不回退到 Mock；记录所用模型与维度。不在这张卡里更换模型或重做索引。
