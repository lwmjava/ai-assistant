# ai-assistant 夜间 AI 自主开发与次日人工审核指南

> 适用于 Cursor Cloud Agent、Codex Cloud Task 或受控的本地后台 Agent。目标是夜间交付一个可审核的任务切片，不是让 AI 无人监督地完成、合并或发布整个企业项目。

固定必读：

- `../../AGENTS.md`
- `../AI辅助开发迭代指导.md`
- `../governance/agent-harness-engineering.md`
- `../../tasks.yaml`
- `../checklists/morning-review-checklist.md`

## 1. 运行原则

夜间 AI 只拥有执行权，不拥有以下决策权：

- 产品范围和验收口径。
- 架构、公共契约和数据迁移决策。
- 风险接受和权限提升。
- 合并、生产发布和不可逆操作。

标准闭环：

```text
白天定义任务与批准计划
→ 夜间在隔离分支执行
→ 自动测试与 Evaluation
→ 生成草稿 PR 和证据包
→ 次日独立 AI 审查
→ 人工业务验收
→ 人工决定修改、合并或放弃
```

## 2. 夜间任务准入条件

任务只有同时满足以下条件才能标记为 `nightly_ready`：

1. 已关联批准的 Product Spec、Architecture/ADR 和任务契约。
2. 目标、Non-goals、允许路径和禁止路径明确。
3. 单个任务可独立测试、审核和回滚。
4. 预计工作量不超过一个夜间窗口，建议 2～4 小时有效编码。
5. 所有依赖任务已完成。
6. 验收标准可执行，不使用“基本可用”“效果良好”等主观表述。
7. 基线测试、任务测试和 Evaluation 命令来自真实仓库。
8. 风险为 L0 或经批准的 L1；不得包含 L3。
9. 不需要中途产品、架构、数据或权限决策。
10. 不使用生产数据库、生产凭据或不可脱敏数据。
11. 已定义失败停止条件、超时、预算和回滚方式。
12. 已指定次日审核人。

任一条件不满足，任务保持 `blocked`、`backlog` 或 `ready`，不得夜间执行。状态枚举以根目录 `tasks.yaml` 的 `status_values` 为准，不得使用未定义状态。

## 3. 适合与禁止的任务

适合：

- 边界明确的只读 Tool、Adapter 或 API。
- 已批准 Skill 的单个工作流步骤。
- 单模块功能和配套测试。
- 稳定可复现 Bug 的最小修复。
- Evaluation Case、契约测试、文档同步。
- lint、类型检查、明确的小范围兼容修复。

禁止：

- 破坏性数据库迁移、生产数据修复。
- 支付、退款、合同、权限或密钥操作。
- 大规模架构重构和跨仓库迁移。
- 无稳定复现的线上故障。
- 需求和验收仍存在关键歧义的功能。
- 自动合并、自动生产部署、关闭回退路径。

## 4. 白天准备阶段

### 4.1 固化事实源

提交并指定：

- `AGENTS.md` 与适用 `.cursor/rules`。
- Product Spec、Architecture、ADR、Agent/Tool/Skill Spec。
- 当前 `tasks.yaml`。
- 基线测试和 Evaluation 报告。
- 构建、测试、运行和清理命令。

Cloud Agent 无法获得未提交且未推送的本地文件。移交前必须确认远程分支包含全部必要上下文。

### 4.2 审批 Implementation Plan

计划必须列出：

- 实际读取的文件和确认事实。
- 拟修改文件。
- 测试先行步骤。
- 正常、失败、权限和真实业务验证。
- 兼容性、迁移和回滚。
- 需要人工决定的事项。

如果计划扩大范围，先拆新任务，不得直接批准“顺便修改”。

### 4.3 配置运行边界

- 独立分支、Worktree 或云端 VM。
- 只授予目标仓库权限。
- 使用测试账号和短期凭据。
- 限制出网域名和 MCP 工具。
- 设置最大执行时间、最大重试次数和成本预算。
- 主分支保护、必需 CI 和必需人工审核。

规则文件只能指导模型，不能替代权限、网络、分支和 CI 控制。

## 5. 夜间执行状态机

```text
QUEUED
→ PRECHECK
→ BASELINE
→ TEST_DESIGN
→ IMPLEMENTING
→ VERIFYING
→ SELF_REVIEW
→ DRAFT_PR
→ AWAITING_HUMAN_REVIEW
```

异常状态：

- `BLOCKED`：缺少事实、权限、依赖或人工决策。
- `FAILED`：执行或验证不可恢复失败。
- `BUDGET_EXCEEDED`：时间、轮次、Token 或费用超限。
- `CANCELLED`：人工或系统取消。

状态迁移必须写入任务日志，禁止用聊天内容隐式表示。

## 6. 夜间执行步骤

1. 检查仓库、分支、提交和工作区状态。
2. 读取规则、任务和关联文档。
3. 核对依赖、允许路径、风险和停止条件。
4. 运行修改前基线测试并保存结果。
5. 先创建能验证需求的失败测试或 Evaluation Case。
6. 确认失败原因是目标行为尚未实现。
7. 做满足任务验收的最小实现。
8. 运行 Unit、Contract/Integration、Agent/RAG、业务回归。
9. 运行防漂移和安全检查。
10. 核对 diff 是否只在允许范围内。
11. 生成草稿 PR，不合并、不部署。
12. 生成机器可读和人可读证据包。

## 7. 强制停止条件

出现以下情况立即停止扩大修改：

- 需要修改允许路径之外的文件。
- 发现需求或架构歧义会改变实现方向。
- 修改前基线已失败，且无法隔离原有失败。
- 同一验证失败修复 3 次仍未通过。
- 需要新增未批准依赖或改变公共契约。
- 发现密钥、生产数据、越权或跨租户风险。
- 需要破坏性命令、生产写入或高风险审批。
- 无法证明真实业务验收。

停止后保留分支和日志，报告“已完成、未完成、阻塞证据、建议决策”，不得降低测试或绕开规则。

## 8. 夜间交付证据包

草稿 PR 必须包含：

1. 任务 ID 和关联验收标准。
2. 实际修改文件及原因。
3. 修改前失败与修改后通过的同一测试证据。
4. 所有执行命令、退出码和报告路径。
5. Evaluation 基线、候选结果和关键风险切片。
6. 脱敏真实业务验证、`trace_id` 或审计证据。
7. 兼容性、迁移和回滚说明。
8. 未运行项目、残余风险和阻塞项。
9. AI 使用的模型、Prompt、Tool、RAG 索引和配置版本。

禁止只写“测试通过”“已完成”“应该没有问题”。

## 9. 次日审核顺序

1. 人先读任务和验收，不先看 AI 总结。
2. 独立审查者检查完整 diff、调用方和测试质量。
3. 重跑关键命令，不能只使用夜间日志。
4. 用脱敏真实业务数据执行主、备、失败和权限路径。
5. 核对最终业务系统状态、事件、审计和 Trace。
6. 检查是否超范围、过度 Mock 或弱化断言。
7. 决定：接受、修改后接受、重新实现或放弃。

## 10. 渐进提高自治程度

新人建议：

- 第 1～2 周：每晚最多一个 L0 小任务，所有计划白天逐项批准。
- 第 3～4 周：稳定后允许一个 L1 可撤销任务，仍禁止自动合并。
- 连续多次达到验收后，才能增加并行任务数量。
- 一旦出现业务回归、越权、漂移或无证据完成，立即降低自治级别。

自治升级以历史通过率和事故数据为依据，不以对 AI 的主观信任为依据。

## 11. ai-assistant 当前夜间边界

当前适合：

- 文档事实核对和链接修复。
- Evaluation JSON Schema、数据校验和确定性评分测试。
- 已批准资料上的 Silver/Adversarial 候选生成。
- 无副作用的 RAG 参数实验脚本。
- 稳定复现且修改范围单一的测试补充。

当前禁止：

- 决定知识库“租户共享还是资源私有”。
- 决定 Local/Milvus 的生产选型。
- 自动修改或删除知识库、索引和数据库数据。
- 同时重构 ChatService、AgentPipeline、Tool 和 State。
- 在没有 baseline 时声称某种 Chunking、Embedding 或 Reranker 更优。
- 自动合并、推送未审查版本或部署。

夜间 RAG 任务至少运行任务声明的聚焦测试；涉及通用代码时再扩大到全量：

```powershell
pytest tests/test_rag.py tests/test_rag_import_jobs.py tests/test_rag_backend.py tests/test_chunking.py -v
ruff check .
mypy app/
```
