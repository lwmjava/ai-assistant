# 恢复时间与数据丢失目标

本文给出本仓库当前单机生产编排的内部运营目标：RPO 与 RTO。它们用于判断备份是否足够新、恢复是否及时，不是对外服务协议（SLA），也不构成可用性百分比、异地容灾或赔付承诺。

适用对象是 [生产备份与恢复](backup-restore.md) 覆盖的三份数据：PostgreSQL 逻辑备份、知识库上传目录，以及 Milvus 相关的 `milvusdata` / `etcddata` / `miniodata` 卷归档。README 中的开发用 SQLite 备份不按这两个数字验收。本文不改备份脚本，也不做容灾架构或定时调度配置。

## 定义

| 指标 | 含义 | 起算与截止 |
|---|---|---|
| RPO（恢复点目标） | 宣布恢复时，允许丢失的数据时间窗口上限 | 宣布故障或开始恢复的时刻，减去最近一次**完整**备份的 `manifest.json` 时间戳。只有同时包含 PostgreSQL、上传目录和 Milvus 三份产物、且校验和核验通过的备份，才算一个恢复点。不完整目录不能用来计算 RPO。 |
| RTO（恢复时间目标） | 从宣布开始恢复到服务重新可用所允许的最长时间 | 宣布开始恢复的时刻，到三项数据核验与应用健康检查均通过的时刻。准备授权、定位备份、执行恢复、启动依赖服务和完成核验都计入；不包括日常备份窗口本身。 |

时间一律按 Asia/Shanghai 记录，并写明时区。脚本或容器若输出其他时区，换算后再记账。

## 目标值与依据

| 指标 | 目标 | 依据 |
|---|---|---|
| RPO | ≤ 24 小时 | 需求方案要求生产库按日做备份。当前可恢复流程是对上述三份数据做一次完整备份，没有异地复制或连续归档，因此不能把丢失窗口写成接近零。按日完成一次完整备份，可将丢失窗口控制在一天以内。 |
| RTO | ≤ 4 小时 | 当前是单机生产编排，恢复按已文档化的脚本执行，不必等待多机切换或异地回切。4 小时覆盖定位完整备份、准备获授权的目标环境、依次恢复三份数据、启动 etcd / MinIO / Milvus 与应用，并完成文档要求的核验，而不是只计算脚本墙钟。 |

这两个数字是运营目标。数据量显著大于日常规模、镜像需要现场拉取、或恢复目标尚未准备好时，墙钟可能超过 4 小时；在有代表性的数据上完成一次计时演练之前，不得把目标写成已经实测达标。

## 与备份频率对齐

要维持 RPO ≤ 24 小时，必须至少每 24 小时成功生成一份完整备份（PostgreSQL + 上传目录 + Milvus 卷），并保留 `manifest.json` 与校验和。

现有 `scripts/backup.sh` 支持按需生成这份完整备份。仓库内没有配置定时任务；部署方需要自行按日执行，或在获得授权后另配调度。漏做日备、或只备份了其中一部分，都视为当前没有按该 RPO 运营，即使脚本本身可用。

备份 Milvus 卷前会停止 `milvus`、`etcd` 和 `minio`，完成后再次启动。日备应放在低峰时段。这段备份停写窗口计入备份操作，不计入 RTO。PostgreSQL 使用逻辑备份，不必为此停库。

## 与恢复流程对齐

恢复步骤、隔离目标确认和核验项以 [生产备份与恢复](backup-restore.md) 为准，顺序建议为：先恢复 PostgreSQL 与上传目录，再恢复 Milvus 卷，然后启动 etcd、MinIO、Milvus 和应用。核验至少包括：

1. 数据库迁移修订与备份来源一致，用户、租户、对话等业务行可查询。
2. 上传目录文件数量、路径和校验和与 `uploads/files.json` 一致。
3. Milvus 可连接，集合名与向量条数符合来源预期；若启动的是生产应用，再做健康检查和一次检索或业务核验。

该流程可以支撑 4 小时的 RTO，前提是完整备份已在可访问位置、目标环境已获授权并准备就绪，且数据量属于该单机部署的常规规模。它不支撑不停机恢复、跨机房切换或未授权写入生产项目。覆盖已有重要数据或恢复到生产，仍须单独授权。

## 如何用演练记录核算

一份演练或真实恢复记录必须同时写出下列字段，才能对照本目标判定是否合格：

| 字段 | 要求 |
|---|---|
| 最近完整备份时间 | 来自所用备份目录的 `manifest.json`，时区为 Asia/Shanghai |
| 宣布开始恢复的时间 | 含日期、时刻和时区 |
| 恢复完成时间 | 三项数据核验与应用健康检查均通过的时刻，含时区 |
| 计算出的 RPO | 开始恢复时间 − 最近完整备份时间，须 ≤ 24 小时 |
| 计算出的 RTO | 恢复完成时间 − 开始恢复时间，须 ≤ 4 小时 |
| 三类数据恢复结果 | PostgreSQL、上传目录、Milvus 均有通过证据 |

缺时间戳、只恢复部分数据、或只用开发 SQLite 代替生产三份数据的记录，不能用来判定达标。探针级隔离演练可以证明脚本可恢复，但数据量不能代表生产规模，也未计时，则不能用来宣称 RTO 或 RPO 已经达标。当前隔离演练记录见 [隔离备份恢复演练记录](backup-restore-drill.md)。
