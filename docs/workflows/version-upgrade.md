# 版本升级说明

产品要求的升级流程是：**停写 → 迁移 → 启动**，再做验证。跨版本不兼容变更必须先写入 [CHANGELOG.md 的 Breaking 区](../../CHANGELOG.md#breaking)，再执行升级。

本页只说明这条发布约定，并与 Breaking 区交叉引用。它不是完整的升级回滚操作手册，也不代替一次真实的跨版本升级与回滚演练。演练记录应链接到 [Breaking 区](../../CHANGELOG.md#breaking)，以及本次升级所涉及版本下的 `### Breaking` 小节。

## 升级顺序

1. **记录不兼容变更**
   若目标版本包含不兼容变更，先按 [Breaking 区约定](../../CHANGELOG.md#breaking) 写入对应版本条目，再开始停写。没有不兼容变更时，仍保留该版本的 Breaking 标题，并写明「无」。

2. **停写**
   停止接受新的用户写入，避免备份、迁移与在途写请求不一致。

3. **迁移**
   在停写后执行数据库迁移，使 schema 到达目标版本。若还有索引重建或配置迁移，按该项变更在 Breaking 区写明的办法执行。

4. **启动**
   启动目标版本应用及必要依赖。

5. **验证**
   核对健康检查、迁移修订，以及升级前抽样的业务数据是否仍可访问。验证失败时不要继续写入新数据，按变更前备份与 Breaking 区载明的回滚要求处理。

## 回滚要点

回滚的目标是服务与数据都回到升级前状态。若 Breaking 区写明必须启动变更前应用版本，只恢复数据却继续运行新版本，通常不能视为回滚成功。

具体操作步骤、隔离约束与演练证据由升级回滚专项交付；本页不展开命令，也不把尚未完成的演练写成已通过。
